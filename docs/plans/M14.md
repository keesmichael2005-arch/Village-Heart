# M14 plan: village tiers and unlocks

Planner: Opus, 2026-11-07. Builder: implement in the step order of section 4; every step ends green on
`scripts/verify.sh --fast`. APIs marked **[verified]** were read in the decompiled 1.21.11 Mojang-mapped sources
(`minecraft-common-…-sources.jar` in the Loom cache). No Gradle build was run for this plan (static checks only).

M14 builds on M1-M8 and M24 (merged on `dev`) and on three in-flight plans: M11 (dinner, `origin/m11-plan`), M12 (dawn
event and treasury, `origin/m12-plan`) and M20 (blueprints, `origin/m20-plan`). Section 3.1 lists every assumption about
them and what to do if one is wrong. **Build gate:** M14 is built after M11 and M12 are on `dev` (ROADMAP order). Steps 1-2
need neither; step 3 starts with a checkpoint against their real code.

## 1. Goal

A village grows from Hamlet to Village to Town. Every dawn the mod checks the next tier's goals (DESIGN §9); when all are met
the tier goes up one step, the owner and members get a chat line, markers that were red with "Requires Village tier" are
re-checked at once and turn green, and the higher-tier jobs can be hired. The Overview tab shows the next tier's goals as a
checklist with live progress ("Population 4 / 6", "Fed days in a row 1 / 3", a green box for each met goal). The tier never goes down.

### 3.2 Rules (decisions)

1. **Goals** (DESIGN §9, numbers in `Balance`, tunable):

   | Next tier | Goals, in checklist order |
   |---|---|
   | Village (from Hamlet) | population ≥ 6; workers ≥ 3; a valid Storage; a valid Farmhouse; a valid Kitchen; fed days in a row ≥ 3 |
   | Town (from Village) | population ≥ 12; workers ≥ 8; guards ≥ 2; fed days in a row ≥ 7; treasury ≥ 32 at a dawn |
   | none (Town) | no goals; the Overview says "Highest tier reached" |

2. **Population** = the Overview's population: villagers loaded in the claim sphere (adults and babies) plus registered workers that are
   not in that census (DESIGN §10 "Population counts loaded villagers plus recorded workers that are not loaded"). One pure formula,
   `core.tier.Population.count(Set<UUID> census, List<WorkerRecord> workers)` = `|census| + |workers not in census|`, used by both the
   Overview and the dawn check, so the checklist number is the number the tier-up uses. `HeartFacts` keeps its adult/baby split for the
   other Overview lines; an L1 test pins `Population.count` against HeartFacts' formula on the same input (T-L1-5).
3. **Workers** = `VillageState.workers().size()` (registered workers, loaded or not, strikers included: they are still employed).
   **Guards** = workers with `jobId == JobType.GUARD.id()`.
4. **Valid building** = at least one `Buildings.valid(server, type)` entry (verdict status VALID) at the moment of the check.
5. **A fed day** = a dinner with `diners > 0 && fed == diners` (everyone who ate was fed, children included). Any other dinner is a
   **hungry day** and resets the streak to 0 (roadmap: "resetting on a hungry day"); a dinner with nobody to feed also resets it.
   A day without a dinner (Heart unloaded, a `/time` jump over 11000, a storm sleep) leaves the streak unchanged: the village is frozen
   or skipped, and DESIGN §6 has no catch-up. The streak saturates at `Balance.MAX_FED_STREAK = 9999` (it is shown as a text arg).
   The streak keeps running across a tier-up (a village fed 7 days from the start is fed-ready for Town).
6. **Idempotent dinner count:** `TierProgress.lastDinnerDay` records the day index last counted; a second report for the same day index
   is ignored. The comparison is `!=` like M11's clock, so `/time set 1000` (day index back to 0) still counts that evening's dinner.
7. **Treasury at a dawn:** at every dawn (any tier) the listener records `bestDawnTreasury = max(best, treasury after wages)`. "After
   wages" because that is what the purse holds at dawn and what the Overview shows from then on; a village must be able to pay its bill
   and still hold 32. The goal is met once `bestDawnTreasury ≥ 32` (sticky: "at some dawn"). The checklist shows `min(best, 32) / 32`.
   On the wages-off test branch the treasury is simply the current one (`PayResult.none`).
8. **When the tier changes:** only at a dawn, after wages, and at most **one step per dawn** (Hamlet → Village, then Town no earlier than
   the next dawn). Order inside the listener: record the dawn treasury, then evaluate the next tier's goals with the updated progress,
   then tier up if all are met. Population and building validity are read live in that tick.
9. **The tier never goes down** (v1): there is no code path that lowers it except the op command `tier set` (3.7), which is an admin
   tool. `VillageState.tierUp()` throws at TOWN; `withTier` stays for tests and the command.
10. **Dawn-tick ordering** (one server tick, `VillageSystems` run at `END_SERVER_TICK` in registration order):
    `villageheart:buildings` (M5) … `villageheart:dinner` (M11) → `villageheart:needs` (M11) → `villageheart:wages` (M12) which, after the
    wage write, fires `VillageDawn` listeners in registration order: `villageheart:tiers` (M14, registered in `VillageHeart.onInitialize`
    right after M12's wage system) → later `villageheart:breeding` (M23). Dinner (11000) and dawn (0) are never due in the same tick in
    normal play. After a `/time set` that lands at phase ≥ 11000 on a new day index, both are due in one tick: dinner runs first, so that
    dawn already counts that day's dinner. Deterministic and documented; no special case.
11. **Release:** a new claim starts from `VillageState.founded` → Hamlet with `TierProgress.INITIAL`. Nothing else to clear.

### 3.3 Core (pure, L1-tested): `dev.villageheart.core.tier`

```java
public enum GoalId { POPULATION, WORKERS, GUARDS, STORAGE, FARMHOUSE, KITCHEN, FED_DAYS, DAWN_TREASURY }

/** Everything the goals read. Booleans are "a valid one exists". */
public record TierInputs(int population, int workers, int guards, boolean validStorage, boolean validFarmhouse,
        boolean validKitchen, int fedStreak, int bestDawnTreasury) {}            // all ints >= 0 (compact ctor)

public record Goal(GoalId id, int have, int need) { public boolean met() { return have >= need; } }

/** goals empty iff next is empty (Town). */
public record TierReport(Tier current, Optional<Tier> next, List<Goal> goals) {
    public boolean allMet();                                                   // !goals.isEmpty() && every goal met
}

public final class TierGoals {
    public static List<GoalId> goalsFor(Tier target);                          // the table of 3.2 #1, in checklist order
    public static int maxGoals();                                              // 6 (pinned against HeartLimits.MAX_GOALS and the screen rows)
    public static TierReport evaluate(Tier current, TierInputs in);            // have for booleans is 0/1, need 1
}

public record TierProgress(int fedStreak, long lastDinnerDay, int bestDawnTreasury) {
    public static final long NO_DAY = Long.MIN_VALUE;
    public static final TierProgress INITIAL = new TierProgress(0, NO_DAY, 0);
    public TierProgress afterDinner(long day, int diners, int fed);            // 3.2 #5, #6
    public TierProgress atDawn(int treasury);                                  // best = max(best, treasury)
}

public record DawnOutcome(Tier tier, TierProgress progress, TierReport report, boolean tieredUp) {}

public final class TierDawn {
    /** 3.2 #7-#8: progress.atDawn(treasury), evaluate with the new progress, one step up if allMet. */
    public static DawnOutcome run(Tier current, TierProgress progress, TierInputs liveInputs, int treasuryAfterWages);
}

public final class TierRules {
    public static Optional<Tier> next(Tier t);
    public static int levelCap(Tier t);                                        // 1 / 2 / 3 (Balance.LEVEL_CAPS)
    public static int levelFromXp(int xp);                                     // Balance.LEVEL_2_XP / LEVEL_3_XP thresholds (M8's JobLevels numbers)
    public static int levelFor(int xp, Tier t);                                // min(levelFromXp(xp), levelCap(t)); the rule M15 must use
}

public final class Population { public static int count(Set<UUID> census, List<WorkerRecord> workers); }
```

`TierDawn.run` takes `liveInputs` with the *stored* `fedStreak/bestDawnTreasury` ignored and replaced by the updated progress, so the
glue cannot pass a stale value. `Balance`: `VILLAGE_POPULATION = 6, VILLAGE_WORKERS = 3, VILLAGE_FED_DAYS = 3, TOWN_POPULATION = 12,
TOWN_WORKERS = 8, TOWN_GUARDS = 2, TOWN_FED_DAYS = 7, TOWN_DAWN_TREASURY = 32, MAX_FED_STREAK = 9999`, `LEVEL_CAPS = {1, 2, 3}` behind
`levelCapFor(Tier)` (no mutable array exposed).

`core.VillageState`:
- new **last** component `TierProgress tierProgress` (non-null); a second public constructor with the old 10 arguments that passes
  `TierProgress.INITIAL`, so the 13 existing `new VillageState(...)` call sites (tests, codec) keep compiling; `copy(...)` carries it
  (every `with*` keeps the progress: T-L1-6 checks this for each one);
- `withTierProgress(TierProgress)`, `tierUp()` (= `withTier(next)`, throws `IllegalStateException` at TOWN).

### 3.4 Glue: `dev.villageheart.tier`

- **`TierFacts.inputs(MinecraftServer, VillageState, Set<UUID> censusIds) : TierInputs`**: `Population.count`, workers, guards,
  `Buildings.valid` for STORAGE / FARMHOUSE / KITCHEN, progress fields from the state. `HeartFacts.collect` passes the census it
  already has (no second entity scan, `VillageCensus` "at most once a second" rule); the dawn listener takes a fresh `VillageCensus.of`.
- **`Tiers.register()`** (from `VillageHeart.onInitialize`, after M12's wage registration):
  `VillageDawn.register("villageheart:tiers", Tiers::onDawn)`.
- **`Tiers.onDinner(server, long day, int diners, int fed)`**: `VillageSavedData.update(v -> v.withTierProgress(v.tierProgress()
  .afterDinner(day, diners, fed)))`, skipped when the result equals the stored progress (no `setDirty` for nothing). Called by M11's
  `DinnerSystem` right after `Dinner.serve` returned (one line in M11 code; the only M14 edit inside M11). INFO log only when the streak
  resets from > 0: `[tiers] day D: hungry dinner (F/N fed), fed streak reset from S`.
- **`Tiers.onDawn(server, village, day, PayResult r)`**: `inputs = TierFacts.inputs(server, village, census)`;
  `out = TierDawn.run(village.tier(), village.tierProgress(), inputs, r.treasuryAfter())`; one `VillageSavedData.update(v ->
  v.withTierProgress(out.progress())` + `.tierUp()` when `out.tieredUp()`). Then, only on a tier-up, **the tier-up effects**:
  1. `Buildings.requestAll(server)`: every marker is prioritised, so "Requires Village tier" markers turn green within about
     `n + hops` ticks (1 priority check per tick) instead of up to `n × 20`; a Mineshaft turning valid re-queues its Mine
     (`prioritiseDependents`, M5).
  2. `HeartFacts.invalidate()`, so open Heart screens get the new tier and the Town checklist on their next ≤ 1 Hz send.
  3. Chat to every online player whose `rankOf` is at least RESIDENT (owner included):
     `Component.translatableWithFallback("message.villageheart.tier_up", "Your village is now a %s! New buildings and jobs are unlocked.", tierName)` **[verified: `Component.translatableWithFallback(String, String, Object...)`]**,
     sent with `ServerPlayer.sendSystemMessage`; and `level.playSound(null, heartPos, SoundEvents.PLAYER_LEVELUP, SoundSource.BLOCKS, 1f, 1f)`
     at the Heart **[verified: `Level.playSound(Entity, BlockPos, SoundEvent, SoundSource, float, float)`, `SoundEvents.PLAYER_LEVELUP` is a `SoundEvent`]**.
  4. INFO log: `[tiers] day D: Hamlet -> Village (population 6, workers 3, fed streak 3)`.
  Hiring unlocks need no code (`JobSlots` reads the tier); blueprint unlocks need none (A8); level caps are read by M15 (A7).
- **M12 change (A5):** `WageSystem` fires `VillageDawn` on both branches; the consumed branch passes `PayResult.none(day, treasury)`
  (a static factory added to M12's record: `paid` and `unpaid` empty, `spent = 0`, `before == after == treasury`, `bill` = the current
  bill). An existing M12 test that asserts "no listener ran with wages off" (if any) is wrong under DESIGN §9 and is changed with a
  commit note.
- Everything runs inside M12's timed wage section (the dawn tick), so it counts towards `VillageTicker` (1 ms budget; the dawn work is
  one census plus three `Buildings.valid` filters, once a day).

### 3.7 Saved data, commands, networking, assets

## 6. Risks, unknowns, out of scope

**Risks**
1. **Top risk: M11/M12 names and hooks.** M14 hangs on two seams it does not own: M11's dinner result (A1) and M12's `VillageDawn`
   (A4), and needs one behaviour M12's plan does not promise: listeners firing when wages are off (A5). Mitigated by keeping M14's side
   to two entry points (`Tiers.onDinner`, `Tiers.onDawn`), a checkpoint at step 3, and T-L2-1 running with wages off so a missing fire
   fails loudly instead of every later tier test silently never tiering up.
2. **Merge churn in `VillageState`, `VillageCodecs.RAW` and `VillageFacts`:** M11 and M12 add components to the same records. The
   `copy(...)` helper and the extra constructor keep it mechanical; T-L1-6 catches a dropped field. RAW's 16-field limit: 3.7.
3. **`requestAll` cannot be proved by timing** (the round-robin may re-check the Mine within the bound by luck). The in-tick probe listener
   is deterministic; if `VillageDawn` registration is not closeable (A4), the probe is a static flag-guarded listener.
4. **Strict "everyone fed"** may be harsh once vanilla breeding adds babies that the stock cannot cover; tunable later (M26 balance),
   not loosened here.
5. **Yard space:** shaft, elevated Mine and three rooms plus 6 villagers in 32 × 32. Villagers wander into rooms; that changes nothing the
   tests assert (population is the claim sphere). If the yard is too tight the builder drops the Mine from T-L2-2 (it is only a control there).
6. **Babies count towards population** (same number as the Overview). A player could reach 6 with babies; acceptable and consistent with
   DESIGN §10, recorded in DESIGN §9 "as built".

**Out of scope:** levelling and XP (M15 applies `TierRules.levelFor`); Smithy golems and gear, Watchtower (later milestones); M20's
blueprint list (reads the tier itself); tier-down or tier decay; advancements, toasts or particles for a tier-up (chat and a sound only);
L3 metrics for the tier (a later scenario can add `village.tier` and `tier.fed_streak` when a milestone needs to assert progression);
a "days until tier-up" estimate.
