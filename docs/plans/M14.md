## 1. Goal

A village grows from Hamlet to Village to Town. Every dawn the mod checks the next tier's goals (DESIGN §9); when all are met
the tier goes up one step, the owner and members get a chat line, markers that were red with "Requires Village tier" are
re-checked at once and turn green, and the higher-tier jobs can be hired. The Overview tab shows the next tier's goals as a
checklist with live progress ("Population 4 / 6", "Fed days in a row 1 / 3", a green box for each met goal). The tier never goes down.

### 3.2 Rules (decisions)

1. **Goals** (DESIGN §9, numbers in `Balance`, tunable):

   | Next tier | Goals, in checklist order |
   |---|---|
   | Village (from Hamlet) | population ≥ 6; workers ≥ 3; a valid Storage; a valid Farmhouse; a valid Kitchen; fed days in a row ≥ 3 |
   | Town (from Village) | population ≥ 12; workers ≥ 8; guards ≥ 2; fed days in a row ≥ 7; treasury ≥ 32 at a dawn |
   | none (Town) | no goals; the Overview says "Highest tier reached" |

2. **Population** = the Overview's population: villagers loaded in the claim sphere (adults and babies) plus registered workers that are
   not in that census (DESIGN §10 "Population counts loaded villagers plus recorded workers that are not loaded"). One pure formula,
   `core.tier.Population.count(Set<UUID> census, List<WorkerRecord> workers)` = `|census| + |workers not in census|`, used by both the
   Overview's population line and the dawn check, so the checklist number is the number the tier-up uses. `HeartFacts` keeps its
   adult/baby split only for the food-days formula and passes `Population.count` into `VillageFacts` as a new `population` fact
   (`HeartSnapshotBuilder` stops computing `adults + babies`; same value as today by construction).
3. **Workers** = `VillageState.workers().size()` (registered workers, loaded or not, strikers included: they are still employed).
   **Guards** = workers with `jobId == JobType.GUARD.id()`.
4. **Valid building** = at least one `Buildings.valid(server, type)` entry (verdict status VALID) at the moment of the check.
5. **A fed day** = a dinner with `diners > 0 && fed == diners` (everyone who ate was fed, children included). Any other dinner is a
   **hungry day** and resets the streak to 0 (roadmap: "resetting on a hungry day"); a dinner with nobody to feed also resets it.
   A day without a dinner (Heart unloaded, a `/time` jump over 11000, a storm sleep) leaves the streak unchanged: the village is frozen
   or skipped, and DESIGN §6 has no catch-up. The streak saturates at `Balance.MAX_FED_STREAK = 9999` (it is shown as a text arg).
   The streak keeps running across a tier-up (a village fed 7 days from the start is fed-ready for Town).
6. **Idempotent dinner count:** `TierProgress.lastDinnerDay` records the day index last counted; a second report for the same day index
   is ignored. The comparison is `!=` like M11's clock, so `/time set 1000` (day index back to 0) still counts that evening's dinner.
   Known and accepted: an admin alternating `/time set` between two day indices makes M11 serve a dinner each time and each counts
   (admin-only behaviour, pinned by a T-L1-2 case, documented).
7. **Treasury at a dawn:** at every dawn (any tier) the listener records `bestDawnTreasury = max(best, treasury after wages)`. "After
   wages" because that is what the purse holds at dawn and what the Overview shows from then on; a village must be able to pay its bill
   and still hold 32. The goal is met once `bestDawnTreasury ≥ 32` (sticky: "at some dawn"). The checklist shows `min(best, 32) / 32`.
   On the wages-off test branch the treasury is simply the current one (`PayResult.none`).
8. **When the tier changes:** only at a dawn, after wages, and at most **one step per dawn** (Hamlet → Village, then Town no earlier than
   the next dawn). Order inside the listener: record the dawn treasury, then evaluate the next tier's goals with the updated progress,
   then tier up if all are met. Population and building validity are read live in that tick.
9. **The tier never goes down** (v1): no code path lowers it (`withTier` is only used by tests; a later admin command may), and
   `VillageState.tierUp()` throws at TOWN.
10. **Dawn-tick ordering** (one server tick, `VillageSystems` run at `END_SERVER_TICK` in registration order):
    `villageheart:buildings` (M5) … `villageheart:dinner` (M11) → `villageheart:needs` (M11) → `villageheart:wages` (M12) which, after the
    wage write, fires `VillageDawn` listeners in registration order: `villageheart:tiers` (M14, registered in `VillageHeart.onInitialize`
    right after M12's wage system) → later `villageheart:breeding` (M23). Dinner (11000) and dawn (0) are never due in the same tick in
    normal play. After a `/time set` that lands at phase ≥ 11000 on a new day index, both are due in one tick: dinner runs first, so that
    dawn already counts that day's dinner. Deterministic and documented; no special case.
11. **Release:** a new claim starts from `VillageState.founded` → Hamlet with `TierProgress.INITIAL`. Nothing else to clear.

### 3.3 Core (pure, L1-tested): `dev.villageheart.core.tier`

```java
public enum GoalId { POPULATION, WORKERS, GUARDS, STORAGE, FARMHOUSE, KITCHEN, FED_DAYS, DAWN_TREASURY }

/** Everything the goals read. Booleans are "a valid one exists". */
public record TierInputs(int population, int workers, int guards, boolean validStorage, boolean validFarmhouse,
        boolean validKitchen) {}                                               // live facts only; ints >= 0 (compact ctor)

public record Goal(GoalId id, int have, int need) { public boolean met() { return have >= need; } }

/** goals empty iff next is empty (Town). */
public record TierReport(Tier current, Optional<Tier> next, List<Goal> goals) {
    public boolean allMet();                                                   // !goals.isEmpty() && every goal met
}

public final class TierGoals {
    public static List<GoalId> goalsFor(Tier target);                          // the table of 3.2 #1, in checklist order
    public static int maxGoals();                                              // 6 (pinned against HeartLimits.MAX_GOALS and the screen rows)
    public static TierReport evaluate(Tier current, TierInputs in, TierProgress p);   // have for booleans is 0/1, need 1
}

public record TierProgress(int fedStreak, long lastDinnerDay, int bestDawnTreasury) {
    public static final long NO_DAY = Long.MIN_VALUE;
    public static final TierProgress INITIAL = new TierProgress(0, NO_DAY, 0);
    public TierProgress afterDinner(long day, int diners, int fed);            // 3.2 #5, #6
    public TierProgress atDawn(int treasury);                                  // best = max(best, treasury)
}

public record DawnOutcome(Tier tier, TierProgress progress, TierReport report, boolean tieredUp) {}

public final class TierDawn {
    /** 3.2 #7-#8: progress.atDawn(treasury), evaluate with the new progress, one step up if allMet. */
    public static DawnOutcome run(Tier current, TierProgress progress, TierInputs liveInputs, int treasuryAfterWages);
}

public final class TierRules {                                                  // EXISTS (M15): M14 adds next() only
    public static Optional<Tier> next(Tier t);                                 // NEW in M14
    public static int levelCap(Tier t);                                        // exists: 1 / 2 / 3 (Balance.LEVEL_CAPS)
    public static int levelFromXp(int xp);                                     // exists: cumulative XP, thresholds from JobLevels.xpForNext
    public static int levelFor(int xp, Tier t);                                // exists: min(levelFromXp(xp), levelCap(t)); M15 uses it
}

public final class Population { public static int count(Set<UUID> census, List<WorkerRecord> workers); }
```

### 3.6a The "needs a Town" notice after a tier-up (BACKLOG M15-r1)

## 6. Risks, unknowns, out of scope

**Risks**
1. **Seams (was the top risk, now low):** M11's dinner and M12's `VillageDawn` are on `dev` and verified (3.1); the wages-off fire is
   done. What is left is the one-line dinner hook using `fedCount`, not `plan.fed()` (A1), and T-L2-1 still runs with wages off so a
   regression in the `none` fire fails loudly.
2. **Top risk now: merge churn in `VillageState`, `VillageCodecs.RAW` and `VillageFacts`.** M13 and M19a (in flight) each add a
   `VillageState` component with a 13-argument compatibility constructor; whichever of the three lands last resolves the constructor
   chain. Four `with*` methods bypass `copy(...)` (section 2), which the T-L1-6 reflection sweep catches. RAW reaches its 16-field limit
   if all three land (3.7): the next milestone that adds a village key must use a nested `ext` codec.
3. **`requestAll` cannot be proved by timing** (the round-robin may re-check the Mine within the bound by luck). The in-tick probe listener
   is deterministic; if `VillageDawn` registration is not closeable (A4), the probe is a static flag-guarded listener.
4. **Strict "everyone fed"** may be harsh once vanilla breeding adds babies that the stock cannot cover; tunable later (M26 balance),
   not loosened here.
5. **Yard space:** shaft, elevated Mine and three rooms plus 6 villagers in 32 × 32. Villagers wander into rooms; that changes nothing the
   tests assert (population is the claim sphere). If the yard is too tight the builder drops the Mine from T-L2-2 (it is only a control there).
6. **Babies count towards population** (same number as the Overview). A player could reach 6 with babies; acceptable and consistent with
   DESIGN §10, recorded in DESIGN §9 "as built".

**Out of scope:** levelling and XP (M15, built; M14 only adds the 3.6a notice); Smithy tools, golems and gear (M19), Watchtower (M21, built); M20's
blueprint list (reads the tier itself); tier-down or tier decay; advancements, toasts or particles for a tier-up (chat and a sound only);
the `/villageheart tier` command (first needed by a later L3 scenario); L3 metrics for the tier (a later scenario can add `village.tier` and `tier.fed_streak` when a milestone needs to assert progression);
a "days until tier-up" estimate.
