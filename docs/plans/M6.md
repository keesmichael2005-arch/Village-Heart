## 1. Goal

The village has one shared **stockpile**: the combined contents of every chest and barrel inside the village's valid Storage
buildings. Chests in other buildings (a House, a Lumber Camp's tool chest) are not part of it. Code can ask "how much bread
does the village have?", deposit goods (they go into the nearest Storage with space and spill into the next one, and whatever
does not fit comes back) and withdraw from any Storage. When every Storage slot is taken, the village raises a **"Storage
full"** alert. Nothing new is visible in the world yet: the workers (M7+) and the Heart screen (M8) are the consumers.

## 3. Design

### 3.1 Concepts and rules (pinned; DESIGN §6 gets these clarifications)

- **Stockpile container** = a position listed under `#chest` or `minecraft:barrel` in the latest scan of a **valid Storage**,
  holding a `ChestBlockEntity` (covers trapped and copper chests) or a `BarrelBlockEntity` right now, in a loaded chunk.
- **Building chests are not stockpile.** A position that is also in the latest scan of **any other registered room building**
  (House, Farmhouse, Lumber Camp, …, valid or not) is excluded, even if a Storage scan lists it too (a chest in a wall shared by
  a Storage and a Lumber Camp is the camp's tool chest; a chest in a wall shared with a House is "a chest in a House"). Shared
  by two Storages → counted once, owned by the first Storage in site order. **After a restart** (scans refill over `n` s), a
  Storage is treated as *unknown* while any registered non-Storage room building in the same level whose marker is within
  `Balance.STOCKPILE_NEIGHBOUR_RANGE` (32) blocks of the Storage marker has no cached scan yet, so a House chest in a shared wall
  can never leak into the stockpile in that window. Only positions in the claim's level are considered (`Pos` has no dimension).
- **A double chest is two containers** (each half has its own 27 slots in its own `ChestBlockEntity`). The stockpile reads and
  writes each half's block entity directly and **never** the combined `ChestBlock.getContainer(...)` container, so nothing is
  counted twice, and a half outside the room is simply not part of the stockpile.
- **Item identity respects components.** Two stacks are the same stockpile item iff `ItemStack.isSameItemSameComponents` (same
  item and equal component maps). A renamed paper, an enchanted book or a damaged sword is a different item from the plain one.
  Totals are kept per variant; "by item id" totals (metrics, simple counts) sum the variants.
- **Site order** (deterministic everywhere): Storage sites sorted by marker `Pos`; containers in a site sorted by `Pos`; slots by
  index.
- **Anchor** of a site = its scan's `door()` (where a worker walks to), else the marker.
- **Nearest Storage with space** for item `k` from position `p`: the site with space for ≥1 `k` that minimises the squared
  Euclidean distance from `p` to its anchor; ties → site order. "Space for `k`" = some slot holds `k` below its limit, or some
  slot is empty and accepts `k`.
- **Deposit** of `n` × `k` from `p`: sort the sites **once** by distance (ties → site order) and walk them in that order,
  skipping sites without space; fill each (first every partial stack of `k` in its containers, in container/slot order; then
  empty slots in the same order); stop when `n` is stored or the list ends. (Filling one site never changes another's space, so
  this equals "repeatedly take the nearest site with space" at O(sites log sites + slots).) Returns
  the amount stored; the caller keeps the rest (the worker keeps it in its inventory, DESIGN §6). A slot's limit is
  `min(container.getMaxStackSize(), item max stack size)` (Container default 99 **[verified]**, so a chest holds 64 cobblestone,
  16 eggs, 1 sword per slot). An over-full slot (count above its limit, from commands) has 0 space and is never shrunk.
- **Withdraw** of up to `n` × `k` from `p`: sites by distance from `p` (ties → site order), or site order when no `p`; inside a site,
  containers and slots in order; take until `n`. Returns the amount taken. Reservations held by others are respected (3.2.4).
- **Storage full** (alert): see 3.2.5.

### 3.2 Core (pure, package `dev.villageheart.core.stock`)

#### 3.2.1 Inventory abstraction

```java
/** One container's slots. K is the item identity (equals/hashCode = same item for stacking). */
public interface Inventory<K> {
    int size();
    @Nullable K key(int slot);              // null = empty slot
    int count(int slot);                    // 0 when empty
    int limit(int slot, K key);             // max count of key in this slot; 0 = the slot refuses key
    void add(int slot, K key, int n);       // slot empty or holding key; n > 0; count + n <= limit (else IllegalStateException)
    void remove(int slot, int n);           // 0 < n <= count; slot becomes empty at 0
    void changed();                         // called once per touched inventory at the end of an operation
}
public record ContainerRef<K>(Pos pos, Inventory<K> inventory) {}
public record StorageSite<K>(Pos marker, Pos anchor, List<ContainerRef<K>> containers) {}   // containers sorted by pos (constructor sorts + List.copyOf)
```

#### 3.2.2 Choosing the containers (`StorageSet`, positions only)

```java
public record SiteCandidate(Pos marker, Pos anchor, List<Pos> containers) {}       // from one valid Storage scan (#chest ∪ minecraft:barrel)
public record Resolved(List<SiteCandidate> sites, List<Pos> unknownMarkers) {}
public static Resolved resolve(List<SiteCandidate> storages, Set<Pos> claimedByOtherBuildings,
                               List<Pos> otherMarkersWithoutScan, int neighbourRange);
```
Sorts sites by marker, moves a Storage to `unknownMarkers` when an entry of `otherMarkersWithoutScan` is within
`neighbourRange` (Euclidean) of its marker, drops excluded positions, de-duplicates positions within a site and across sites
(first site in order keeps it), and sorts each container list. A site may end with no containers; the glue then counts it as
unknown (3.2.5). Pure, so the shared-wall, House and restart rules are proven in L1.

#### 3.2.3 `Stockpile<K>` (replaces `core.Stockpile`)

The old string counter is deleted; `StockpileTest` is rewritten over `FakeInventory` and keeps its three cases (deposit then
withdraw, cannot withdraw more than stored, negative amount rejected): the semantics move, nothing is weakened. A
`Stockpile<K>` is a **view** over live inventories: it holds no counts of its own, so it can never drift from the chests.

```java
public final class Stockpile<K> {
    public Stockpile(List<StorageSite<K>> sites, Reservations<K> reservations);   // the constructor sorts sites by marker (any input order)
    public List<StorageSite<K>> sites();

    public long count(K key);                                  // sum over all slots
    public long count(Predicate<? super K> match);
    public long available(K key, @Nullable UUID holder);      // max(0, count - reserved by others than holder)
    public boolean hasSpaceFor(K key);
    public Optional<StorageSite<K>> nearestWithSpace(Pos from, K key);

    /** Stores up to n (n >= 0), nearest site first, spilling. Returns how many were stored. */
    public int deposit(Pos from, K key, int n);
    /** Same, into one site only (a worker standing at that Storage). */
    public int depositInto(StorageSite<K> site, K key, int n);
    /** Takes up to n (n >= 0), nearest first; never takes what others reserved. Returns how many were taken. */
    public int withdraw(@Nullable Pos from, K key, int n, @Nullable UUID holder);
    /** Takes up to n of the first matching key found in the withdraw order; returns (key, taken) or empty. */
    public Optional<Taken<K>> withdrawFirst(@Nullable Pos from, Predicate<? super K> match, int n, @Nullable UUID holder);

    /** unknownSites / unreadContainers come from the glue (only it knows about missing scans and unloaded chunks). */
    public StockSnapshot<K> snapshot(long gameTime, int unknownSites, int unreadContainers, StorageAlert alert);
    public record Taken<K>(K key, int count) {}
}
```
Rules: `n < 0` → `IllegalArgumentException`; `n == 0` → 0 with no `changed()` call. Every operation is all-or-what-fits: the
return value is exactly what moved (conservation is tested). `deposit` does not touch slots of other keys. `withdraw` with a
holder consumes up to that holder's reservation of `key` first (`reservations.consume(holder, key, taken)`).

#### 3.2.4 Reservations (hook for M20, also used by M22's "surplus")

```java
public final class Reservations<K> {                   // holder = a UUID (a worker's entity UUID or a build id), never an entity
    public void set(UUID holder, K key, int n);        // n >= 0; 0 removes (a builder reserves its blueprint's material list)
    public void release(UUID holder);                  // all of a holder's reservations (build finished or cancelled)
    public int reserved(K key);                        // sum over holders
    public int reservedBy(UUID holder, K key);
    void consume(UUID holder, K key, int n);            // package-private, called by Stockpile.withdraw
}
```
A reservation is a **claim, not a lock**: items stay in the chests and players can still take them out; `available` is
clamped at 0. A reservation can exceed the stock (M20: "reserve what you need, show what is missing"). M6 keeps the reservations
in the transient runtime (not saved); M20 decides whether build reservations are persisted (it can restore them from its own
saved build state at load). No in-world caller in M6.

#### 3.2.5 Snapshot and alert

```java
public record StockSnapshot<K>(
    long gameTime,
    List<Total<K>> totals,      // one per variant, count > 0; sorted by count desc, then first-seen order (site, container, slot)
    int sites,                  // valid Storage buildings with >= 1 container read this time
    int unknownSites,           // valid Storage whose contents are unknown: no cached scan, a neighbour unscanned (3.1),
                                // or not one container readable (chunk unloaded, all chests excluded or gone)
    int containers,             // stockpile containers read this time
    int unreadContainers,       // listed but skipped: chunk not loaded, or no chest/barrel there any more
    int slots, int freeSlots,   // over the containers read
    StorageAlert alert) {
    public record Total<K>(K key, long count) {}
    public long count(K key);
    public <I> Map<I, Long> totalsBy(Function<? super K, I> id);   // e.g. by item id; TreeMap (sorted)
}
public enum StorageAlert { OK, FULL, NO_STORAGE }
public final class StorageAlertTracker {
    public void noteDepositShort(long gameTime);           // a deposit returned less than asked
    public StorageAlert refresh(StockSnapshot<?> s, long gameTime);   // computes and remembers the state
    public StorageAlert state();  public long since();     // game time the current state began (rising edge)
}
```
- `NO_STORAGE` when `sites + unknownSites == 0` (no valid Storage at all).
- `FULL` when `containers > 0` and (`freeSlots == 0`, or a spilling deposit came up short within the last
  `Balance.STORAGE_FULL_HOLD_TICKS` (200) ticks). The hold stops a single short deposit from flashing FULL→OK within a second.
  With `containers == 0` but some unknown sites (after a restart, or the player walked away and the Storage chunk unloaded while
  the Heart chunk still ticks), the previous state is kept: no false "full", no false "ok".
- `OK` otherwise. `since` changes only when the state changes.
- Only the spilling `Stockpiles.deposit` calls `noteDepositShort`, and only when it stored less than asked (it has then tried
  every site, so nothing anywhere had space for that item). `depositHere` (one Storage) never does: one full Storage is not a full
  village.
- `FULL` is "no empty slot anywhere", not per item: a partial cobblestone stack can still take cobblestone while FULL shows.
  Workers decide with `hasSpaceFor(key)` (M7+ "stop gathering" check), the alert is for the player.

`Balance` gains `STOCKPILE_REFRESH_TICKS = 20` (how often the system refreshes the alert), `STORAGE_FULL_HOLD_TICKS = 200`
and `STOCKPILE_NEIGHBOUR_RANGE = 32` (all tunable).

### 3.3 Minecraft glue (package `dev.villageheart.stock`)

#### 3.3.1 `StackKey` (the K of the glue)

```java
public final class StackKey {
    public static @Nullable StackKey of(ItemStack s);     // null for s.isEmpty(); new StackKey(s.getItem(), s.getComponentsPatch())
    public Item item();  public DataComponentPatch patch();
    public ItemStack toStack(int n);                      // new ItemStack(item.builtInRegistryHolder(), n, patch)
    public int maxStackSize();                            // lazily cached toStack(1).getMaxStackSize()
    public String id();                                   // BuiltInRegistries.ITEM.getKey(item).toString(), e.g. "minecraft:paper"
    public boolean is(TagKey<Item> tag);                  // item.builtInRegistryHolder().is(tag)
    equals: item == other.item && patch.equals(other.patch);  hashCode: cached, 31 * item.hashCode() + patch.hashCode()
}
```
Why this equals `isSameItemSameComponents` exactly: that method compares `item` and then the `PatchedDataComponentMap`s, whose
`equals` is `prototype.equals && patch.equals` **[verified `ItemStack:646`, `PatchedDataComponentMap:222`]**; the prototype is
the item's own default map, so for one item it reduces to patch equality. The patch is normalised on write (setting a component
to its default value removes it from the patch) **[verified `PatchedDataComponentMap.set/applyPatch`]**, so equal stacks have
equal patches. `ItemStack.getComponentsPatch()` returns `DataComponentPatch.EMPTY` for plain stacks and otherwise wraps the patch
copy-on-write, so building a key per slot is cheap and later edits of the live stack never change a key **[verified
`ItemStack:245`, `PatchedDataComponentMap.asPatch:203`]**. `new ItemStack(Holder<Item>, int, DataComponentPatch)` **[verified
`ItemStack:265`]**, `Item.builtInRegistryHolder()` **[verified]**. L1 cannot load `Item`s, so `StackKey`'s equivalence with
`isSameItemSameComponents` is proven in L2 (T-L2-5).

#### 3.3.2 `ContainerInventory implements Inventory<StackKey>`

Wraps one `Container` (a single chest half or a barrel):
- `size()` = `getContainerSize()` (27 for chest and barrel **[verified]**); `key/count` from `getItem(slot)`.
- `limit(slot, k)` = `canPlaceItem(slot, s) ? container.getMaxStackSize(s) : 0` with `s = k.toStack(1)` cached in the key
  (`Container.getMaxStackSize(ItemStack)` = `min(getMaxStackSize(), stack.getMaxStackSize())` **[verified]**).
- `add`: empty slot → `setItem(slot, k.toStack(n))`; else `getItem(slot).grow(n)`. `remove`: `getItem(slot).shrink(n)`, and
  `setItem(slot, ItemStack.EMPTY)` at 0. `changed()` → `container.setChanged()` (marks the chunk unsaved and updates comparators:
  `BlockEntity.setChanged` → `level.updateNeighbourForOutputSignal` **[verified `BlockEntity:205`]**).
- Never `removeItemNoUpdate`/`clearContent`. Loot-table chests: `RandomizableContainerBlockEntity.getItem` unpacks a pending loot
  table first (with a null player, as a hopper does) **[verified `RandomizableContainerBlockEntity:54`]**; accepted (a structure
  chest walled into a Storage gets its loot rolled when first read).

#### 3.3.3 Finding the containers (`StorageContainers.at`)

```java
static @Nullable Container at(ServerLevel level, BlockPos pos) {
    LevelChunk c = level.getChunkSource().getChunkNow(pos.getX() >> 4, pos.getZ() >> 4);  // null if not loaded; never loads
    if (c == null) return null;
    BlockEntity be = c.getBlockEntity(pos);                     // LevelChunk.getBlockEntity(BlockPos) = CHECK: no creation
    return (be instanceof ChestBlockEntity || be instanceof BarrelBlockEntity) && !be.isRemoved() ? (Container) be : null;
}
```
**Not** `level.getBlockEntity(pos)`: on the server thread it calls `getChunkAt(pos)`, which **loads the chunk synchronously**
**[verified `Level:591-598`]**. `ServerChunkCache.getChunkNow` returns null off-thread and never loads **[verified, M4]**.
`ChestBlockEntity` is the block entity of chest and all 8 copper chests (`BlockEntityType.CHEST` lists them) and
`TrappedChestBlockEntity extends ChestBlockEntity` **[verified]**. An ender chest, shulker box, hopper or furnace at a listed
position is skipped. A `#chest` position with a non-chest now (scan up to `n` s old) is skipped and counted in
`unreadContainers`.

#### 3.3.4 Sites (`StorageSites.collect`) and the facade (`Stockpiles`)

```java
// StorageSites: per call, from M5's views; ~O(buildings + containers). Only views whose level() is the claim's level.
static Collected collect(MinecraftServer server) {
    level    = the claim's ServerLevel (VillageState.heart().dimension())
    storages = Buildings.valid(server, STORAGE) in level
    others   = Buildings.all(server) in level, kind ROOM, type != STORAGE
    excluded = union of others' latestScan positions("#chest") ∪ positions("minecraft:barrel")
    otherMarkersWithoutScan = others with an empty latestScan → marker Pos
    candidates = storages with latestScan → SiteCandidate(marker, scan.door() ?: marker, #chest ∪ minecraft:barrel)
    resolved = StorageSet.resolve(candidates, excluded, otherMarkersWithoutScan, STOCKPILE_NEIGHBOUR_RANGE)
    return ContainerBinder.bind(level, resolved.sites())  +  unknown = storages without scan + resolved.unknownMarkers
}
// ContainerBinder.bind(level, List<SiteCandidate>) → (List<StorageSite<StackKey>> sites, int unreadContainers, int emptySites):
// each Pos via StorageContainers.at; null → unreadContainers++; a site with no bound container is dropped and counted as
// unknown. Shared by StorageSites.collect and the test factory StockpileTestSupport.siteOf, so step-4 tests exercise it.
```
The facade every later milestone uses (all methods **server thread only**; each starts with `requireServerThread(server)`,
`IllegalStateException` otherwise, like M4's `RoomScans.scan`):

```java
public final class Stockpiles {
    public static StockSnapshot<StackKey> snapshot(MinecraftServer s);             // computed fresh on every call (no memo)
    public static long count(MinecraftServer s, Item item);                        // all variants
    public static long count(MinecraftServer s, TagKey<Item> tag);
    public static long count(MinecraftServer s, StackKey key);
    public static Map<String, Long> totalsById(MinecraftServer s);                 // M2 metrics; sorted
    public static boolean hasSpaceFor(ServerLevel level, ItemStack stack);         // M7+: "stop gathering" check
    public static Optional<BlockPos> nearestWithSpace(ServerLevel level, BlockPos from, ItemStack stack);  // the anchor to walk to
    /** Moves as much of stack as fits (nearest first, spilling); shrinks stack by that amount; returns it. */
    public static int deposit(ServerLevel level, BlockPos from, ItemStack stack);
    /** Same, into the Storage whose anchor is nearest to from only. */
    public static int depositHere(ServerLevel level, BlockPos from, ItemStack stack);
    /** Up to max (capped at one stack) of key; EMPTY when none. */
    public static ItemStack withdraw(ServerLevel level, @Nullable BlockPos from, StackKey key, int max, @Nullable UUID holder);
    public static ItemStack withdrawFirst(ServerLevel level, @Nullable BlockPos from, Predicate<StackKey> match, int max, @Nullable UUID holder);
    public static Reservations<StackKey> reservations(MinecraftServer s);
    public static StorageAlert alert(MinecraftServer s);   public static long alertSince(MinecraftServer s);
}
```
- Every call builds a fresh `Stockpile<StackKey>` over `StorageSites.collect` (a few tens of µs, 3.4). A deposit/withdraw whose
  `level` is not the claim's level does nothing (returns 0 / EMPTY). There is **no snapshot memo**: a memo would serve stale totals
  after a same-tick `setItem` by a player, hopper or test, and a game-time key would never expire under `/tick freeze`.
- Only `deposit` (spilling) calls `tracker.noteDepositShort(gameTime)` when it stored less than asked (3.2.5).
- `StockpileRuntime` (transient, one per server, dropped on `SERVER_STOPPED` and when the claim changes, like M5's runtime):
  the `Reservations` and the `StorageAlertTracker`.
- `StockpileSystem implements VillageSystem`, registered as `"villageheart:stockpile"` after M5's building system: every
  `STOCKPILE_REFRESH_TICKS` → `tracker.refresh(snapshot(server), gameTime)`. Registered via `VillageSystems.register`, so its
  cost is inside `village_ms`.
- **Thread safety:** everything runs on the server thread (worker ticks, block events, systems, the sim collector). Off-thread
  calls are refused, not silently empty. No state is shared with the client. Live containers are never cached, so a player
  editing a chest is seen by the very next call, and a chest a player has open receives deposits normally (the open
  `ChestMenu` reads the same container and syncs the slots).
- No saved data, no networking, no assets, no commands, no lang keys in M6 (the alert has no text until M8).

### 3.4 Performance budget

- **Cost model.** One snapshot = one `getItem` + one `StackKey` + one hash-map merge per slot (27 per container). Plain stacks
  allocate only the key record (`getComponentsPatch()` returns the `EMPTY` constant). A big village (4 Storages × 8 chests = 864
  slots) is a few tens of µs; refreshed every 20 ticks that is < 0.005 ms/tick on average.
- **Budget (written into TESTING.md):** one snapshot (= one `StockpileSystem` refresh) of 32 full containers (864 slots, 32
  variants) **< 1 ms**, i.e. **< 0.05 ms per tick** averaged over the 20-tick refresh; a deposit or withdraw **< 0.3 ms** for 32
  containers.
- **Proof:** L1 `StockpilePerfTest` (64 sites × 8 containers × 27 slots = 13 824 slots, 90 % full, 300 keys): snapshot median
  < 3 ms; a worst-case deposit into full storage (scans everything, stores 0) median < 1 ms; a deposit of 64 × 27 × 8 × 64 items
  into empty storage that **spills across all 64 sites** median < 3 ms (catches a quadratic "re-find the nearest" loop). The grid
  is built outside the timed region, 30 warm-ups, 30 timed calls, the failure message prints all timings, results are asserted
  so an early exit cannot pass. L2 `snapshotCostReal` (T-L2-9) times the real glue at 32 chests **and** the `StockpileSystem`
  tick itself. L3 sees it inside `village_ms` once scenarios have Storage (M11).
- **Bounded work.** No per-tick scanning beyond the 1 Hz refresh; deposits/withdraws are bounded by the slot count and stop as
  soon as the amount is met.

## 6. Risks and unknowns

| # | Risk | Mitigation |
|---|---|---|
| 1 | **Top risk: M6 sees chests only through M5's cached scans.** A chest added to or removed from a Storage is seen up to `n × 1 s` later; right after a restart Storages are "unknown" until rescanned, and the interfaces are taken from a plan, not code | Live reads skip stale positions safely (T-L2-7, T-L2-10); unknown sites keep the previous alert (T-L1-17) and appear in `unknownSites` so M8 can say "checking storage…"; step 5 re-checks A2-A7 against merged code; all core and step-4 glue are independent of M5 |
