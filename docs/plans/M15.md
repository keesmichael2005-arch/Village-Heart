# M15 plan: job levels and tools

Status: plan (planner, 2026-11-07). Branch `m15-plan`. Builder: read section 3.1 (assumptions) **before step 1**, and the decision in
section 3.8 (D1) before step 7.

## 1. Goal

Workers get better with practice. Every unit of work (a log felled, a crop harvested, an item cooked...) earns XP; at 100 and 300 XP a
worker reaches level 2 and 3 and works ×1.25 / ×1.5 faster, but never above the tier's cap (Hamlet 1, Village 2, Town 3; XP beyond
the cap is banked and turns into levels when the village grows). A level-up is visible: happy-villager particles, a celebrate sound, a
chat line to village members, the vanilla level badge on the villager's belt (stone, iron, gold), and the Heart screen bar. Tools
(tier multipliers, wear) already work since M9; M15 proves the difference side by side: an iron-axe lumberjack out-fells a stone-axe one.

### 3.2 Core (pure, `dev.villageheart.core.job`, L1-tested)

```java
/** What a job counts as one unit of work. XP per unit is Balance.XP_PER_UNIT[ordinal] (tunable, M26). */
public enum WorkUnit {
    LOG_FELLED,      // lumberjack, 1 per log (M9 counter work.lumberjack.logs)
    CROP_HARVESTED,  // farmer, 1 per mature crop block harvested (M10)
    ITEM_COOKED,     // cook, 1 per output item (M13)
    ITEM_MINED,      // miner, 1 per item in a haul (M16)
    GAME_HUNTED,     // hunter, per trip (M17)
    HOSTILE_KILLED,  // guard, per kill in the claim (M18; M18 picks KILL_XP, default here 5)
    SPAR,            // guard, 1 per sparring WorkClock unit (M18)
    ITEM_SMITHED,    // blacksmith, per ingot / item / repair (M19)
    BLOCK_PLACED,    // builder, 0.2 per block (500 blocks a day at 1 block/s) (M20)
    TRADE_MADE;      // merchant (M22)
}

public record Progress(int level, int xp) { /* level 1..3, xp 0..Balance.MAX_BANKED_XP */ }

public record XpChange(Progress before, Progress after, boolean levelledUp, boolean reachedCap) {}
//   reachedCap: xp crossed the next threshold during this gain but the tier held the level (the "capped" chat line, once per threshold)

public final class Leveling {
    /** before + amount (amount >= 0; negative throws), xp clamped to MAX_BANKED_XP, level = max(before.level, TierRules.levelFor(xp, tier)). */
    public static XpChange gain(Progress before, int amount, Tier tier);
    /** Level the pass should hold now: max(level, TierRules.levelFor(xp, tier)). Never lower (A3). */
    public static int levelNow(Progress p, Tier tier);
    /** True when the worker has the XP for the next level but the tier caps it (the Heart bar turns gold). */
    public static boolean capped(Progress p, Tier tier);
    /** The tier needed for the next level, for the capped notice ("needs a Village" / "needs a Town"); empty at level 3. */
    public static Optional<Tier> tierForNext(Progress p);
    /** Clamps stored values from a save: level to 1..3, xp to 0..MAX_BANKED_XP. */
    public static Progress sanitize(int level, int xp);
}

/** Fractional XP per worker (BLOCK_PLACED is 0.2). Keyed by villager UUID; not saved (at most < 1 XP lost on a restart). */
public final class XpAccumulator {
    public int add(UUID worker, WorkUnit unit, int units);  // whole XP to award now; the remainder carries
    public void forget(UUID worker);
}
```

`Balance` (new block "levels (M15)"): `MILLI_XP_PER_UNIT = {1000, 1000, 1000, 1000, 5000, 5000, 1000, 2000, 200, 2000}` (**integers**, thousandths of an XP,
indexed by `WorkUnit.ordinal()`, exposed through `milliXpPerUnit(WorkUnit)` only; `XpAccumulator` sums `long` milli-XP, so 0.2 never drifts to 0.999...), `MAX_BANKED_XP = LEVEL_3_XP` (300: XP beyond level 3 has no use, and the cap keeps the
Heart bar meaningful). Expected pace at level 1 (DESIGN numbers): lumberjack 70-100 logs per day → level 2 after about 1-1.5 days,
level 3 after 3-4 days; farmer about 60-80 crops; cook about 80 items; builder 100 XP a day. M26 tunes these. The comment on
`LEVEL_2_XP`/`LEVEL_3_XP` ("display only until M15") is updated.

Why XP is banked up to 300 at a capped tier: DESIGN §4 sets caps per tier and M14's plan expects banked XP to turn into a level on the
tier-up ("300 XP at Hamlet stays level 1 and becomes 2 after the tier-up"). A worker at Hamlet with 300 XP becomes level 2 at Village
and level 3 at Town immediately, which rewards the work done while small.

### 3.3 Glue (`dev.villageheart.worker`, `worker.job`)

1. **One XP API.** `Workers.addXp(Villager villager, int amount) : Optional<XpChange>` (server thread; empty for a non-worker or with
   no village). Reads the attachment and `VillageClaims.current(server).tier()`, calls `Leveling.gain`, writes the new
   `WorkerData` with `setAttached` (record copy with the new level/xp), and when the level changed calls `Workers.setLevel` (A2: record
   mirror), `syncBadge` and `WorkerLevels.fire(...)`. `amount == 0` is a no-op (no write).
   `worker.job.WorkXp.award(Villager v, WorkUnit unit, int units)` is what jobs call: `XpAccumulator` → `Workers.addXp`. One static
   `XpAccumulator` (server thread only; `forget` on fire/death, next to M9's `LumberJob.forget`; cleared on server stop).
2. **Level-change listeners.** `WorkerLevels.register(LevelListener)` with `onLevelChanged(ServerLevel, Villager, XpChange)` and
   `onCapped(ServerLevel, Villager, XpChange)`. M15 registers `LevelUpFeedback` (3.4); M18 registers its perks. Listeners run after the
   attachment and record are written.
3. **The level pass** (in `WorkerSystem.tick`, every 20 ticks, next to the profession repair, inside the existing section): for each
   loaded worker with an attachment, `n = Leveling.levelNow(progress, tier)`; when `n > level`, write it the same way as 1 (this is how
   a tier-up, `setTier` in tests, and banked XP of a worker that was unloaded during the tier-up become levels); fires the listeners
   with `levelledUp = true`. A level **above** the tier cap (only by direct writes: M12/M18 tests, or a future admin command; the
   tier never goes down) is kept and `WorkSpeed` uses it as is: "the cap holds" is about earned levels. Documented in DESIGN §4. Also: `VillagerData.level != data.level` → `syncBadge`. Cost: one attachment read and one compare per
   loaded worker per second (no allocation when nothing changes).
   The re-install branch (registered villager with no attachment) uses `WorkerRecord.level` (A2) instead of 1, xp =
   the total XP of that level (`levelFromXp` agrees), so a lost attachment does not cost levels already paid for in wages.
4. **Badge.** `Workers.install` sets `withLevel(data.level())` instead of 1 (the vanilla profession-level texture: 1 stone, 2 iron,
   3 gold; `VillagerProfessionLayer` draws `profession_level` from `VillagerData.level()` for any profession other than NONE
   **[verified in the 1.21.11 client jar: `LEVEL_LOCATIONS` stone/iron/gold/emerald/diamond, reads `VillagerData.level()`]**;
   `VillagerData.withLevel(int)` **[verified]**). `restoreVanilla` keeps level 1. `setVillagerXp` stays 0 (vanilla trading XP is not
   ours; workers do not trade). A higher vanilla level has no side effect without `increaseMerchantCareer` (private, only called from
   the trade XP path) **[verified: called only from `customServerAiStep` and `rewardTradeXp` paths]**. Builder checks (step 2,
   section 8): (a) vanilla's profession reset (`ResetProfession`, skips level > 1) is not in the worker brain, and `restoreVanilla`
   resets level 1 before the vanilla brain returns; (b) a zombie conversion + cure keeps `VillagerData` (mod profession, level badge)
   without our attachment: the load/orphan handling must treat "mod profession, no attachment, no record" as an orphan and
   `restoreVanilla` it (add it if M7 does not; T-L2-11); (c) workers still cannot open trading (no `getOffers()` call generates
   level-2 trades).
5. **Codec leniency.** `WorkerCodecs` decodes through `Leveling.sanitize` (level 0 or 7, xp -5 or 10 000 in a save → clamped, logged once
   per decode site (a codec has no entity context); never a decode error that would drop the worker attachment).
6. **Fire / rehire.** Firing removes the attachment (M7), so XP and level are gone; a rehire starts at level 1, 0 XP (DESIGN: firing
   makes them unemployed; nothing says experience is kept). Documented in DESIGN §4.
7. **Unloaded workers** earn nothing (they do not work). Their record keeps the last level (wages, A2).
8. BACKLOG M7 "Workers.levelOf/TRIPS use inline fully qualified names (cosmetic)": fixed in passing (M15 edits `Workers` anyway).

### 3.8 The side-by-side test and decision D1 (needs the orchestrator / user)

**The roadmap number cannot be met with DESIGN's numbers.** The tool multiplier scales only the cutting time: iron 1.5 / stone 1.25 =
**1.2 is the ceiling** of the log ratio, reached only if the worker never walks. With walking overhead `w` ticks per log, logs per window
are `T / (w + 50/m)`, so iron/stone = `(w + 40) / (w + 33.3)`. Even with no overhead this is 1.2 < 1.3. A stone axe would have to break
mid-day (131 uses) to reach 1.3, which a lumberjack does not reach in a day (`LUMBER_LAST_FELL` 5000: about 4 000 felling ticks, at most
100 logs). Raising iron's multiplier to ≥ 1.9 would change DESIGN.

Options (the builder must not pick one silently; DoD 4):
- **(A, recommended)** Keep DESIGN's multipliers and the stone-vs-iron comparison; the roadmap line becomes "an iron-axe lumberjack
  fells ≥1.1× the logs of a stone-axe one, and ≥1.3× those of a wooden-axe one, over the felling part of one work day (side by side)".
  Expected with big trees (~20 logs, ~150 ticks overhead per tree): iron/stone ≈ 1.16, iron/wood ≈ 1.4. One test, three lumberjacks.
- (B) Compare iron with wood only at ≥1.3 (theoretical 1.5).
- (C) Raise `TOOL_SPEED[IRON]`: >= 1.625 with no walking, about 1.72 at 7.5 ticks overhead per log (about diamond's 1.75), 1.9 for a
  margin (DESIGN change, unbalances M16/M19).

Levels cannot rescue the number: at HAMLET all three are capped at level 1, and starting the iron worker with XP would rig the test.

The test below is written for (A); (B) is the same test with the stone level removed. If no answer comes before step 7, build (A),
keep the roadmap text unchanged, and mark the roadmap line "blocked on D1" in PROGRESS: the orchestrator decides.

**Layout (deterministic as far as villager walking allows).** Three identical scenes stacked vertically so that the three groves are
disjoint for the tree search and identical for walking (horizontal copies would overlap neighbouring test structures; a 32 xz search
radius needs ~70 blocks between camps):
- Level 0 = the normal yard scene (`LumberTestSupport.scene(h, false, true)`: Lumber Camp + Storage, grass at y -1, torches).
- Levels 1 and 2 = the same scene translated by `Δ = (0, 30, 0)` and `(0, 60, 0)`: a **glass** platform (one layer at y 29 / 59, the
  yard's 32×32 footprint, so sky light reaches every level; grass + dirt only in patches under each tree base and where the scene needs
  grass) with a 2-high glass rim, the camp room, Storage room, markers, chest and torches built with the same helpers at translated
  positions. Room scans are unaffected (the rooms have their own roofs; the sky check matters only for roof holes). Separation: B's
  lowest log is 30 above A's Chopping Block (> `LUMBER_DY` 16); A's dark-oak tops (≤ ~10) are ≥ 20 below B's block. **Every log of all
  three groves**, the three Chopping Blocks and the three Storages are asserted `ClaimGeometry.inClaim` at setup (radius 80: the top
  grove's crowns are ~70 up and ≤ 25 across from the Heart).
- Tiers on the levels: **iron on level 0** (the ground yard, under two glass floors: the worst light, so any bias works against the
  expected result), stone on level 1, wood on level 2.
- Time: `WorkerTestSupport.begin` turns time on (M7: the day advances; the test asserts it advanced); the environment is the test's own
  (`levels_side_by_side`), so no other test shares the server-wide day time.
- The test clears the two platform volumes and discards every villager in them first (a failed or timed-out earlier run may have left
  them) and again in its last step; the hired villagers are `WorkerTestSupport.track`ed so `VillageTestSupport.reset` discards them on
  the next run even after a timeout (the GameTest cleanup only covers the structure); `sweepStrayTrees` is extended to those boxes. TESTING.md gets an exception to "keep trees inside the yard".
- Each grove: the same list of `(feature, base, seed)`: 6-8 `TreeFeatures.DARK_OAK` with **≥ 20 logs each** (asserted per tree at setup;
  pick seeds that give it) in the strip z 14-30, so that each grove holds ≥ 160 logs (more than iron can fell in the window). The setup asserts the three
  log sets are exact translations of each other (same seed; fails loudly if the feature is position-dependent).
- Axes: 2 per camp chest of that camp's tier (wood ×2, stone ×2, iron ×2): a wooden axe (59 uses) may break during the window and the
  second one takes over (this also tests the break → next tool path).
- Hire three adult villagers at the translated spawn spots in the same tick, each with `preferredBuilding` = its own camp (assert each
  record's building). Tier HAMLET (default), wages off (A2), day time 1000.
- **Measurement**: a per-tick sampler (registered from the test body, gated) counts, per grove, log removals with `dayTime` in
  `[1000, LUMBER_LAST_FELL)`; attribution checked through `LumberRuntime.claims()` (every felled tree of grove k was claimed by worker k,
  as in M9's `twoLumberjacksOneCamp`; the owner is recorded when the **first** log of a tree goes, because the claim is gone once the
  tree is done). Every 100 ticks the sampler also reads each camp's axe wear (damage summed over the chest, + `maxDamage` per vanished
  axe): it must equal that worker's logs felled so far (± 1, a cut in the sampled tick) at **every** sample, so late or bulk wear fails.
  Per worker it logs `w` = (window ticks − logs × ticks-per-log) / logs. The window ends at day tick 5000; the test then finishes
  (maxTicks 6 000). GameTests are not paced (M9 risk 5), so this is CPU time, not 5 minutes; the test has its own environment (its own
  batch) and can be run alone with the exact filter id.

## 6. Risks and unknowns

1. **Top risk: D1.** The roadmap's "≥1.3× a stone axe" is mathematically out of reach with DESIGN's 1.25/1.5 multipliers (ceiling 1.2).
   The test and the roadmap line need the orchestrator's decision; the builder must not weaken it quietly.
2. **Side-by-side layout.** Rooms, markers and Storages built outside the structure box (platforms at +36/+72): the claim sphere, room
   scans with sky access, `nearestWithSpace` choosing each level's own Storage (3D distance assumed; assert per-level Storage counts
   rise), and cleanup of the platforms. Fallback if the stacked layout fights the framework: the same yard three times in a row (one
   worker, the grove regrown from the same seeds each morning, a different axe each day). That compares sequentially, not side by side,
   and is recorded as a deviation.
3. **Walking noise** makes the ratio vary; measured over 5 runs (5.2).
4. **Order of merges.** M12/M14/M18 plans assume different owners for the level rule; A1/A2/A6 pin who adds what. If M18 is built
   before M15, M15 adopts M18's code (A6).
5. **Vanilla level badge** on a mod profession: verified that the layer reads `VillagerData.level()` for any non-NONE profession;
   the L4 shot confirms. A vanilla level > 1 has no trade side effects (no offers are generated).
6. **Feedback cannot be observed server-side** (particles, sound): covered by the sink seam and the L4 look; the chat is asserted.
7. **Attachment writes** per log (record copy + `setAttached`): ~100 per worker per day, negligible; the record mirror is written only
   on a level change (rare), so `VillageSavedData` is not marked dirty per log.

**Out of scope**: XP for jobs not merged yet (their milestones call the API; ROADMAP notes), guard perks (M18), tool repair (M19), a
held-tool visual (M9 out of scope), losing levels (never in v1), XP for walking/replanting/deposits, balancing XP rates (M26), a
level-up advancement, the Training Yard.
