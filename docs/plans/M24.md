## 1. Goal

Several players run the one village together. The Owner opens a new **Ranks** tab on the Heart screen, sees every known
player (online or offline) with their rank, makes them Steward, Resident or Visitor, and can hand the whole village to a
Steward or Resident after a confirmation. Ranks apply at once to every Heart action, and Visitors can no longer open or
break the chests and other containers inside the village's claimed buildings (Residents and above can). An op command lets a
server admin give an abandoned village to someone else.

### 3.2 Permissions: a minimum rank per permission (core)

DESIGN §2's table is cumulative (each rank can do everything the ranks below it can), so each permission has one minimum rank.

```java
public enum Rank { OWNER, STEWARD, RESIDENT, VISITOR;           // unchanged order (codecs use names; HeartCodecs the ordinal)
    public boolean atLeast(Rank min) { return ordinal() <= min.ordinal(); } }

public enum Permission {                                         // append only (M12 appends too; keep M12's two in its order)
    VIEW_OVERVIEW(VISITOR), VIEW_DETAILS(RESIDENT), HIRE(STEWARD), FIRE(STEWARD), RECHECK_BUILDING(STEWARD),
    SET_GUARD_SHIFT(STEWARD) /* M18 */, DEPOSIT_TREASURY(RESIDENT) /* M12 */, WITHDRAW_TREASURY(OWNER) /* M12 */,
    OPEN_CONTAINERS(RESIDENT), MANAGE_RANKS(OWNER), TRANSFER_OWNERSHIP(OWNER), BREAK_HEART(OWNER),
    START_BLUEPRINT(STEWARD) /* M20 */;
    private final Rank minimum; ... public Rank minimum() }

Permissions.allows(rank, p) = rank.atLeast(p.minimum())
```

- The compiler forces every new permission to name its minimum rank (no forgotten `switch` arm).
- `WorldClaim.mayBreakHeart` keeps its `BreakDecision` result but decides through `Permissions.allows(village.rankOf(player),
  BREAK_HEART)`, so the Heart's break rule is part of the same matrix. `core.WorldClaim` → `core.heart.Permissions` is a core-to-core
  import (allowed).
- `START_BLUEPRINT` is added now so the L1 matrix covers the whole DESIGN §2 table. It is **defined, not enforced** until M20
  (its action does not exist yet); `SET_GUARD_SHIFT` likewise until M18. Both carry a `/* enforced in M20 / M18 */` comment and the
  ROADMAP M18/M20 entries get a note "gate the action with the existing permission".
- `Permission` is never serialized (saves and the wire carry ranks, not permissions), so M12 and M24 appending values in either order
  is safe. `Rank`'s order is load-bearing (`atLeast`, `HeartCodecs` ordinals, the `SetRank` int): an L1 test pins `Rank.values()` to
  `[OWNER, STEWARD, RESIDENT, VISITOR]`.
- Ops still get no bypass on the screen or the chest guard. The op escape hatch is a command (3.6).

### 3.3 Members: ranks with last-known names (core + saved data)

New record `core.KnownPlayer(UUID id, String name, long lastSeen)` (name cut to `Balance.MAX_PLAYER_NAME = 32`, non-blank;
`lastSeen` = game time). New `VillageState` component **`List<KnownPlayer> known`** (after `ranks`), the village's name book:

- Invariants (constructor): no duplicate ids; the owner is never in `known` (the owner's name is `ownerName`); **every UUID in
  `ranks` has a `known` entry** (a ranked player always has a name); `known.size() <= Balance.MAX_KNOWN_PLAYERS = 64`; at most
  `MAX_KNOWN_PLAYERS - 1` ranked players. Stored sorted by `lastSeen` then id, so equality and the save are stable.
- `seen(UUID id, String name, long now)`: for the owner, updates `ownerName`; else adds or updates the entry (name and
  `lastSeen`). When the book is full it evicts the **unranked** entry with the oldest `lastSeen` (ranked players are never evicted);
  if every entry is ranked the new Visitor is simply not recorded (still shown while online, 3.5).
- `withRank(UUID, Rank)` (M1 signature) stays: it throws when the player has no `known` entry, so callers must `seen` first;
  `withRank(UUID, String name, Rank, long now)` = `seen(...).withRank(...)` (what the glue uses). Demoting to VISITOR removes the
  rank but keeps the name (the player stays in the Ranks list as a Visitor).
- `transferOwnership(UUID newOwner, long now)`: requires `rankOf(newOwner)` STEWARD or RESIDENT. The old owner becomes a
  **Steward** (gets a `known` entry with `ownerName`), the new owner's rank and `known` entry are removed and `ownerName` becomes
  its last-known name. `claimedAtGameTime`, treasury, buildings and workers are unchanged (same village; the claim epoch does not change).
- `name(UUID)`: owner → `ownerName`, else the `known` name, else `""` (the glue then shows the first 8 hex digits of the UUID).

`core.rank.RankRules` (pure) returns `Optional<Rejection>` for a requested change, checked **after** the gate:
- `setRank(state, target, Rank r)`: `r == OWNER` → `BAD_RANK`; `target == owner` → `OWNER_RANK_FIXED`; target neither known nor
  online (the glue passes `boolean online`) → `UNKNOWN_PLAYER`; a new ranked member over the cap → `TOO_MANY_MEMBERS`; same rank → ok, no change.
- `transfer(state, actor, target)`: `target == actor` → `OWNER_RANK_FIXED`; rank of target not STEWARD/RESIDENT → `NOT_A_MEMBER`
  (you can only give the village to someone you already trust; prevents a mis-click on a stranger).

Saved data (`VillageCodecs`): new optional key **`known_players`**: list of `{ "id": "<uuid>", "name": "...", "last_seen": <long> }`
read with the lenient list codec (A4) and defaulting to `[]`. Repair on load (in the `RAW → VillageState` step, so an old or
hand-edited save never fails the whole village): drop entries for the owner and duplicates (first wins); for a ranked UUID with no
entry add `KnownPlayer(id, "", 0)` (name shown as the UUID prefix until the player joins again); trim to the caps
deterministically (unranked oldest first; if ranked players alone exceed 63, keep Stewards before Residents, then the most recent
`lastSeen`, then id) and log one WARN listing the dropped UUIDs. Names are stored with `§` formatting codes stripped and are always
rendered with `Component.literal` (never as a translation key or with formatting). Downgrading to a pre-M24 build drops
`known_players` (ranks survive; names come back as placeholders): documented, not supported. `RAW` grows to 10 fields (`RecordCodecBuilder` allows 16). A pre-M24 save (ranks but no names) loads with placeholder names.
Field names are part of the save format (`VillageCodecsTest` pins them).

Glue `dev.villageheart.rank.Members` (new package):
- `ServerPlayConnectionEvents.JOIN` **[verified: `Join.onPlayReady(ServerGamePacketListenerImpl, PacketSender, MinecraftServer)`]**:
  while a claim exists, `seen(player.getUUID(), player.getGameProfile().name(), gameTime)` (updates renamed players and the owner
  name; records Visitors so the Owner can rank them later while they are offline). Exposed as `Members.onJoin(server, player)`.
  `ServerPlayConnectionEvents.DISCONNECT` refreshes `lastSeen` too (a player online for days must not look like the oldest entry).
  The online flags in the Ranks tab need no extra hook: `HeartFacts.cached` collects at most once **per tick** (`cachedTick`), so the
  next 1 Hz refresh already sees the player list change.
- `setRank(server, actor, target, rank)` and `transfer(server, actor, target)`: one `VillageClaims.data(server).update(...)`,
  `HeartFacts.invalidate()`, `HeartMenu.markAllDirty(server)`, a log line, and notices (3.7). When an online player drops to
  **Visitor** and their open menu reads a **protected** container, it is closed with `player.closeContainer()`
  **[verified: `ServerPlayer.closeContainer()`]**. "Reads a protected container": some slot's `container` is a `BlockEntity` at a
  protected position, or a `CompoundContainer` (double chest) one of whose halves is (`CompoundContainer.contains(Container)`).
  A crafting table, a villager trade or a chest outside the buildings stays open. The rate limiter is untouched.
- Commands and payloads go through the **same** `RankRules` + `Members` code; every change (rank and transfer, including the
  command's "make Resident, then transfer") is validated first and applied in **one** `update`, so nothing fails halfway.

### 3.4 Chest protection (Minecraft glue + pure core check)

**Scope for v1 (decided).** A Visitor (any game mode, ops included) cannot **open** and cannot **break** a container that is
inside one of the village's claimed buildings, and cannot break a registered building **marker** (otherwise "break the marker,
then open the chest" defeats the rule in two clicks). Residents, Stewards and the Owner can. Everything else is out of scope:
hoppers and hopper minecarts placed next to or under a chest, pistons, explosions (creepers, TNT), breaking walls or floors,
chest/hopper minecarts, creative pick-block-with-data, entity containers (donkeys, item frames), outdoor-site chests (Mineshaft,
Hunting Ground, Training Yard: no room scan) and the claim area outside buildings. Why: DESIGN §2 asks only for "cannot open chests
inside claimed buildings"; Village Heart is a co-op village mod, not a grief-protection plugin (servers that need that run a claim
mod), and every indirect route above either needs block breaking that the building validation then shows in red, or is a creative
or explosion case. **This understates nothing on purpose:** a Visitor *can* break a floor block and put a hopper under a Storage chest,
and copper golems (1.21.9+) move items out of copper chests. v1 accepts that; DESIGN §2 and the README say plainly "Visitors cannot open
or break containers in buildings; it is not grief protection (hoppers, explosions and golems are not stopped)", and BACKLOG gets one item
("indirect container access by Visitors": hopper under/next to a protected container, golems, pistons, explosions).

**Which blocks (decided):** every block whose block entity is a `Container`, not only chests: chests, barrels, furnaces, smokers,
hoppers, droppers, dispensers, shulker boxes, brewing stands, crafters, and also jukeboxes, decorated pots and chiseled bookshelves
(they hold items, and a Visitor taking a disc or a book out of a village building is the same thing as taking bread). Exempt: the
ender chest (personal). Tested with one non-chest container (a furnace) refused and the ender chest allowed.

**What counts as protected** (pure `core.rank.ContainerGuard`, L1-tested):
```java
record GuardArea(String dimension, Pos marker, Optional<RoomScan> enclosed) {}
static boolean isProtected(String dimension, Pos pos, List<GuardArea> areas)
// true if some area in the same dimension has enclosed.occupies(pos), or has no enclosed scan and
// |pos - marker| <= Balance.GUARD_FALLBACK_RADIUS (16, Chebyshev) -- fail closed until the first enclosed scan.
```
- Positions: the clicked block, plus the other half of a double chest (`ChestBlock.TYPE != SINGLE` →
  `ChestBlock.getConnectedBlockPos(pos, state)` **[verified, static]**), protected if either half is.
- Which buildings: every registered `ROOM` building of the current village, any status, taken from the **saved** registry
  (`VillageState.buildings()`, which survives a restart; `Buildings.all` iterates it too) — never from the runtime scan cache, so an empty
  cache after a restart means "fallback box for every room", not "no buildings". The scan used is the **last enclosed** scan
  of that marker, not the raw latest one: a Visitor who breaks a wall makes the next scan leak, and a leaking scan's interior is
  partial garbage. `BuildingRuntime` gets `lastEnclosed: Map<HeartLocation, RoomScan>`, written in `BuildingValidator` when
  `raw.enclosed()`, removed with the building (same place as `rawScans.remove`); `Buildings.guardAreas(server)` builds the list.
  `lastEnclosed` is runtime only: after a restart every building is in the fail-closed fallback until it is rescanned (seconds).
- Which blocks: a block whose loaded block entity is a `net.minecraft.world.Container` (chests incl. trapped/copper, barrels,
  furnaces, smokers, blast furnaces, hoppers, droppers, dispensers, shulker boxes, brewing stands, crafters...). The ender chest is
  personal (`EnderChestBlockEntity` is not a `Container` **[verified]**) and stays usable. The block entity is read with
  `LevelChunk.getBlockEntity` via `getChunkNow` (the clicked chunk is loaded; same rule as the stockpile code).
- Outside a claim (no village, or another dimension) nothing is protected.

**Hooks** (`dev.villageheart.rank.ContainerProtection.register()`):
- Open: Fabric `UseBlockCallback.EVENT` **[verified: called at HEAD of `ServerPlayerGameMode.useItemOn` and on the client in
  `MultiPlayerGameMode`; "hooked in before the spectator check"; non-PASS cancels]**. On the client it returns `PASS` (the
  client does not know ranks; `ChestBlock.useWithoutItem` on the client only predicts SUCCESS and opens nothing). On the server, for
  a protected container and a player without `OPEN_CONTAINERS`: return `InteractionResult.FAIL` and send the action-bar line
  `message.villageheart.protect.container` ("This belongs to the village of %s. Ask the Owner to make you a Resident."). Vanilla's
  `handleUseItemOn` then resends the block states of the clicked block and its neighbour **[verified: lines 1334-1335]**. Because a
  refused use with an item in hand (a disc on a jukebox, an item on a decorated pot) can leave a predicted inventory change on the
  client, the refusal also calls `player.containerMenu.sendAllDataToRemote()` (the same resync M1 uses after a refused Heart placement).
  **Exception:** vanilla skips the block's use when
  `isSecondaryUseActive()` and either hand holds an item (sneak-place against the chest, `ServerPlayerGameMode` line 355
  **[verified]**); the guard returns PASS in exactly that case so a Visitor can still place a torch on a Storage wall chest. A
  spectator Visitor is refused (vanilla's spectator branch would open the menu).
- Break: the existing `PlayerBlockBreakEvents.BEFORE` listener (`VillageHeart.allowBreak`) grows into
  `ContainerProtection.allowBreak`: Heart (unchanged rule, now via `BREAK_HEART`), protected container or registered marker and no
  `OPEN_CONTAINERS` → `false` + action-bar line `message.villageheart.protect.break`. Fabric's mixin calls BEFORE inside
  `ServerPlayerGameMode.destroyBlock` **[verified]**, which returns false, and vanilla's block-change ack restores the client's
  predicted break. For a double chest the client's prediction may also have turned the other half into a single chest, so a
  `PlayerBlockBreakEvents.CANCELED` listener sends `ClientboundBlockUpdatePacket` for the connected half (checked in T-L4-2).
- Payload receivers and these hooks all run on the server thread (Fabric 1.20.5+ play receivers execute on the main thread, as M8's
  do; the interaction events are called from `ServerPlayerGameMode`).
- Cost: only when the block is a container or a marker (checked first), then one pass over the village's buildings with set
  lookups. No per-tick work, nothing in the 1 ms budget.

### 3.5 Heart screen: the Ranks tab (snapshot, facts, client)

Core:
- `VillageFacts` + `List<MemberFact> members`, `MemberFact(UUID id, String name, Rank rank, boolean online)`.
  `HeartFacts.collect` builds it from the state and `server.getPlayerList()`: the owner, every `known` player, and every online
  player not in `known` (online Visitors are always rankable). Name: online profile name > `state.name(id)` > UUID prefix.
- `HeartSnapshot` + `List<MemberRow> members, int moreMembers` (appended components). `MemberRow(UUID id, String name, Rank rank,
  boolean online)`. Filled only for viewers with `MANAGE_RANKS` (the Owner); empty otherwise, so Stewards and Residents are never sent
  other players' UUIDs. Order: Owner, Stewards, Residents, Visitors; within a rank online first, then name (case-insensitive), then id.
  Cap `HeartLimits.MAX_MEMBERS = 100` with "+N more".
- `HeartCodecs`: `MEMBER_ROW` (UUID, `NAME`, `RANK`, `BOOL`), list bounded by `MAX_MEMBERS`; appended to `SNAPSHOT`.
  `HeartCodecsTest`'s worst case grows by ≤ 100 × (16 + 3 + 96 + 2) ≈ 12 KB; still asserted under 512 KiB.

Payloads (C2S, `heart/net`, registered in `HeartNetwork`):
- `SetRankPayload(int containerId, UUID player, int rank)` (`heart_set_rank`; `VAR_INT` rank, any int decodes) →
  `HeartAction.SetRank(UUID player, int rankId)`; `permission() = MANAGE_RANKS`.
- `TransferOwnershipPayload(int containerId, UUID newOwner, int expectedRank)` (`heart_transfer_ownership`) →
  `HeartAction.Transfer(UUID, int expectedRank)`; `permission() = TRANSFER_OWNERSHIP`. The client sends the rank its row showed;
  if the target's current rank differs (a demotion raced the confirm), the server refuses with `TARGET_CHANGED` ("That player's rank
  just changed. Check and try again.").
- `HeartAction` gets `default Optional<Rejection> malformed()` (M12's `Withdraw` overrides it for `BAD_AMOUNT`, A2);
  `SetRank` returns `BAD_RANK` unless `rankId` is STEWARD, RESIDENT or VISITOR. `ActionGate` calls it after the epoch/village checks
  and before the permission. A crafted payload never throws.
- `HeartActions.handle` switch: `SetRank` → `RankRules.setRank` then `Members.setRank`; `Transfer` → `RankRules.transfer` then
  `Members.transfer`. Replies: `message.villageheart.rank.set` ("%s is now a %s."), `…rank.unchanged`, `…rank.transferred`
  ("You gave the village to %s. You are now a Steward."). Every UUID is validated against the current state (re-read), never
  trusted from the screen.
- `Rejection` + `BAD_RANK, UNKNOWN_PLAYER, OWNER_RANK_FIXED, TOO_MANY_MEMBERS, NOT_A_MEMBER, TARGET_CHANGED` (appended; lang keys from `id()`).

Client (`HeartScreen`):
- `TAB_KEYS` + `tab.ranks` (index 4, key `5`). `tabAllowed(4) = allows(MANAGE_RANKS)`; for everyone else it is drawn locked with the
  M8 tooltip. At 427 px the five tabs are `min(110, (427 - 2·MARGIN)/5)` ≈ 80 px wide; "Ranks" and "Stockpile" fit (L4 asserts no clipping).
- The list (same row widget code as Villagers): a green dot for online (grey for offline), name, rank label
  (`gui.villageheart.heart.rank.<rank>`). Header line: "%s players · Ranks apply at once". Selecting a row (not the Owner's) shows
  the action bar: `[Steward] [Resident] [Visitor]` (the current rank's button inactive) and `[Transfer ownership]` (active only for a
  Steward or Resident; tooltip otherwise "Make them a Resident or Steward first").
- **Confirmation:** the first click on Transfer turns it into `[Confirm: give the village to %s]` (red text) for 100 ticks or until
  another row/tab is selected (the existing `pendingConfirm` pattern); only the second click sends `TransferOwnershipPayload`. No
  separate `ConfirmScreen` (replacing the screen would close the menu).
- After a transfer the next snapshot has `viewerRank = STEWARD`; `onSnapshot → selectTab(tab)` locks the Ranks tab and drops to the
  Overview (M8's rule: a locked tab can never stay shown).
- Test hooks: `rowCentre(int index)`, `actionButton(String key)` lookup is the existing `clickScreenButton` by lang key.

### 3.6 Op commands (BACKLOG M1: absent owner)

Under the existing `villageheart` root (op level 2), new class `rank.RankCommands`:
- `/villageheart owner <player>`: the target is a **string argument resolved against online players and the village's known
  players** (suggestions from both), not `GameProfileArgument` (which can do a blocking profile lookup for a never-seen name and would
  record a stranger). Unknown name → error "No player called %s has been seen by this village." Validated with `RankRules` first,
  then "make Resident if Visitor + transfer" in one `update`. Works while the old owner is offline. This ticks the BACKLOG M1 item (an op no longer has to `/setblock` the
  Heart away). The old owner becomes a Steward, as with a normal transfer.
- `/villageheart rank <player> <steward|resident|visitor>`: same target resolution, and exactly the screen's `RankRules`
  (`OWNER_RANK_FIXED`, caps); each rejection prints its `Rejection.message()`. Used by the scripted 2-player session (3.8) and handy on servers.

### 3.8 Release-gate harness: a 2-player dedicated-server session (sketch, built in step 10)

v1.0 gate: "a dedicated server with 2 players (Owner + Resident) runs a scripted session with no desync errors". Fabric's
client-gametest API can start an **in-process dedicated server** and connect the test client to it
**[verified: `context.worldBuilder().createServer(Properties)` → `TestDedicatedServerContext` (`runCommand`, `runOnServer`,
`computeOnServer`, `connect()` → `TestServerConnection.getClientWorld()`); online-mode false, spawn-protection 0 by default; needs the
EULA, which `build.gradle` already accepts]**. Only one real client exists per test JVM, so the second player is a server-side fake
player on that dedicated server (`GameProfile` + `EmbeddedChannel` + `placeNewPlayer`, as `SimPlayer` does, outbound drained every
step), acting through `HeartActions.handle`. **Keep-alive:** a fake connection never answers keep-alives, and the server disconnects
a player after 15 s without an answer. The helper drains its outbound queue every tick (a server tick listener active only during the
test), and for each `ClientboundKeepAlivePacket` it finds calls `connection.handleKeepAlive(new ServerboundKeepAlivePacket(id))`; the
test asserts at the end that the fake player is still in the player list (first check what `SimPlayer` already gets away with:
the sims run for hours, so the builder confirms whether the timeout applies to `EmbeddedChannel` connections before adding code).

**Gate wording (not decided by M24):** the gate says "2 players (Owner + Resident)". This harness is **1 real networked client + 1
server-side player**: everything the real client sees crosses the network, the fake Owner's side does not. M24 builds the harness and
adds a note under the gate item in ROADMAP ("harness: `MultiplayerClientTests`, 1 real client + 1 server-side player; a second real
client would need a protocol bot"). Whether that satisfies the gate is the orchestrator's/user's call at release; M24 does **not**
tick the gate. The real client is the player whose view can desync, so it plays the role that changes:

`MultiplayerClientTests.ownerAndResident` (L4, called from `VillageHeartClientTests`):
1. `createServer()`, `connect()`, wait for chunks. Fake owner "Olga" joins; commands build bell, Heart (claimed by Olga through
   `VillageClaims.claim`), a Storage room with two chests and items, 10 emeralds in the client's inventory.
2. Client is a Visitor: aims at the Storage chest, right mouse → after 5 ticks no screen on the client, server `containerMenu` is the
   inventory menu, chest unchanged. With a music disc in hand it uses a jukebox in the room → refused, the client's hand still holds
   the disc and the client's jukebox state equals the server's. It holds left mouse on one half of a double chest until the break
   would finish → refused, and **both** halves' client block states equal the server's (`TYPE` LEFT/RIGHT kept).
3. Olga makes the client a Resident (`SetRank` through `HeartActions.handle`). Client opens the chest (real input), shift-clicks one
   stack into its inventory, closes.
4. Client opens the Heart, deposits (M12 "Deposit all" button), Olga transfers ownership to the client; the client sees the Ranks tab
   unlock with Olga listed as an online Steward, withdraws 1 emerald, sets Olga to Resident through the UI.
5. **Desync checks after every step:** (a) the client's `HeartMenu.snapshot()` equals the **last snapshot the server actually sent**
   to that player (a test accessor on the server `HeartMenu.lastSent`), polled ≤ 40 ticks, **and** a step-specific field has the
   expected value (`viewerRank`, member count, treasury), so two equal stale snapshots cannot pass; (b) the client's inventory equals
   the server's (item id + count + components per slot); (c) server chest contents equal the expected counts; (d) the client is still
   connected (`mc.getConnection() != null`) and so is the fake player; (e) the test prints `MP_SESSION begin` / `MP_SESSION end`, and
   `scripts/check-mp-log.sh` (stub-log self-tests, like `check-model-log.sh`) fails if, between the markers, a line from the `Server

## 6. Risks, unknowns, out of scope

1. **(Top risk) The guard depends on cached room scans.** A chest is only "inside a building" as far as the last enclosed scan says.
   Windows: a chest added to a room is protected only from the next scan (≤ n × 20 ticks); after a restart the fallback box (16)
   protects too much (a Visitor's own chest next to a building) until the rescan. Accepted and documented; T-L2-3 pins both directions.
   Using the raw scan would fail open on a leak; scanning on every click would cost up to a room scan per right-click.
2. **UseBlockCallback on the client.** Returning PASS client-side relies on vanilla's client prediction for containers opening
   nothing; a modded container that opens a client-only screen would flash. Only vanilla containers are tested.
3. **Dedicated server inside the client test JVM (step 10).** New territory for this repo: one more server start (~20-40 s), shared
   static state between the integrated and the dedicated server (`HeartActions.RATE`, `HeartNetwork` sender, `HeartFacts` cache: all
   reset on `SERVER_STOPPING`, check), the fake player's `EmbeddedChannel` must be drained, and the lost-wakeup mixin must also
   cover this connection. If `createServer` cannot run in CI (port, EULA, memory) after two honest attempts, keep the harness behind
   `-Dvillageheart.mpSession=true`, record the blocker in PROGRESS and BACKLOG, and do not count the gate item as done.
4. **M12 not built yet** (A1-A5): only step 9 waits; the `Permissions` merge is one file.
5. **`VillageState` grows a 10th component**: every `new VillageState(...)` changes (M12's too). The builder should add a private
   `copy(...)` helper first so later milestones add components in one place.
6. **Name book and big servers**: 64 known players; online Visitors beyond that are still listed while online. Fine for co-op scale.
7. **Offline-mode name collisions**: two UUIDs can share a name; rows and payloads use UUIDs, the list shows both.

**Out of scope:** indirect container access (hoppers, minecarts, pistons, explosions, wall breaking), creative pick-block with data,
outdoor-site chests, entity containers, protecting non-container blocks or the claim area; per-building or per-player permissions;
more than one Owner or co-owners; rank changes by Stewards; a ranks history/log; ops bypassing ranks in the screen (deliberately none);
a second real client and a server restart in the 2-player session.
