## 1. Goal

One command, `scripts/simulate.sh bare 5`, boots a real headless Minecraft server on a fixed seed.
It finds the real plains village there and claims it with a Village Heart through the normal
placement path. It then fast-forwards 5 in-game days and writes one metrics record per day to
`reports/sim/bare.json`. It ends with an exit code that says whether the scenario's assertions held.
Later milestones (`starter`, `defended`, `raid`, `full`) add a scenario by dropping a JSON file into
`sim/scenarios/`, with no harness changes, and the 1 ms/tick budget (DESIGN §12) gets a real measurement.

## 3. Design

### 3.1 How the server boots: a Loom run config (decision)

**Chosen: a custom Loom run config `simulation` → task `runSimulation`.** It is a real dedicated server
(`server()`) that runs the `gametest` source set, so the harness code is never shipped in the mod jar. The run
directory is `build/run/sim`, and a system property switches the harness on. **[spiked]**: this exact block, placed **after**
the `fabricApi { … }` block, created `runSimulation`. A world was generated and the server reached "Done" in ~4 s after
Gradle started it (about 25–30 s wall time including Gradle configure on a warm cache).

```groovy
// build.gradle, AFTER fabricApi { configureTests { … } } (sourceSets.gametest does not exist before it:
// putting it in the first loom {} block fails with "Could not get unknown property 'gametest'")
loom {
	runs {
		simulation {
			server()
			name "Simulation"
			source sourceSets.gametest
			runDir "build/run/sim"
			property "villageheart.sim.request", file("build/run/sim/sim-request.json").absolutePath
			vmArg "-Xmx3G"
			programArgs "--nogui"
		}
	}
}
```

Why not the alternatives:
- **The Fabric GameTest server** generates a void/flat test world, not a seeded world with a village, and it
  stops when its tests finish. A test that runs for 30 days fights its timeout and batch model.
- **A custom server entrypoint or a raw `java -jar`** means rebuilding Loom's dev launch (remapped
  classpath, DLI config) by hand. The run config gets all of this for free.
- **`runServer` with args** cannot take the gametest source set and would put the harness into `main`.

How the harness is switched on: the `gametest` mod gets a `"main"` entrypoint,
`dev.villageheart.sim.SimulationBootstrap`. If `System.getProperty("villageheart.sim.request")` is null it
returns at once. So `runGameTest`, `runClientGameTest` and players' games are unaffected. All run parameters
come from the **request file** (JSON) that `simulate.sh` writes. Environment variables and program args are not used:
the dedicated server's own option parser handles program args, and with `--no-daemon` Gradle forks a daemon, so
the request file is the one channel that is sure to work.

Facts from the spike that the design relies on:
- **A server crash still ends `./gradlew runSimulation` with exit code 0** (Loom catches it and writes a crash report). **[spiked]**
  So `simulate.sh` never trusts Gradle's exit code. The report file's `status` is the only source of truth (§3.7).
- `server.halt(false)`, called from inside an `END_SERVER_TICK` callback, saves players, chunks and saved data, then stops cleanly. **[spiked]**
- The Mojang auth lookups fail (offline sandbox) and only log an ERROR. `online-mode=false` works. **[spiked]**
- `pause-when-empty-seconds=0` in `server.properties`: no pause seen while no player was online. **[spiked]**
  The harness also keeps its fake player online, so the 1.21.2+ empty-server pause cannot trigger.
- On restart with the same world dir, the claim (`villageheart_village.dat`), `gameTime`/`dayTime` and the forced
  chunks all come back. **[spiked]**: 48041 game ticks restored, claim present.

### 3.2 World, seed and finding the village

- **Seed `1`** (`level-seed=1`, default world type). **[spiked]**: the nearest `minecraft:village_plains` start is
  **(640, ~, 816)**, 812 blocks from spawn. The bell (MEETING POI) is at **(639, 66, 821)**. There are **8 villagers and 1 iron golem**
  within 96 blocks. The Heart, placed on the first solid ground east of the bell, landed at **(642, 64, 821)** and claimed.
  Spawn distance does not matter: the harness force-loads the village and teleports there.
- The seed is a constant in the harness (`SimWorld.SEED = 1L`), and `simulate.sh` writes it into `server.properties`.
  A scenario may override it with `"seed"`, but no scenario should until there is a reason.
- Locate (on `SERVER_STARTED`, overworld) **[verified + spiked]**:
  ```java
  Registry<Structure> reg = level.registryAccess().lookupOrThrow(Registries.STRUCTURE);
  HolderSet<Structure> plains = HolderSet.direct(reg.getOrThrow(BuiltinStructures.VILLAGE_PLAINS));
  Pair<BlockPos, Holder<Structure>> hit = level.getChunkSource().getGenerator()
          .findNearestMapStructure(level, plains, level.getRespawnData().pos(), 100, false); // 100 chunks, like /locate; ~0.7 s
  ```
  `hit == null` → ERROR "no plains village within 100 chunks". **Do not** call `structureManager().getStructureAt(pos, …)`
  on the returned position: the spike got an invalid start, and `getBoundingBox()` **threw `IllegalStateException`
  "Unable to calculate boundingbox without pieces" and crashed the server**. Do not use structure bounds. Use the POI.
- Load: `level.setChunkForced(cx+dx, cz+dz, true)` for dx, dz ∈ [-4, 4] around the start chunk (81 chunks; ~7 s
  of chunk generation on the server thread, which logs one "Can't keep up" WARN, expected) **[spiked]**. The chunks stay forced for the
  whole run, and the forcing persists in the save. That helps resume.
- Find the bell: poll every 20 ticks, for up to 600 ticks, with
  `level.getPoiManager().findClosest(t -> t.is(PoiTypes.MEETING), villagePos, 96, PoiManager.Occupancy.ANY)`.
  The spike found it 40 ticks after forcing **[spiked]**. Not found → ERROR "no bell near village".
- **Heart spot** (`SimWorld.heartSpot(level, bell)`): for r = 2..6 and the four directions E, S, W, N in that order, take
  `ground = level.getHeightmapPos(Heightmap.Types.MOTION_BLOCKING_NO_LEAVES, bell.offset(dir*r)).below()`. Accept it if
  `ground` is not a bell, its top face is sturdy (`isFaceSturdy(level, ground, Direction.UP)`), `ground.above()` is air, and
  the distance from `ground.above()` to the bell is ≤ `ClaimRules.MAX_BELL_DISTANCE`. Use the first one accepted. Seed 1 gives (642, 64, 821).

### 3.3 The simulated owner (fake player)

- `SimPlayer.join(server, level, at)`: a `GameProfile(SimWorld.OWNER_UUID, "SimOwner")`, where
  `OWNER_UUID = UUID.nameUUIDFromBytes("villageheart-sim-owner".getBytes(UTF_8))` is **fixed**, so a resumed run is
  the same owner and gets its player data back. It uses the `VillageTestSupport.player` recipe (`ClientInformation.createDefault()`,
  `CommonListenerCookie.createInitial(profile, false)`) and `setGameMode(GameType.CREATIVE)`, and is teleported
  above the Heart spot **[spiked]**. Creative: mobs ignore it and it cannot die.
- Why a player at all: (a) the claim needs a `Player` owner and a real placement. (b) Since 1.21.5, mob spawning and
  random ticks (crop growth for M10/M11) only happen near a non-spectator player. A scenario without one would not
  be realistic. The player stays at the Heart for the whole run, like a player standing AFK there.
- **Must:** drain the fake connection. A bare `EmbeddedChannel` keeps every packet the server writes in its
  outbound queue forever (chunks, entity updates), which leaks memory over 30 days. Keep the channel in
  `SimPlayer`, and call `channel.releaseOutbound()` every 20 ticks. `server.heap_used_mb` is reported every day
  (§3.6) so that a leak shows up.
- Placement: `ItemStack heart = new ItemStack(ModBlocks.VILLAGE_HEART_ITEM)`, `player.setItemInHand(MAIN_HAND, heart)`,
  `player.gameMode.useItemOn(player, level, heart, MAIN_HAND, new BlockHitResult(Vec3.atCenterOf(ground).add(0, 0.5, 0), Direction.UP, ground, false))`
  **[verified + spiked]** (it returned `Success` and `VillageClaims.current(server)` was present). If the result is not a success
  or no claim exists afterwards → ERROR, with the `ClaimRules.Result` from `VillageClaims.evaluate(level, ground.above())`.

### 3.4 Time, days and fast-forward

- After setup the harness sets `level.setDayTime(0)` **[verified]** (dawn, with `doDaylightCycle` left at its default true),
  stores `G0 = level.getGameTime()`, and calls
  `server.tickRateManager().requestGameToSprint(days * 24000 + 200)` **[verified + spiked]**. The sprint runs ticks back to
  back with no 50 ms sleep.
- **Sim day d (1-based) ends at game time `G0 + d·24000`.** The harness keeps `nextDay` (starting at 1). In every `END_SERVER_TICK`
  where `gameTime - G0 >= nextDay·24000` it records day `nextDay` and increments it (`>=`, never `==`, so a skipped tick cannot lose a day). So "population on day 1" means at the end of day 1 (the next dawn). A **baseline** record
  (day 0) is taken right after setup, at `G0`. It is written separately (`"baseline"`) and does not count as one of the N
  days. Every in-game clock is lined up with real dawns: dinner at 11000 (M11) and wages at dawn (M12) fall
  inside the right sim day.
- When the last day is recorded: `stopSprinting()` **[verified]**, then evaluate, write, `server.halt(false)`.
- Day-timed actions (§3.5) are held in a pure `core.sim.ActionSchedule`: actions sorted by `T = (day-1)·24000 + tick`. Each tick it
  returns every action not yet run with `T <= gameTime - G0` (`>=` again), and it counts `actionsDone`. That count is saved in the report and used on resume.
- **Order inside one harness tick (fixed, unit-tested on `ActionSchedule` plus a pure `SimClock`):** (1) record any day that ended;
  (2) run the due actions; (3) rewrite the report (days and `actions_done`); (4) if `stop_after_day` or the last day is reached, finish.
  So an action at `day = D+1, tick = 0` runs in the same tick that ends day D, **after** the record and **before** a `--reload-at D` halt.
  It runs once, in phase 1, and is never re-run, because `actions_done` comes back on resume.
- **Timer and wall-clock resets:** at the `G0` tick, after the baseline is recorded, call `VillageTicker.TIMER.snapshotAndReset()` and
  reset the day's wall clock and tick counter. The first `village_ms` and `wall_seconds` then cover exactly day 1. Do the same
  at the moment the sprint restarts on resume, so day D+1 does not contain boot ticks.
- **Speed measured in this container (4 cores, 15 GB)** **[spiked]**, vanilla village with 8 villagers:
  - With no player, 24000 ticks sprinted at 716 TPS (34 s/day).
  - With the creative fake player, 2 days took 102 s. Daytime quarters took ~9 s per 6000 ticks, night
    quarters ~15 s (mob spawning), and the first quarter 20 s (chunk generation around the player).
    That is ≈ **50 s per day ≈ 1.2 days per real minute**.
  - **Budgets:** a 5-day run ≈ 4–5 min plus ~40 s of Gradle/boot ≈ **5–6 min**. A 30-day run ≈ **25–30 min** at this load.
    Later scenarios (more villagers, mod workers) will be slower. `simulate.sh` timeout = `240 + 150·days` s
    (5 days → 16.5 min, 30 days → 79 min), so a hang still ends.
- Autosave keeps running during the sprint (every 6000 ticks). That cost is real and stays in the measurements.

### 3.5 Scenario format

Scenarios are files `sim/scenarios/<name>.json` at the repo root, so `simulate.sh` can list and validate names without Java.
They are parsed by `core.sim.ScenarioParser` (pure, L1-tested):

```json
{
  "schema": 1,
  "name": "bare",
  "description": "Claim the seed-1 plains village and do nothing else. Proves the harness and records vanilla baseline.",
  "default_days": 5,
  "actions": [
    { "action": "claim" }
  ],
  "assertions": [
    "claimed == 1 on every day",
    "population >= population@day1 - 1 on last day",
    "village_ms.mean < 1 on every day"
  ]
}
```

- `name` must equal the file name (parser error otherwise). `default_days` ≥ 1.
- `actions`: an ordered list. Each has `action` (a type id) plus optional `day` (default 0 = during setup, before the baseline)
  and `tick` (0..23999, default 0), plus type-specific fields. Actions with `day ≥ 1` run during the sprint (§3.4).
  `day` must be ≤ the number of days being run, or it is a request error (exit 2, before the server boots any further).
- **Action types in M2** (glue `dev.villageheart.sim.SimActions`, a `Map<String, SimAction>`):
  - `claim`: place the Heart at `heartSpot` with the fake owner (§3.3). Optional `"offset": [dx, dy, dz]` from the bell
    overrides the spot search (for later scenarios that need the Heart in a set place).
  - `command`: `"command": "summon minecraft:zombie ~3 ~ ~"`. It runs through
    `server.getCommands().performPrefixedCommand(source, cmd)` **[verified]**, where `source = server.createCommandSourceStack()`
    `.withLevel(overworld).withPosition(Vec3.atBottomCenterOf(heart))`
    `.withCallback((ok, result) -> …)` **[verified]**. `~` is relative to the Heart. `ok == false` → ERROR with the command text.
    This is the escape hatch that makes most later setups cheap: `/place template …` for prebuilt buildings,
    `/summon`, `/give`, `/fill`, `/time`, `/raid`.
  - `fail`: throws `IllegalStateException("scenario fail action")` inside the harness's try/catch → status ERROR (self-test).
  - `crash`: sets a flag. A separate `END_SERVER_TICK` listener that is **not** wrapped in the harness catch throws on the next tick.
    That is a real server crash: a crash report is written, Loom still exits 0, and the report stays `RUNNING` (self-test).
  - `hang`: `Thread.sleep` in a loop on the server thread. Vanilla's `ServerWatchdog` (`max-tick-time=60000`, set explicitly in
    `server.properties`) kills the JVM after 60 s with a crash report. The script's stall check (§3.7) is the backstop (self-test).
  - `command` details: positions use `~` relative to the Heart, or relative to the bell if no claim exists yet (so a command can run
    before `claim`). Output is **not** suppressed: the server source logs it into `reports/sim/<name>.log`. The ERROR detail is the
    command text plus "see log". If the callback never fires during `performPrefixedCommand` (some parse failures), that is also an ERROR.
- Later milestones add action types (`structure`, `stock`, `hire`, `raid`, …) as one `SimAction` class each, plus one
  map entry. Unknown `action` → parse error.
- `seed` (optional, long): see §3.2.

**Assertion language** (`core.sim.Assertion`, a recursive-descent parser, pure):

```
assertion := compare [ scope ]
compare   := sum CMP sum                     CMP: >= <= > < == !=
sum       := product (("+" | "-") product)*
product   := unary (("*" | "/") unary)*
unary     := "-" unary | atom
atom      := NUMBER | ref | FUNC "(" sum ")" | "(" sum ")"
ref       := PATH [ "@" dayref ]
dayref    := "day" INT | "first" | "last" | "prev"     written without spaces: population@day1, population@prev
FUNC      := "sum" | "mean" | "min" | "max"
scope     := "on" ( "every day" | "last day" | "day" INT | "days" INT ".." INT ) | "from day" INT
NUMBER    := DIGITS [ "." DIGITS ] [ ("e"|"E") ["+"|"-"] DIGITS ]     no leading ".", INT := DIGITS (lexing stops before "..")
PATH      := [a-z_][a-z0-9_]* ( "." [a-z0-9_:/]+ )*     e.g. population, village_ms.mean, stockpile.items.minecraft:oak_log
```

Semantics:
- Lexing: whitespace separates tokens but is not required around operators. `-` is never part of a PATH, so
  `population@day1-1` is `population@day1 - 1`. Inside a ref, `@day` must be followed directly by digits (`@day1`); `@day 1` is
  a syntax error, which keeps it apart from the scope keyword `day`. Scope keywords are only valid after `on`, except `from day N`, which is a scope on its own.
- The default scope is `last day`. Day numbers are 1-based. `@first` = day 1, `@last` = the last day run,
  `@prev` = the previous day (day 0 = baseline for day 1). `@day N` with N outside 0..days → evaluation FAIL with a clear detail.
- **No FUNC in the assertion:** it is checked for every day in the scope. A bare `ref` means "this day". It passes only if
  every day passes. The detail names the first failing day and the values on both sides,
  e.g. `day 3: population=5.0 < population@day1-1=7.0`.
- **With a FUNC:** each FUNC folds its argument over the days in the scope. A bare `ref` inside a FUNC means "each day".
  A bare `ref` outside means the last day of the scope, and `@prev` outside means the day before that. The comparison is checked once.
  **Rejected at parse time:** nested FUNCs (`sum(max(x))`) and `@` refs inside a FUNC (`sum(population@day1)`).
- **Empty or out-of-range scopes** (`days 3..2`, `from day 6` or `on day 9` with 5 days) → FAIL "empty scope", never a vacuous pass.
- Metric paths are checked when the assertion is **parsed** against `MetricNames.KNOWN` (§3.6). The dynamic families
  `stockpile.items.<id>`, `stockpile.tag.<tag>` (reserved, filled by M6, e.g. `stockpile.tag.minecraft:logs`) and `deaths.cause.<cause>`
  are valid for any suffix and read 0 when missing. An unknown path, bad syntax or
  division by zero → `AssertionSyntaxException` at parse time, or a FAIL with the detail at evaluation time. Never a silent pass.
- Later milestones add functions in one place (`AssertionFunctions`), each with a unit test. Expected ones: `streak(<compare>)`
  for "food days left never 0 for more than 1 day in a row", `delta(path)` = value − value@prev for "logs increase every day",
  `ratio(a, b)`. Comparing two runs (the M13 "beats the M11 baseline" check, and the release gate's "same trend after a reload")
  is a separate pure `ReportCompare` with `simulate.sh --compare <report.json>`. It is out of scope for M2 and named here so nobody forces it into the grammar.

`core.sim.ScenarioEvaluator.evaluate(Scenario, MetricsTable, List<String> extraAssertions)` → `ScenarioResult(status, List<AssertionResult>)`.
The status is `PASS` if all pass, else `FAIL`. Extra assertions come from `simulate.sh --assert`.
All assertions (scenario and extra) are **parsed at harness start**, before the world work. A parse error writes status `ERROR` and halts within seconds.

### 3.6 Metrics: per-day record and JSON schema

Core records (pure, `dev.villageheart.core.sim`):

```java

public record DeathRecord(String cause, boolean byMob, long gameTime) {}
public record DayMetrics(int day, long gameTime, boolean claimed,
        int population, int adults, int babies, int employed,

```

### 3.7 `scripts/simulate.sh`: CLI, exit codes, reload

```
scripts/simulate.sh <scenario> [days] [--assert "<expr>"]... [--reload-at <day>]
scripts/simulate.sh --list
env: SIM_TIMEOUT_SECONDS (overall limit), SIM_STALL_SECONDS (default 600), SIM_GRADLE_CMD (default "./gradlew --no-daemon runSimulation")
```
The script uses `set -uo pipefail` (no `-e`, like `verify.sh`) and captures each return code explicitly.

1. **Validate** (→ **exit 64** with usage): the scenario file `sim/scenarios/<scenario>.json` exists. `days` is an integer 0..365, default
   `default_days` read with `python3 -c 'import json…'`. `--reload-at` is in 1..days-1. `days = 0` with `--assert` is refused.
2. **Lock and clean:** `exec 9> build/run/sim/.lock; flock -n 9 || { echo "another simulation is running"; exit 2; }`.
   Java 25 the same way as `verify.sh`. `mkdir -p reports/sim build/run/sim`. Delete `reports/sim/<scenario>.*` (json, tmp,
   summary, every log), `build/run/sim/world` and `build/run/sim/crash-reports`. Write `build/run/sim/eula.txt` (`eula=true`) and
   `server.properties`: `online-mode=false`, `level-seed=<seed>`, `difficulty=normal` (the default is easy, where villagers never
   turn into zombie villagers; the report records it), `pause-when-empty-seconds=0`, `max-tick-time=60000`, `spawn-protection=0`,
   `view-distance=6`, `simulation-distance=6`, `sync-chunk-writes=false`, `enable-rcon=false`, `motd=villageheart-sim`.
3. **Request:** write `build/run/sim/sim-request.json` (with python3, for correct JSON escaping):
   `{"scenario_file": abs, "scenario": name, "days": N, "out": abs reports/sim/<name>.json, "extra_assertions": [...],
     "stop_after_day": D or null, "resume": false}`.
4. **Run one phase** (function `run_phase <log>`):
   - Start `setsid timeout -k 30 <T>s $SIM_GRADLE_CMD < /dev/null > <log> 2>&1 &`, where T = `SIM_TIMEOUT_SECONDS` or `240 + 150·days`.
     A `trap` on EXIT/INT/TERM kills the whole process group (`kill -- -$pgid`), so no daemon or server JVM outlives the script or holds
     `session.lock` for the next run.
   - **Watch while it runs** (poll every 5 s):
     - (a) The report must appear within 180 s of the start.
     - (b) After that, the report's mtime must change at least every `SIM_STALL_SECONDS`. The harness rewrites it every day,
       and also every 6000 ticks with only `"heartbeat"` updated, so a slow day is not mistaken for a stall.
     - Breaking (a) or (b): kill the group and **exit 2** ("harness did not start" or "stalled").
   - `wait` gives `rc`. **Any `rc ≠ 0` → exit 2**, whatever the report says. That covers a Gradle compile failure, a timeout (124 or 137)
     and a kill. Only when `rc == 0` does the report decide.
5. **Decide** (python3 reads the report). **Exit 0 needs all of these:**
   - `status == "PASS"`,
   - `clean_shutdown == true` (written by the harness in `SERVER_STOPPED`, after the final save),
   - `len(days) == N`,
   - no file in `build/run/sim/crash-reports/`.

   Otherwise `FAIL` → 1, and anything else → 2.
6. **With `--reload-at D`:** phase 1 runs with `stop_after_day: D`. The harness ends phase 1 in tick order §3.4: it records day D, runs the
   due actions, writes the report, then halts. The script requires `rc == 0`, `status == "RUNNING"`, `len(days) == D`,
   `clean_shutdown == true` and `stopped_after_day == D`. Otherwise exit 2. It then rewrites the request with `resume: true` and
   `stop_after_day: null`, and runs phase 2 on the **same world dir** (log `<name>.2.log`).
   On `resume` the harness:
   - reads the report with `MetricsJson.read`;
   - checks that the claim exists, `gameTime >= G0 + D·24000` and the owner UUID matches;
   - re-joins `SimPlayer` (the fixed UUID), restores `ActionSchedule` from `actions_done`, appends `D` to `reloads` and sets `clean_shutdown` back to false;
   - resets the timers (§3.4) and re-sprints for `G0 + days·24000 − gameTime + 200` ticks.
7. The exit codes:

| Code | Meaning |
|---|---|
| 0 | `PASS` + `clean_shutdown` + N records + no crash report + Gradle rc 0 |
| 1 | `FAIL`: at least one assertion was false (red is red); everything else was healthy |
| 2 | `ERROR`, or any of: Gradle rc ≠ 0 (compile failure, timeout, killed), no report within 180 s, a stalled report, a missing or unparsable report, status still `RUNNING`, no `clean_shutdown`, a crash report, a record count ≠ N, the lock is held |
| 64 | usage error |

   The script prints `reports/sim/<name>.summary.md` when it exists, plus the last 30 log lines on ERROR.
8. `--list` prints the scenario names and descriptions.

**Harness side of the contract** (`SimulationBootstrap`):
- In `onInitialize`, read the request. If that fails (missing file, bad JSON), write `{"status":"ERROR","error":…}` to the fallback path
  `build/run/sim/sim-error.json`. The script reads that file as the report when `out` is absent.
- If the request is good, write the first report (`status: RUNNING`) to `out` right away, before the world loads.
- Any failure before `SERVER_STARTED`, such as a bad scenario file or an assertion parse error, is stored. A `SERVER_STARTED` hook then writes ERROR and halts at once.
- `SERVER_STOPPED` rewrites the report with `clean_shutdown: true` (keeping the status).

`days = 0` is a smoke run: boot, locate, setup, baseline, then halt with status `PASS` without evaluating assertions (~40 s).
Use it while building. `days = 0` together with `--assert` is a usage error (exit 64), so no assertion can pass silently.

**Stub self-test in `verify.sh --fast`:** `scripts/test-simulate.sh` runs `simulate.sh` with `SIM_GRADLE_CMD` pointing at
`scripts/testdata/fake-sim.sh`. That fake writes a canned report chosen by an env var (PASS, FAIL, ERROR, RUNNING, PASS without
clean_shutdown, PASS with 4 of 5 days, PASS plus a crash-report file, no report, exit 1, sleep past `SIM_TIMEOUT_SECONDS=5`).
The test checks the exit code for each case (0,1,2,2,2,2,2,2,2,2) and that `--reload-at` makes two phases. `verify.sh` gets the step
"Layer 3 script self-test (stubbed server)", which runs `bash -n scripts/simulate.sh` and then this test (a few seconds).
This keeps the exit-code contract under the definition of done, even though the real L3 runs are manual.

### 3.8 Measuring village-logic ms/tick when there is barely any logic

Add the hook that all later per-tick mod work reports into, and time it now. Two kinds of work have to be counted:
(a) village-wide systems (validation, needs, wages), which run once per server tick, and (b) worker behaviour (M7+), which runs
**inside entity ticks** (brain behaviours or goals), not at the end of the tick. So the timer adds up **sections** during the tick
and records one total per tick:

```java
// core (pure)
public final class TickTimer {                 // per-day samples of nanoseconds, one sample per server tick
    public void add(long nanos);               // accumulate into the current tick (IAE if < 0)
    public void commitTick();                  // record the accumulated sum as one sample (0 is a valid sample) and clear it
    public TickStats snapshot();               // mean/p95/max in ms; p95 = nearest-rank on the sorted samples; empty → all 0
    public TickStats snapshotAndReset();       // also clears any uncommitted sum
}   // stores samples in a growable long[] (24000/day = 192 KB). Sorting at day end is cheap. Server thread only.

// main glue: dev.villageheart.world
public interface VillageSystem { void tick(MinecraftServer server, VillageState village); }
public final class VillageSystems {            // ordered registry; M5+ register validation, needs, wages …
    public static Registration register(String id, VillageSystem s);   // Registration implements AutoCloseable (unregisters); duplicate id → IAE
    static void tickAll(MinecraftServer server); // no-op when there is no claim
}
public final class VillageTicker {             // registered in VillageHeart.onInitialize on ServerTickEvents.END_SERVER_TICK
    public static final TickTimer TIMER = new TickTimer();
    /** For mod work outside VillageSystems (worker behaviours inside entity ticks): try (var t = VillageTicker.section()) { … } */
    public static Section section();           // Section implements AutoCloseable; close() adds the elapsed nanos to TIMER
    static void onEndTick(MinecraftServer s) { try (var t = section()) { VillageSystems.tickAll(s); } TIMER.commitTick(); }
}
```

- **Rule for later milestones** (written into TESTING.md): all mod per-tick work runs either in a `VillageSystem` or inside a
  `VillageTicker.section()`. A separate tick listener, or behaviour code outside a section, escapes the budget measurement.
  Entity ticks run before `END_SERVER_TICK` in the same server tick, so sections opened there land in the same sample.
  The harness's own work (collector, actions, player drain, report writing) is **not** inside the timer.
  The spike shows why: its dummy hook also timed its own setup and showed a 270 ms max on that tick.
- `VillageTicker` registers before the harness's listener, and Fabric events fire in registration order. The harness only reads
  `TIMER`, so the order does not change what is measured.
- In M2 the measured mean is ~0.0003 ms (two `nanoTime` calls plus the empty loop; the spike measured 0.22–0.35 µs).
  The `bare` scenario asserts `village_ms.mean < 1 on every day` as a guard for the budget. GameTests T-L2-1 (a system) and T-L2-1b
  (a section opened inside a GameTest tick callback, i.e. not in END_SERVER_TICK) prove the hook measures real work.
- Add `dev.villageheart.core.Balance` with `CLAIM_RADIUS = 80` *(tunable, DESIGN §1)*. It is the start of the one balance class from DESIGN §12.

## 6. Risks, unknowns and out of scope

**Risks** (highest first):
1. **Run time and variance.** ~50 s per day now. Later scenarios, with 12–20 villagers and mod workers, may be 2–3× slower, and the 30-day `full`
   run could pass an hour. The cures can come later: lower `view-distance`/`simulation-distance` to 4, `/gamerule doMobSpawning`
   per scenario, or `doDaylightCycle`. Villager AI is not seeded, so two runs differ. Assertions must allow slack (`- 1` as in the roadmap).
   The verifier may see `bare` fail if a zombie siege kills 2 villagers. If that happens, report it: do **not** loosen the assertion
   silently (CLAUDE.md rule 4). The fix would be a scenario-level `{"action":"command","command":"gamerule doInsomnia false"}` or similar, with the reason given.
2. **The fake player's packets leak memory** over long runs (§3.3). Mitigation: drain plus the `heap_used_mb` metric. A 30-day run with `-Xmx3G` is the real test (M26).
3. **The seed depends on the Minecraft version.** A worldgen change in a future MC update moves or removes the village. The harness fails loudly
   ("no plains village" / "no bell"), and the positions are recorded in every report. The village bounds come from the POI, never from structure bounds (the spike crashed on those).
4. **A Gradle/Loom upgrade could change the run config DSL or task name.** Mitigation: `simulate.sh` checks that the report exists and has the right number of days.
5. **The Fabric event order** between `VillageTicker` and the harness is assumed (registration order). Only the reading of `TIMER` depends on it, not the measurement.
6. **`setChunkForced` blocks the first tick for ~7 s** (it generates 81 chunks). This is harmless, but it is excluded from `village_ms` and from day 1 `wall_seconds`, because both are reset at G0 (§3.4).
7. **Process hygiene.** `setsid`, the process-group kill and `flock` are new to this repo. If they misbehave, a leftover server holds `session.lock`
   and the next run fails with ERROR (not a false PASS). `test-simulate.sh` checks that no stub process is left.
8. **Vanilla's watchdog** (`max-tick-time=60000`) could kill a legitimately slow tick later (a huge build step in M20). This shows up as an
   ERROR with a crash report. Raise the value per run if it ever happens, but never disable it: it is the hang detector.

**Out of scope for M2:**
- The `starter`/`defended`/`raid`/`full` scenarios (M11, M18, M25, M26), and their action types (`structure`, `stock`, `hire`, `raid`) and assertion functions (`streak`, `delta`, `ratio`).
- Running L3 in CI or in `verify.sh` (roadmap: not by default). A manual GitHub workflow can come with M26.
- Real values for employed, buildings, stockpile and food (filled in by M5/M6/M7/M11 through the collector table in §3.6).
- Multi-player sessions and the 60-day soak (release gate). M2 already reports `world.save_bytes` and `server.heap_used_mb` for the soak.
  Counting `villageheart` ERROR log lines is left for the soak milestone (a grep of the log in `simulate.sh` will do).
- `ReportCompare` / `--compare` (M13's "beats the M11 baseline", and the release gate's "same trend after a reload").

## 8. Critique addressed

A fresh critic (given only this plan and the roadmap) returned 16 findings. All were taken on board:

| # | Finding | Change |
|---|---|---|
| 1 | A Gradle failure or timeout leaked through as exit 1/124 | §3.7: any Gradle `rc ≠ 0` → exit 2. The report only decides when rc is 0. No `set -e` |
| 2 | Orphaned daemon/server JVMs after a timeout; two runs sharing the dir | `setsid` + `timeout -k 30` + a process-group kill in `trap`, plus `flock` on `build/run/sim/.lock` |
| 3 | A harness that never starts, or a hang, burns the full timeout | Early `RUNNING` report in `onInitialize`, the fallback `sim-error.json`, early failures halt in `SERVER_STARTED`, the script's 180 s start check and stall check (heartbeat every 6000 ticks), and vanilla's watchdog via `max-tick-time` |
| 4 | A crash after PASS (while saving) still gives exit 0 | `clean_shutdown` is written in `SERVER_STOPPED` and required. Any crash report → exit 2 |
| 5 | Actions at day boundaries and on resume run twice or never; `==` triggers | Pure `ActionSchedule` + `SimClock` with `>=`, a fixed tick order (record → actions → write → finish), `actions_done` saved for resume, and L1 tests for the boundary and resume cases |
| 6 | Grammar contradictions (`from day`, `@day1`, `1..3` lexing, FUNC/@ mixing, empty scopes) | §3.5 grammar rewritten: `from day N` needs no `on`; `@day1` only; NUMBER/INT lexing defined; nested FUNCs and `@` inside a FUNC rejected; empty scope → FAIL. Tests added |
| 7 | CamelCase `getMsgId` causes; double counting on zombie conversion; difficulty easy; no mob total | Damage-type registry key; dedupe by UUID with conversion replacing the cause (T-L2-4); `difficulty=normal`, recorded in the report; `deaths.mobs` |

| 9 | The timeout and real-crash paths are untested; `--days` typo | `crash`/`hang` self-test actions and scenarios, `SIM_TIMEOUT_SECONDS`, `SIM_GRADLE_CMD` + `test-simulate.sh` in `verify.sh --fast`. T-L3-5 rewritten |
| 10 | Build-order steps not checked by `--fast` | §4 preamble: `runGameTest` compiles the gametest set, the stub test joins `--fast`, and steps 6–9 name a required real run |
