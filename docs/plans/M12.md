## 1. Goal

The village has a purse. Residents and above put emeralds into it by right-clicking the Heart with emeralds in hand (or with the
"Deposit all" button on the Heart screen); only the Owner can take emeralds out, from the Overview tab. Every dawn each worker is
paid 1 / 1 / 2 emeralds (level 1 / 2 / 3). When the purse is short, workers are paid in hiring order and the rest go on strike for
that day: they stop working, the Overview shows a red strike alert, and a deposit pays them at once so they go back to work. Unpaid
wages are never owed later. The Overview also shows tomorrow's wage bill and warns when the treasury cannot cover it.

### 3.2 Decisions

1. **Deposit = right-click the Heart with emeralds in the main hand, plus a "Deposit all" button on the Overview tab.** Right-click is the
   physical, obvious act ("emeralds deposited at the Heart", DESIGN §6) and costs one override; the button exists because the screen is
   where the player sees a strike and the emeralds are usually in the inventory, not the hand. **Withdraw = Owner-only buttons on the
   Overview** ("Withdraw 1", "Withdraw 64"): withdrawing has no physical gesture, and buttons reuse M8's validated action path (rate limit,
   open menu, epoch, rank re-read). No chest/slot GUI: M8's menu has zero slots and every write is a validated C2S action.
   - `VillageHeartBlock.useItemOn(ItemStack, BlockState, Level, BlockPos, Player, InteractionHand, BlockHitResult)` **[verified signature]**:
     if the stack is not an emerald (`stack.is(Items.EMERALD)`) or the hand is not `MAIN_HAND` → `InteractionResult.TRY_WITH_EMPTY_HAND`
     **[verified constant]**, so vanilla falls through to M8's `useWithoutItem` and the screen opens as before (verified in
     `ServerPlayerGameMode.useItemOn` bytecode: a `TryEmptyHandInteraction` result with `MAIN_HAND` calls `BlockState.useWithoutItem`).
     Emeralds in the main hand: client returns `SUCCESS` (hand swings); server runs `Treasury.depositFromHand` (3.6) and returns `SUCCESS`
     whether it was allowed or not (a refused Visitor gets the action-bar message, no screen). Not the claimed Heart → `TRY_WITH_EMPTY_HAND`
     (M8 then says "This Heart does not hold a village"). Sneaking with an item skips the block entirely (vanilla: `isSecondaryUseActive()`
     with a non-empty hand skips `useItemOn` and `useWithoutItem` **[verified bytecode]**), so sneak-click does nothing: documented.
   - The **whole held stack** is deposited (clamped so the treasury stays ≤ `Integer.MAX_VALUE`; the rest stays in the hand).
   - **Creative players pay too**: the stack is shrunk with `stack.shrink(n)` even when `hasInfiniteMaterials()` (vanilla `consume` would
     not), so creative mode cannot mint treasury. The sim owner is creative; it fills the treasury by command (3.8).
   - Any emerald `ItemStack` counts (a renamed emerald loses its name in the treasury, which stores a count): documented.
2. **Ranks.** New permissions `DEPOSIT_TREASURY` (Owner, Steward, Resident; DESIGN §2) and `WITHDRAW_TREASURY` (**Owner only**).
   M8's `Permissions.allows` returns true for Steward on everything, so M12 rewrites the Steward case as an explicit list
   (everything except `WITHDRAW_TREASURY`) and `PermissionsTest` covers the full rank × permission matrix. Everyone (Visitors too) sees
   treasury, wage bill and the strike alert: they are Overview data (DESIGN §10, §2 "Visitor: view the Overview tab").
3. **The dawn event: a shared day clock, no catch-up.** `core.time.DailyClock(int eventTick)` with `dayIndex(dayTime) = floorDiv(dayTime, 24000)`,
   `due(dayTime, lastDay) = phase(dayTime) >= eventTick && dayIndex != lastDay`, `initialLastDay(dayTime)` (= `dayIndex` if `phase >= eventTick`,
   else `dayIndex - 1`). M11's `DinnerClock` becomes `DailyClock(Balance.DINNER_TICK)` (its tests stay unchanged and green: a pure refactor
   in step 1). Wages use `DailyClock(Balance.WAGE_TICK = 0)`, so `due` is simply "the day index changed": the first tick of a new day, which
   is also where a night skipped by sleeping lands (vanilla sets the time to the next multiple of 24000). Same rules as dinner:
   - `!=`, not `>`: `/time set 1000` from day 5 jumps back to day index 0 and still pays wages once.
   - A jump over several days (`/time add 72000`) pays **once** (one run, today's wages), never once per skipped day.
   - Only the Heart's level's `getDayTime()` **[verified]**, and only while `level.isLoaded(heart)` **[verified]** (DESIGN §6). When the Heart
     chunk loads again on a later day, wages run once on that first tick, whatever the time of day.
   - `last_wage_day` is saved next to M11's `last_dinner_day`. Absent (a new claim, a pre-M12 save) → initialised on the first tick to
     `initialLastDay` = today, so claiming never charges at once.
   - `advance_time` off (vanilla `doDaylightCycle`): the day index never changes, so nobody is paid or strikes. Documented.
   - Ordering inside the dawn tick: wages first, then the **dawn listeners** (`VillageDawn.register(id, DawnListener)`, empty in M12) so
     M14 (tier goals at dawn, "treasury ≥ 32 at some dawn") and M23 (breeding at dawn) use the same event and the same no-catch-up rule.
     Each listener gets `(server, village, day, PayResult)`.
4. **Who is paid, with what level.** Every registered worker (`VillageState.workers()`, hiring order), loaded or not: a worker is employed
   whether or not its chunk is loaded, and the bill must be computable while it is away (the Overview shows it). Its level comes from a
   new mirror field `WorkerRecord.level` (codec key `level`, optional, default 1): `Workers.hire` writes 1, `WorkerSystem.tick` (every 20 ticks)
   copies a loaded worker's `WorkerData.level` into its record when they differ, and `Workers.setLevel(server, villager, level)` (added
   here, used by M15) writes both at once. Unloaded workers are paid at their last known level. A 4-argument `WorkerRecord` constructor
   (level 1) keeps every M7-M11 call site compiling unchanged.
5. **The pay rule** (`core.economy.PayRun`, pure). Wage by level `Balance.WAGES = {1, 1, 2}` (tunable; level < 1 reads as 1, level > 3 as 3).
   Walk the workers in hiring order; a worker whose wage is ≤ what is left is paid and the treasury drops by that wage; otherwise it is
   **unpaid** and the walk **continues** (a later, cheaper worker can still be paid). "Paid in hiring order" (DESIGN §6) is the priority
   order; skipping on instead of stopping at the first unaffordable worker matters only once level-3 workers (wage 2) exist, and it never
   leaves a worker on strike while an emerald that could pay it sits in the treasury. The roadmap case (3 × level 1, 2 emeralds → first two
   paid, third strikes, 0 left) is the same under either reading. Result `PayResult(day, treasuryBefore, treasuryAfter, spent, bill,
   paid: List<UUID>, unpaid: List<UUID>)`.
6. **Strike = in today's unpaid set, until paid.** `core.economy.Payroll(long lastWageDay, List<UUID> unpaid)` (hiring order, saved).
   - At dawn the set is **replaced** by that run's unpaid list: owed wages are not carried over (DESIGN §4/§6), so yesterday's strikers cost
     only today's wage, like everyone else.
   - **A deposit settles strikers at once** (`Payroll.settle`): after every treasury deposit (right-click, button, command, M22 income)
     the unpaid workers are paid today's wage in hiring order by the same rule as 5, and leave the set. This reconciles DESIGN §4 ("on strike
     until the treasury can pay") with §6 ("the rest strike for the day"): a strike lasts the rest of the day unless the player pays. Settling
     never pays anyone twice in a day (only members of the unpaid set are paid) and never pays past days.
   - A worker hired after today's wage run is not in the set, so it works its first (partial) day unpaid but not on strike (`Needs.DEFAULT`
     has `paid = true`). Its first wage is at the next dawn.
   - A fired worker stays in the set until the next dawn: fire-and-rehire on the same day does not end a strike (no free day by firing).
     Records that are no longer workers are ignored when the set is read and dropped at the next dawn.
   - `PaidSource` (M11) becomes `record -> !payroll.unpaid().contains(record.villager())`.
7. **Strike → no work.** `needs.paid = false` makes `Needs.speed()` 0 (M11), so `WorkSpeed.multiplier` is 0 and `WorkClock` never completes a
   unit. The speed-0 planner row (M11, in M9's and M10's planners) idles the worker at its building and sets the status: **`ON_STRIKE`** when
   `!needs.paid`, else `TOO_HUNGRY`. Precedence in `Workers.status`: `WORKPLACE_INVALID > ON_STRIKE > TOO_HUNGRY > job statuses > storage statuses
   > OK` (a strike first, because a deposit ends it at once). Deposit trips still run (a striker carries what it already holds to Storage, as
   M11 allows for the hungry); felling, harvesting, planting, collecting and fetching do not. `Workers.status` reads the strike from the
   payroll, not from the entity, so it is right for unloaded workers too. Lang `status.villageheart.on_strike` = "On strike: unpaid".
8. **The needs mirror is immediate.** Right after a wage run or a settle, the system calls M11's needs mirror for the loaded workers whose
   `paid` changed (not only on the next 100-tick refresh), so a striker stops at the dawn tick and a settled worker resumes on the deposit
   tick.
9. **Feedback.** Wage run: one INFO log line `[wages] day D: paid P/N, spent S, treasury B -> A, strikers [uuid…]`. When anyone is unpaid, every
   online Owner/Steward gets one chat line: "%s workers are on strike: the treasury could not pay their wages" (singular variant). Deposit
   and withdraw: an action-bar line to the actor ("Deposited %s emeralds. Treasury: %s"; with a settle: "… Paid %s striking workers.") and an
   INFO log line with the player name (an audit trail for multiplayer; a ledger UI is out of scope).
10. **Test isolation.** M11's `VillageTestSupport.reset` defaults (`forceDefaultNeeds = true`, `dinnerEnabled = false`) protect older tests from
    hunger. M12 adds `NeedsTestHooks.wagesEnabled` (reset → `false`): the wage system skips its dawn run, so no older GameTest ever strikes or
    loses treasury (their treasury is 0 and every crossed dawn would otherwise strike all their workers). `forceDefaultNeeds` changes meaning
    slightly: it forces `fed`, `hungryDays` and `housed`, but `paid` always comes from `PaidSource` (with wages off the unpaid set stays empty,
    so older tests still see `paid = true`). M12's own tests (environment prefix `wages_`) set `wagesEnabled = true` after `begin` and keep
    the fed/housed override, so a paid lumberjack works at full pace without a House. Main code reads the flag through M11's
    `NeedsOverride` static (null/defaults in production: wages on). L3 and L4 have no hooks: wages run.
11. **Overview numbers.** Wage bill = `PayRun.bill(levels of current workers)` = what the next dawn would cost (DESIGN §10 "tomorrow's wage
    bill"). Alerts (core, appended through `VillageFacts.extraAlerts`): `STRIKE` (danger) "1 worker is on strike: deposit emeralds at the
    Heart" / "%s workers are on strike: …" when the current unpaid set has a registered worker; `TREASURY_SHORT` (warning) "Treasury short:
    %s of %s emeralds for tomorrow's wages" when `0 < bill` and `treasury < bill` (a warning before the strike happens). The wage line is red
    (`0xFFFF5555`) when the treasury is short. On the Villagers tab a striker's activity is `ON_STRIKE` ("On strike") and its emerald icon is
    slashed (M8 already draws `NeedsFlags.paid`).

### 3.4 Glue: wages (`dev.villageheart.economy`)

- `WageSystem implements VillageSystem` (registered as `villageheart:wages` **after** M11's `villageheart:needs`, so a dawn tick's mirror
  sees the new payroll): each tick, one `getDayTime()` read of the Heart's level; `WAGE_CLOCK.due(...)` and `level.isLoaded(heart)` →
  `runDawn`. Skips when `NeedsOverride` says wages are off (tests, 3.2 #10).
- `runDawn(server, village, day)`: payees = `village.workers()` → `Payee(villager, record.level())`; `PayRun.run`; in **one**
  `VillageSavedData.update` the treasury becomes `treasuryAfter` and the payroll `afterDawn(result)` (same tick, same file, one `setDirty`);
  then the needs mirror (3.2 #8), the log line and chat (3.2 #9), `WageStats.record(result)` (L3), `VillageDawn.fire(...)`.
- `Treasury` (the only writer of the treasury besides wages and release):
  - `deposit(server, int n, @Nullable ServerPlayer by) : DepositResult(accepted, settledWorkers, treasuryAfter)`: clamp with `depositable`,
    add, then `Payroll.settle` against today's payees, mirror, log. `VillageClaims.depositTreasury` (M1, used by tests) delegates to it.
  - `depositFromHand(ServerPlayer, InteractionHand)`: rank check (`DEPOSIT_TREASURY`), stack shrink by the accepted count, action-bar reply
    (`message.villageheart.treasury.deposited`, `…deposited_settled`, `…not_allowed` "Only Residents and above can deposit emeralds",
    `…full` when nothing fits).
  - `depositInventory(ServerPlayer)`: counts and removes emeralds with `Inventory.clearOrCountMatchingItems(s -> s.is(Items.EMERALD), max,
    player.inventoryMenu.getCraftSlots())` **[verified signature]** (it removes up to `max` and returns the count; `max = depositable(...)`),
    then `deposit`. Nothing to deposit → `…no_emeralds`.
  - `withdraw(ServerPlayer, int asked)`: `withdrawable` (0 → `…empty`), `withdrawTreasury`, then
    `player.getInventory().placeItemBackInInventory(new ItemStack(Items.EMERALD, n))` **[verified]** (adds, and drops what does not fit at the
    player). No settle on withdraw (it can only make things worse, and strikes are already decided).
- `WorkerSystem.tick` (M7) gains the level mirror (3.2 #4). `Workers.hire` writes `level 1`; `Workers.setLevel` writes attachment and record.
- `Workers.status` (M7/M9/M11) gains `ON_STRIKE` from `VillageClaims.data(server).payroll().onStrike(...)` with the 3.2 #7 precedence.
- `PaidSource` (M11) → `PayrollPaidSource` reading the saved payroll (one `HashSet` built per refresh, not per worker).
- `Wages.resetClock(server)`: `last_wage_day = dayIndex(now)` (the harness calls it right after its `setDayTime(0)`, next to M11's
  `Dinner.resetClock`, so sim day 1 has no wage run and the first one is at the dawn of sim day 2).
- Release (`VillageClaims.releaseAt`) and `clear()`: the payroll is part of the claim and goes with it (`WorldClaim.releaseAt` resets it like
  `reservedJobBlocks`), so a new village starts with no strikers and a fresh clock. The treasury still drops as items (M1, unchanged).

## 6. Risks and unknowns

1. **Three unmerged dependencies (top risk).** M8 (screen), M9 (lumberjack, watcher) and M11 (needs mirror, `PaidSource`, test hooks, clock)
   are plans or half-built code. M12's rules are written against their *planned* names (3.1). Mitigation: steps 1-2 need none of them; every
   assumption names its fallback; the builder re-checks A1-A3 against `dev` before steps 3, 5 and 6 and records differences as deviations.
2. **Older GameTests start striking.** Every GameTest that hires and crosses a dawn would strike with treasury 0. Mitigation: wages are off in
   `reset` and the switch lands in the same step as the wage system (3.2 #10); a full `verify.sh` after step 3 proves it. Same for the L3
   `starter` scenario (3.8), which must be re-run by hand.
3. **T-L2-1 is long and depends on AI.** A full working day (≈ 11 000 ticks) with two lumberjacks walking. The negative claim (C chops 0) is
   only meaningful with the control (A chops ≥ 1); if A fails to chop (pathing), the test fails loudly rather than passing vacuously.
   Measured ticks are logged (`[m12] …`) and copied into PROGRESS so slack is measured.
4. **Payroll in the claim vs. treasury in `VillageState`.** They live in the same saved data and are written in the same `update`, so they
   cannot disagree after a crash between two saves (one file). If M11 puts `last_dinner_day` somewhere else, the payroll follows it.
5. **Level mirror lag.** `WorkerRecord.level` trails the attachment by ≤ 20 ticks for loaded workers; M15 must use `Workers.setLevel` (stated in
   its future plan's assumptions). A dawn inside that window pays the old level once: harmless.
6. **Creative deposits shrinking stacks** may look odd to a creative player (vanilla creative block use does not consume). Chosen so creative
   cannot mint money; documented.
7. **Overview space.** The treasury bar takes 24 px from M8's 183 px body; M14's goal checklist later needs room too. The L4 layout assertion
   catches overflow; if it fails, the alerts cap drops from 5 to 4 (a deviation, stated).

**Out of scope** (later milestones or post-v1): levels and XP (M15; M12 only reads them); merchant income (M22, which calls `Treasury.deposit`);
tier goals reading the treasury at dawn (M14, via `VillageDawn`); breeding at dawn (M23, via `VillageDawn`); a Ranks tab and ownership transfer
(M24; M24's "only the Owner can withdraw" L2 reuses T-L2-3); a treasury ledger/history UI; strike visuals in the world (angry-villager particles,
strikers gathering at the bell); back pay or debt; per-worker wage settings; withdrawing to a chest; non-emerald currencies.
