## 1. Goal

Right-clicking the claimed Village Heart opens a tabbed screen. **Overview** shows the village (title, tier, next tier,
population and beds, workers and slots, food days left, treasury, wage bill placeholder, alerts). **Villagers** lists the
workers and the unemployed adults with job, level, XP bar, needs icons and current activity, and lets a Steward or the Owner
assign a job or fire a worker. **Buildings** lists every marker with type, position, valid/invalid with the reasons and worker
slots used. **Stockpile** shows item totals over Storage, the food nutrition total and the storage alert. The server checks
the rank on every action, and Visitors see the Overview tab only (they are not even sent the other tabs' data).

### 3.2 How the screen opens: `ExtendedScreenHandlerType` (a menu with no slots)

Options considered:
- **Plain `MenuType` + empty first frame**: no opening data, the screen would be blank until the first refresh packet.
- **Custom payload only** (S2C "open" payload, client calls `setScreen`): we would re-implement what the menu system gives for
  free: the container id, closing on distance (`stillValid`), closing on Escape/disconnect, one open screen per player.
- **Chosen: Fabric `ExtendedScreenHandlerType<HeartMenu, HeartOpenData>`** **[verified, fabric-screen-handler-api-v1]**. The
  opening data (the first snapshot) travels with the open packet, so the screen is complete on its first frame; vanilla
  owns the lifecycle. `HeartMenu extends AbstractContainerMenu` with **zero slots**: read-mostly, all writes go through our
  own C2S payloads, never through slot clicks.

Facts this relies on **[verified]**:
- `ServerPlayer.tick()` calls `containerMenu.broadcastChanges()` every tick, then closes the menu when
  `!containerMenu.stillValid(this)` (`closeContainer()`, which sends `ClientboundContainerClosePacket`).
- `ServerPlayer.openMenu(MenuProvider)` closes any other menu, creates ours with the next container id; Fabric's
  `ServerPlayerMixin` replaces the vanilla open packet with its `OpenScreenPayload` carrying `getScreenOpeningData(player)`,
  which it calls **after** `createMenu` (so the factory can read the new menu). An `ExtendedScreenHandlerType` opened with a
  non-extended provider throws `IllegalArgumentException`.
- `ExtendedScreenHandlerType(ExtendedFactory<T, D>, StreamCodec<? super RegistryFriendlyByteBuf, D>)`;
  `MenuScreens.register(MenuType, ScreenConstructor<M, U extends Screen & MenuAccess<M>>)` is public, so the screen can be a
  plain `Screen implements MenuAccess<HeartMenu>` (no slot rendering, no inventory background).
- `AbstractContainerMenu.stillValid(ContainerLevelAccess, Player, Block)` = block still there and
  `player.isWithinBlockInteractionRange(pos, 4.0)`. On the client `ContainerLevelAccess.NULL` evaluates to true.
- **`Screen.isPauseScreen()` defaults to true.** `AbstractContainerScreen` overrides it to false. `HeartScreen` must override
  it to false too, or the integrated server pauses in singleplayer and no refresh ever arrives (and the L4 test hangs).
- `LocalPlayer.closeContainer()` sends `ServerboundContainerClosePacket(containerMenu.containerId)` and closes the screen;
  `ClientPacketListener.handleContainerClose` calls `clientSideCloseContainer()` (screen closed by the server).

Registration (`dev.villageheart.heart.ModMenus`, common init):
```java
public static final ExtendedScreenHandlerType<HeartMenu, HeartOpenData> HEART = Registry.register(BuiltInRegistries.MENU,
        Identifier.fromNamespaceAndPath(VillageHeart.MOD_ID, "heart"),
        new ExtendedScreenHandlerType<>(HeartMenu::new, HeartOpenData.STREAM_CODEC));
```
`HeartOpenData(BlockPos heart, HeartSnapshot snapshot)`.

Opening: `VillageHeartBlock.useWithoutItem(BlockState, Level, BlockPos, Player, BlockHitResult)` **[verified signature]**:
on the server, if the claim's Heart is at this position (`VillageClaims.current(server).filter(v -> v.isHeartAt(locate(level, pos)))`)
call `HeartScreens.open(serverPlayer, level, pos)`; otherwise send the action-bar message
`message.villageheart.heart.not_this_village` ("This Heart does not hold a village."). Return `InteractionResult.SUCCESS`
on both sides (the hand swings; same as chests). `useItemOn` is **not** overridden, so holding an item still opens the screen
(vanilla falls through to `useWithoutItem` unless sneaking with an item), and M12 can later override `useItemOn` for emerald deposits.
Every rank may open it (Visitors see Overview).

`HeartMenu` (common, `dev.villageheart.heart`):
- Client constructor `(int id, Inventory inv, HeartOpenData data)`; server constructor adds `ServerLevel level, BlockPos heart, int epoch`.
- `stillValid(player)`: server side `epoch == VillageClaims.data(server).epoch()` **and** `AbstractContainerMenu.stillValid(ContainerLevelAccess.create(level, heart), player, ModBlocks.VILLAGE_HEART)`.
  So walking away (~8.5 blocks), breaking the Heart, or a release/re-claim closes the screen within one tick.
- `quickMoveStack` returns `ItemStack.EMPTY`; no slots, so vanilla slot sync sends nothing.
- `broadcastChanges()` (server): `super.broadcastChanges()`, then inside `try (var t = VillageTicker.section())`: when
  `dirty || gameTime - lastRefresh >= Balance.HEART_REFRESH_TICKS (20)`, build this viewer's snapshot (3.4) and send
  `HeartSnapshotPayload(containerId, snapshot)` **only if it differs** (`!snapshot.equals(lastSent)`). `dirty` is set after an action.
- Client side it holds the latest `HeartSnapshot` plus a `version` counter that the screen watches.

### 3.3 Networking: payloads and codecs (`dev.villageheart.heart.net`)

All payloads use the 1.21.11 API **[verified]**: `record X(...) implements CustomPacketPayload`,
`static final CustomPacketPayload.Type<X> TYPE = new CustomPacketPayload.Type<>(Identifier.fromNamespaceAndPath("villageheart", "..."))`,
`StreamCodec` built with `StreamCodec.composite` (up to 12 fields), `ByteBufCodecs.VAR_INT/VAR_LONG/BOOL/stringUtf8(n)`,
`ByteBufCodecs.list(max)`/`collection`, `ByteBufCodecs.optional`, `UUIDUtil.STREAM_CODEC`, `BlockPos.STREAM_CODEC`. Every codec is a
`StreamCodec<ByteBuf, T>` (no registries needed: items travel as id strings), which `PayloadTypeRegistry.register(Type, StreamCodec<? super B, T>)`
accepts. Registration in `HeartNetwork.register()` (common init): `PayloadTypeRegistry.playS2C().register(...)` /
`playC2S().register(...)`, then `ServerPlayNetworking.registerGlobalReceiver(TYPE, handler)`; the client registers its
receivers in `VillageHeartClient` with `ClientPlayNetworking.registerGlobalReceiver` (handler runs on the client thread; the
server handler runs on the server thread **[verified: Fabric `AbstractChanneledNetworkAddon.handle` throws
`RunningOnDifferentThreadException` off-thread and the mixin re-schedules on `server.packetProcessor()`]**).

| Payload | Dir | Fields | Limits |
|---|---|---|---|
| `HeartSnapshotPayload` | S2C | `int containerId, HeartSnapshot snapshot` | worst case ≈ 270 KB, tested < 512 KiB (vanilla S2C cap 1 MiB **[verified `ClientboundCustomPayloadPacket.MAX_PAYLOAD_SIZE`]**) |
| `HeartActionResultPayload` | S2C | `int containerId, boolean ok, String key, String fallback, List<String> args` | key 128, fallback 256, ≤ 4 args of 64 |
| `AssignJobPayload` | C2S | `int containerId, UUID villager, String jobId, Optional<BlockPos> building` | jobId ≤ 32 chars (C2S cap 32767 **[verified]**) |
| `FireWorkerPayload` | C2S | `int containerId, UUID villager` | — |
| `RecheckBuildingPayload` | C2S | `int containerId, BlockPos marker` | — |

Decoding a string longer than its limit throws `DecoderException` (vanilla `stringUtf8(n)`), so an oversized C2S payload
kicks the sender (vanilla behaviour for malformed packets); the server never sees it. M18 adds `SetGuardShiftPayload` the same way.

**Refresh and size.** One full snapshot per viewer at most once per second, only when it changed (no deltas: a typical
village is 2-6 KiB; one viewer at 1 Hz is nothing). Snapshot caps (`core.heart.HeartLimits`, all overflow counted and shown as
"+N more"): villagers 100 rows, buildings 128 rows, reasons 4 per building, stockpile 256 item kinds, every text 120 chars,
names 32 chars, job choices 9, alerts 5 (+N more). **`stringUtf8(n)` limits characters, not bytes: a character is up to 3
bytes on the wire.** Real bound with those caps: buildings 128 x 4 reasons x (key <= 64 + fallback 120 x 3) ≈ 217 KB, villagers
100 x ~250 B ≈ 25 KB, stock 256 x ~80 B ≈ 20 KB, overview < 4 KB: about **270 KB**. Hence reason fallbacks are capped at 120 chars and
4 reasons per row (+N more), and the L1 test fills every string with 3-byte characters ('€') and the longest keys and asserts the
encoded size < **512 KiB** (half the vanilla 1 MiB S2C cap), printing the real number.

### 3.4 The snapshot (pure core, `dev.villageheart.core.heart`)

```java
public record HeartSnapshot(Rank viewerRank, Overview overview, List<VillagerRow> villagers, int moreVillagers,
        List<JobChoice> jobChoices, List<BuildingRow> buildings, int moreBuildings, Stock stock) {}

public record Overview(String ownerName, Tier tier, Optional<Tier> nextTier, List<GoalLine> goals /* empty until M14 */,
        int population, int adults, int babies, int beds, int workers, int workerSlots,
        int foodDaysTenths /* -1 = no villagers */, int treasury, int wageBill /* -1 until M12 */, List<AlertLine> alerts) {}
public record GoalLine(TextLine label, int have, int need, boolean met) {}            // M14 fills it
public record AlertLine(AlertCode code, Severity severity, TextLine text) {}
public enum AlertCode { NO_STORAGE, STORAGE_FULL, INVALID_BUILDINGS, WORKPLACE_INVALID }   // M11 STARVING, M12 STRIKE, M25 RAID append
public record TextLine(String key, String fallback) {}                               // -> Component.translatableWithFallback(key, fallback)

public record VillagerRow(UUID id, String name, String jobId /* "" = none */, String vanillaProfession /* "minecraft:none" etc. */,
        int level, int xp, int xpForNext /* 0 = max */, NeedsFlags needs /* null-free: KNOWN bit */, ActivityKind activity,
        boolean workplaceInvalid, boolean nitwit, boolean hasTraded, boolean loaded) {}
public enum ActivityKind { WORKING, IDLE, GOING_HOME, SLEEPING, RESTING, MEETING, PANICKING, HIDING, AWAY, OTHER }
public record JobChoice(String jobId, int freeSlots, boolean tierLocked) {}

public record BuildingRow(String typeId, int x, int y, int z, RowStatus status, List<TextLine> reasons, int moreReasons,
        DetailKind detail, int detailCount, int workersHere) {}
public enum RowStatus { VALID, INVALID, UNCHECKED, DEFERRED }
public record Stock(List<StockLine> items, int moreKinds, long totalItems, long nutrition, int storages, int unknownStorages,
        int containers, int freeSlots, int slots, StorageAlert alert) {}
public record StockLine(String itemId, long count, int nutritionEach) {}
```

`HeartSnapshotBuilder.build(VillageFacts facts, Rank viewer)` turns plain facts (records filled by the glue, 3.5) into the
snapshot. Rules (all L1):
- **Rank filter**: `Permissions.allows(viewer, VIEW_DETAILS)` false → `villagers`, `buildings`, `stock.items` empty,
  `stock` zeroed, `jobChoices` empty, counts 0. `jobChoices` only when `allows(viewer, HIRE)`. Overview always.
- **Villager order**: workers in hiring order, then unemployed adults (nitwits last) by name, then UUID. Babies are not rows
  (counted in Overview). Cap 100.
- **Names**: the custom name if the villager has one, else `VillagerNames.of(uuid)` (pure, deterministic: two syllable lists,
  index from `uuid.getMostSignificantBits()` / `getLeastSignificantBits()`, e.g. "Bram", "Tilda"). Truncated to 32 chars.
- **XP bar**: `JobLevels.xpForNext(level)` from §4 (level 2 at 100, level 3 at 300; level 3 → 0 = max). Constants
  `Balance.LEVEL_2_XP = 100`, `LEVEL_3_XP = 300` are added by M8 for display only; M15 owns gaining XP and levels.
- **Food days** = `floor(10 * nutrition / (adults * 10 + babies * 5))` tenths (DESIGN §6, children half); population 0 → -1.
  M11 reuses `FoodDays.tenths(...)` and may refine which foods count.
- **Building order**: INVALID first, then UNCHECKED/DEFERRED, then VALID; within a group `BuildingType` enum order, then (x, y, z).
  Reasons are `Reason.translationKey()` + `Reason.message()`, capped at 4 (+N more), fallback cut to 120 chars.
- **Alerts** (in this order): `NO_STORAGE` (warning), `STORAGE_FULL` (warning; text "Storage full: no empty slot in any
  readable Storage", and when `unknownStorages > 0` " (N Storage not checked yet)": this is the BACKLOG M6 note "one readable full
  Storage plus one unknown shows FULL by design, say so"), `INVALID_BUILDINGS` (n > 0, "N buildings need attention"),
  `WORKPLACE_INVALID` (n > 0, "N workers have no valid workplace").
- **Alerts** list capped at 5 lines (+N more), so the Overview never overflows its 183 px body.
- **Stock lines**: summed per item id (`StockSnapshot.totalsBy(StackKey::id)`; variants merged for display), sorted by count
  desc then id, cap 256. `nutritionEach` = the item's default `DataComponents.FOOD` nutrition, 0 when not food **or** in the new item tag
  `#villageheart:not_village_food` (`data/villageheart/tags/item/not_village_food.json`: rotten flesh, spider eye, poisonous potato,
  pufferfish, suspicious stew, chorus fruit; M11 reuses the tag for dinner); `nutrition` = sum over **all** kinds (not only the shown 256).
- `HeartSnapshot` and every part are records holding only `List`/`Optional`/primitives/strings/enums (**no arrays**), so
  `equals` is the refresh dedupe. `HeartMenu.lastSent` starts as the opening snapshot, so the first tick sends no duplicate.

### 3.5 Facts from the world (glue, `dev.villageheart.heart.HeartFacts`)

`HeartFacts.collect(MinecraftServer) : Optional<VillageFacts>` (server thread; never loads chunks):
- `VillageState` from `VillageClaims.current`.
- **Census**: `VillageCensus.of(server, state)` (moved from `SimMetricsCollector.Census` into main glue
  `dev.villageheart.world.VillageCensus`; the collector delegates to it so L3 metrics and the screen count the same way):
  loaded `Villager`s in the claim dimension within the 80 sphere (`ClaimGeometry.inClaim`, M7, which also rejects other
  dimensions), adults and babies. **Population** on the screen = loaded census + recorded workers that are not loaded (so it does
  not drop when a worker's chunk unloads); the tooltip says "Unemployed villagers count only while nearby".
- **Beds** = sum of `verdict.slots()` of VALID Houses (`Buildings.all`, detail HOMES).
- **Workers**: each `WorkerRecord` with its loaded villager (A8), its `WorkerData` (A3), `Workers.status` (A5), activity (A7);
  unloaded workers get `loaded=false`, activity AWAY, level/xp/needs from nothing (row shows "Away").
- **Unemployed adults**: census villagers without the worker attachment, not babies; `nitwit`, `hasTraded`, vanilla profession key.
- **Slots**: `workerSlots` = sum over `JobType` of the site slots (A6); `JobChoice` per job: free slots (`JobSlots.freeSlots`), `tierLocked = job.tier() > state.tier()`.
- **Buildings**: `Buildings.all` with `verdict` (deferred → DEFERRED), detail kind from `BuildingRequirements.of(type).detail()`,
  `workersHere = state.workersAt(marker).size()`.
- **Stock**: `Stockpiles.snapshot(server)`; nutrition from `BuiltInRegistries.ITEM.getValue(Identifier.parse(id)).components().get(DataComponents.FOOD)`.

`HeartFacts.cached(server)` memoises the facts per (server, game time, claim epoch) so N viewers in one tick cost one collect.
`HeartFacts.invalidate()` after every action. Cost target: one collect under 1 ms for 30 villagers, 20 buildings, 32 chests
(stockpile snapshot alone is ~0.3 ms, M6). The census `getEntities` over a 161^3 box is the only new scan; it runs at 1 Hz and
only while someone has the screen open.

### 3.6 Actions and permissions

Core (`dev.villageheart.core.heart`):
```java
public enum Permission { VIEW_OVERVIEW, VIEW_DETAILS, HIRE, FIRE, RECHECK_BUILDING, SET_GUARD_SHIFT /* M18 */ }
public final class Permissions { public static boolean allows(Rank rank, Permission p); }   // M24 extends the matrix
public sealed interface HeartAction permits Assign, Fire, Recheck {                          // M18 adds SetGuardShift
    Permission permission();
    record Assign(UUID villager, String jobId, Optional<HeartLocation> building) ...  // HIRE
    record Fire(UUID villager) ...                                                      // FIRE
    record Recheck(HeartLocation marker) ...                                            // RECHECK_BUILDING
}
public enum Rejection { NOT_OPEN, STALE, NO_VILLAGE, NO_PERMISSION, RATE_LIMITED, UNKNOWN_JOB, VILLAGER_NOT_FOUND, NOT_A_BUILDING }
public final class ActionGate {   // order, first failure wins: RATE_LIMITED, NOT_OPEN, STALE, NO_VILLAGE, NO_PERMISSION
    public static Optional<Rejection> check(boolean allowedByRate, boolean menuOpen, boolean sameEpoch, Optional<VillageState> v,
                                            UUID player, HeartAction a);
}
public final class RateLimiter {  // token bucket per player UUID over game ticks: capacity 8, +1 per 5 ticks (tunable, Balance)
    public boolean tryAcquire(UUID player, long gameTime);
}
```
Matrix (DESIGN §2): Visitor: VIEW_OVERVIEW. Resident: + VIEW_DETAILS. Steward: + HIRE, FIRE, RECHECK_BUILDING, SET_GUARD_SHIFT.
(Recheck is not in the roadmap entry: a cheap extra over the existing `Buildings.request` "check now" hook, kept at Steward so the
matrix stays inside DESIGN §2's "Resident = view".)
Owner: everything. Server operators get no bypass (an op who wants in can be made Steward); single player's player is the Owner anyway.

Glue `HeartActions.handle(ServerPlayer player, int containerId, HeartAction action)` (every C2S receiver calls it):
1. Rate limiter **first** (shared `HeartActions.RATE`, keyed by player UUID; survives reopening the screen), so a flood of
   bad packets costs one map lookup each and cannot fill the log. Entries are dropped on `ServerPlayConnectionEvents.DISCONNECT`;
   the limiter, the facts cache and the WARN throttle are cleared on `ServerLifecycleEvents.SERVER_STOPPING` (the integrated
   server is reused between worlds).
2. `menuOpen` = `player.containerMenu instanceof HeartMenu m && m.containerId == containerId && m.stillValid(player)`.
3. `sameEpoch` = `m.epoch() == VillageClaims.data(server).epoch()`. There is one village per world (DESIGN §2), so the epoch
   identifies it; there is no second village whose cache or menus could mix with this one.
4. Rank re-read from the **current** `VillageState` (a rank change while the screen is open counts at once).
5. Action:
   - Assign: `JobType.byId` (else UNKNOWN_JOB); villager = `heartLevel.getEntity(uuid)` instanceof `Villager` in the **Heart's own
     level** only (else VILLAGER_NOT_FOUND; M7's `ClaimGeometry` also rejects other dimensions); the optional building must be a
     registered building of the village (else NOT_A_BUILDING); `Workers.hire(heartLevel, villager, job, building)`; a
     `Refused(reason)` is reported with `reason.langKey()`. The hire wipes trades deliberately (DESIGN §4): the two-click
     confirmation is client UX only, the server needs no flag.
   - Fire: loaded → `Workers.fire`; not loaded but recorded → `Workers.fireById`; neither → `not_a_worker`.
   - Recheck: the marker (in the Heart's dimension) must be a registered building (else NOT_A_BUILDING) → `Buildings.request(server, loc)`.
6. Reply with `HeartActionResultPayload` (rejections: key `message.villageheart.heart.rejected.<rejection>`; RATE_LIMITED replies
   at most once per second per player); log rejections at DEBUG, NO_PERMISSION at WARN (a normal client never sends it: the buttons
   are hidden) but at most once per player per minute.
7. On success: `HeartFacts.invalidate()`, every open `HeartMenu` marked dirty (they refresh on their next `broadcastChanges`).

S2C sends go through `HeartNetwork.sender` (default `ServerPlayNetworking::send`); GameTests swap in a recorder with
`HeartNetwork.setSenderForTest(...)` and restore it in `done`.

### 3.7 The screen (client, `dev.villageheart.client.heart`)

`HeartScreen extends Screen implements MenuAccess<HeartMenu>`, registered with `MenuScreens.register(ModMenus.HEART, HeartScreen::new)`.
Layout follows vanilla's `StatsScreen` **[verified, 1.21.11]**: `HeaderAndFooterLayout`, `TabManager`, `TabNavigationBar.builder(tabManager, width).addTabs(...)`,
`repositionElements()` sets the tab area below the bar; the footer (33 px) holds the status line and a Done button.
- `isPauseScreen()` → false. `onClose()` → `minecraft.player.closeContainer()`. The inventory key also closes it.
- Tabs: Overview, Villagers, Buildings, Stockpile (labels `gui.villageheart.heart.tab.<name>`). For a Visitor, tabs 2-4 are

## 6. Risks, unknowns, out of scope

**Risks (top first):**
1. **M7 not merged or its API moves** (A1-A12). Mitigation: steps 1-3 are M7-free; `HeartFacts`/`HeartActions` are the only
   M7 importers; T-L2-7 pins every number the screen shows from M7.
2. **427 x 240 is tight.** Long job/activity words or a translated language can overflow. Mitigation: fixed column widths
   from 3.7, ellipsis + the `clippedThisFrame` assertion in L4, tooltips with the full text.
3. **L4 timing**: verdicts, hiring, snapshot refresh (20 ticks) and the client receiving it. Mitigation: poll the client
   snapshot with a bound instead of fixed waits; the NetworkSynchronizer guarantees packets are handled by the end of a tick.
4. **Fabric dispatch of a C2S payload in a GameTest** goes through `handleCustomPayload` on a player whose "client" never sent
   channel registrations. Reading `AbstractChanneledNetworkAddon.handle`, the server only needs its global receiver, but this is
   unproven until step 6. Fallback: call the receiver lambda (`HeartNetwork.receiverForTest(TYPE)`) with the decoded payload.
5. `ByteBufCodecs` static init in plain JUnit (fallback in 5, L1).
6. The census `getEntities` over 161^3 at 1 Hz per open screen: cached per tick, only while open; measured in T-L2-7.

**Out of scope:** Ranks tab (M24), treasury deposit/withdraw (M12; the Overview shows the number only), wage bill (M12),
tier goals (M14), guard shifts (M18; the payload pattern is ready), blueprints on the Buildings tab (M20), reserve settings
(M22), raid/starving/strike alerts (M11/M12/M25), village naming, delta updates, a Heart item-hand shortcut, client config.
Not taken from BACKLOG: M6 `unreadContainers` as unknown (stockpile logic, not the screen).

## 7. Critique addressed

A fresh critique session (given only this plan and the roadmap entry) returned 21 findings. Changes:
- **Payload size (MAJOR):** `stringUtf8` limits characters; bound recomputed with 3-byte characters (≈ 270 KB), reasons cut to 4 x
  120 chars, alerts capped at 5, the L1 size test uses '€' and asserts < 512 KiB.
- **Cross-dimension / foreign targets (BLOCKER as raised):** villagers are looked up in the Heart's level only, preferred building and
  Recheck markers must be registered buildings; new T-L2-13, extra cases in T-L2-2. The "two villages" part of findings 1-2 does not
  apply: one village per world, the epoch identifies it (stated in 3.6).
- **Input API changes in 1.21.9+ (MAJOR):** listed in 3.7 (`KeyEvent`, `MouseButtonEvent`, `setTooltipForNextFrame`, `Identifier`);
  step 7 compiles an empty screen first.
