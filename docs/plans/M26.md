## 1. Goal

The numbers marked *(tunable)* get set from evidence instead of guesses. A new 30-day layer-3 scenario, `full`, plays a whole village with
no player input after setup. It has every building type, 12 villagers, a Hamlet start and a starter kit of stone tools, food and 32
emeralds. The village must reach the Village tier, never be out of food for two days running, never go into debt, and keep its own logic
under 1 ms per tick. That last number is measured in a way that cannot miss mod work. An agent then follows a written procedure: run, read
the numbers, change a small set of `Balance` values, and repeat until the gates and the balance targets hold. Every before/after is recorded
in PROGRESS.md, and no test or assertion is changed to make a run pass.

### 2.2 How village-logic time is measured today, and its two defects

`VillageTicker.onEndTick` (an `END_SERVER_TICK` listener) opens a section around `VillageSystems.tickAll` and then calls `TIMER.commitTick()`.
Worker behaviours (`UpdateWorkerActivity`, `GoToJobBlock`, `StandAtJobBlock`, `DepositTrip`, `*Work` of every job) and some event paths
(`BuildingSystem.useMarker`, `HeartMenu`, `BuildersTableMenu`, `WorkerSystem.processLoaded`, the reservation pass) open their own sections.

1. **Double counting.** `Section` is not reentrant. A section opened inside another is added twice: `BuildSystem.tick` opens one inside
   `tickAll`'s, and any system written the same way later does too. The reported number is too high. That is safe for the gate but wrong
   for tuning. Work done by listeners that run after `VillageTicker`'s listener is counted in the next tick's sample, which is harmless for a mean.
2. **Escapes.** Mod work outside any section is not measured: `AwayTrips.processLoaded` (its own `END_SERVER_TICK` listener), `LevelUpFeedback.flush`,
   the `ENTITY_LOAD` / `AFTER_DEATH` / `MOB_CONVERSION` handlers in `WorkerSystem` and `AwayTrips`, `ContainerProtection` callbacks,
   `VillagerBrainMixin` (brain build on load), and whatever M11-M25 add (M19's golem gate mixin, M23's breeding gate, M25's raid listeners).
   Nothing checks coverage today. TESTING.md only states the rule.

### 3.3 What "village logic time" is, and how it is measured (exact method)

**Definition.** For one server tick, *village logic time* is the wall time the server thread spends with at least one `dev.villageheart.*`
frame on its stack, except frames of the simulation harness (`dev.villageheart.sim.*`). That includes vanilla code the mod calls (a path
search started by `WalkTo`) and mod code vanilla calls (brain behaviours, mixins, event handlers). It excludes vanilla's own follow-up work
(the navigation tick that walks a path the mod set). The **per-day mean** is the sum over the day's 24 000 ticks divided by 24 000 (ticks
with no mod work count as 0). The gate is: **every day's mean < 1 ms** and the **30-day mean < 1 ms**.

**Primary measurement: nesting-safe sections** (`village_ms.*`, what the gate reads).
- `core.sim.TickTimer` gains `enter(long now)` / `exit(long now)` with a depth counter. Only the outermost enter/exit pair adds its span.
  `VillageTicker.Section` stays `AutoCloseable`: `enter` runs in the constructor and `exit` in `close`, so a body that throws still exits.
  Every use is try-with-resources (already the rule). **Mismatch handling:** an `exit` without an `enter`, or `commitTick` while
  depth > 0, throws only in strict mode (`TickTimer.strict`, set by GameTests and the sim harness). In production it logs one WARN and
  resets the depth, so a measurement bug never crashes a player's server. Calls not on the server thread
  (`server.isSameThread()`) are ignored and counted (`offThreadCalls`, asserted 0 in strict mode). `add(nanos)` asserts depth == 0.
- **Harness suspension:** the collector and the food sampler call mod code (`Dinner.nutrition`, `Stockpiles`, `VillageState`) that may
  open sections. They run inside `try (var h = VillageTicker.harness())`, which sets a suspended flag. Sections opened while it is set
  record nothing. So the harness never counts as village logic, in the timer or in JFR.
- **Coverage step:** every escape listed in 2.2 (and any found in M11-M25 code at step 0, by grepping `register(` on Fabric events and
  `@Mixin` handlers) is wrapped in `VillageTicker.section()`. Rule for the future (TESTING.md): an event handler that can do work wraps itself.
- Ordering: `VillageTicker`'s `END_SERVER_TICK` listener commits the tick. A section that runs after it, in a later listener of the same
  tick, lands in the next sample. That is documented and harmless for a mean, and the p95 can shift by one tick.

**Independent cross-check: JFR sampling** (`village_ms.jfr`, a coverage gate, `full` only).
- With `"profile": true` in the scenario, the harness starts a `jdk.jfr.consumer.RecordingStream` at the baseline, with
  `enable("jdk.ExecutionSample").withPeriod(Duration.ofMillis(10))`, and `startAsync()`. The callback runs on JFR's own thread and only
  counts. For events whose `getThread("sampledThread").getJavaName()` is `"Server thread"`, it adds to `total`. A frame is a **mod
  frame** if `getMethod().getType().getName()` starts with `dev.villageheart.` **or** its method name contains `$villageheart$`.
  Mixin merges `@Inject`/`@Redirect` handler bodies into the vanilla target class, and Fabric's Mixin names them
  `<kind>$<id>$villageheart$<name>`; step 0 confirms the naming with `javap -p` on the remapped dev jar, and T-L1-7 pins it. A sample
  with a mod frame and no `dev.villageheart.sim.` frame adds to `village`. It also counts `truncated` samples
  (`getStackTrace().isTruncated()`). Counters are `AtomicLong`s, read and reset at each day record.
- **No vanilla AI under a mod frame.** Step 0 checks that no mod frame sits *under* vanilla brain ticking. `VillagerBrainMixin` injects
  only at brain construction (`registerBrainGoals`), and the mod brain's behaviours are separate objects that `Brain.tick` calls, so a
  vanilla behaviour sample has no mod frame below it. If step 0 finds a wrapper around brain or AI ticking (any milestone), the classifier
  gets an exclusion for that wrapper's frame, and it is listed in section 8 and pinned by T-L1-7.
- `village_ms.jfr = village / total × (wall_seconds × 1000 / ticks_in_day)`. In sprint the server thread is always busy, so wall per tick
  is the tick time. `village_ms.jfr_samples = total`, `village_ms.jfr_truncated = truncated`. Known bias: `jdk.ExecutionSample` sees only
  threads running Java. Server-thread time in native code is in neither count, so the share is of Java time. This is documented and acceptable for a coverage check.
- The stream's buffers deliver events about 1 s late. That shifts about 2 % of a day across a boundary, which is acceptable. Before the
  **final** record the harness calls `RecordingStream.stop()` (JDK 20+, flushes) so the last day is complete. On resume
  (`--reload-at`) a new stream starts with the timers. `setMaxAge(Duration.ofMinutes(10))` keeps the repository small for the 60-day soak.
- The classification is pure: `core.sim.SampleClassifier.classify(List<Frame(className, methodName)>) → VILLAGE | HARNESS | OTHER`, L1-tested.
- The simulation run config gains `vmArg "-XX:FlightRecorderOptions:stackdepth=256"` (the documented colon form; a bad option stops the
  JVM at start, which is an ERROR in the step-4 smoke, not silent). The default depth of 64 can cut off the mod frame under a deep vanilla
  path search. The truncated count is reported, and the coverage gate below fails if it is above 1 % of the samples.
- A minimum-sample gate keeps the estimate meaningful: `sum(village_ms.jfr_samples) >= 1000 * 30` over the run (about 5 000 a day are
  expected; fewer means the sampler skipped the server thread).
- **Coverage gate** (in `full`): `mean(village_ms.jfr) <= 2 * mean(village_ms.mean) + 0.05 from day 1` and `mean(village_ms.jfr) < 1 from day 1`.
  At 10 ms per sample and about 50 s per day there are about 5 000 server-thread samples a day. With a village share near 1 %, the
  monthly estimate has about ±5 % noise, so a factor of 2 plus 0.05 ms is a true "something escaped the sections" signal, not noise.
- **Red is red** (T-L3-3): the request accepts `probe_burn_ms` (CLI `--probe-burn <ms>`, sim-only). The harness then registers an
  `END_SERVER_TICK` listener in package `dev.villageheart.probe` (gametest source set, not `sim`) that spins for that long outside any
  section. With 0.5 ms the coverage gate must FAIL (`village_ms.mean` unchanged, `village_ms.jfr` about +0.5).

**Measurement hygiene.** `nanoTime` spans include time the thread was preempted. Gate runs therefore run **alone**: no other Minecraft
process (`pgrep -f villageheart.sim.request` and `pgrep -f runGameTest` both empty), and the 1-minute load average divided by `nproc`
below 0.4 (`/proc/loadavg` is host-wide in a container, so this is a ceiling, not proof). `simulate.sh` waits up to 10 min for that
condition and then runs anyway with `load_ok: false` in the report. The digest refuses such a run as a B0 or F row. The report records
`load_avg_start` and `load_avg_end`. Tuning probes run two at a time (3.9), use `--profile off`, and their timing metrics are
informational only.

### 3.4 Assertion language and scenario format additions (all pure, `core.sim`)

1. **`zerorun(path)`**: the length of the longest run of consecutive day records in the scope whose value is 0 (|x| < 1e-9) **or NaN**
   (NaN means no villagers. Counting it as empty is the conservative choice). It is a function over the scope like `max`. In
   `AssertionFunctions`, L1 in `AssertionTest`. The gate applies it to **one sample per day**, `food.days_left_after_dinner` (3.5). That
   is the day's low point, the stock that must last until the next dinner. One instant per calendar day means a short dip across dawn
   can never count as two days (critique #23).
2. **`targets`**: an optional list of assertion strings, parsed like `assertions`, evaluated and printed in `.summary.md` and the report
   (`target_results`), and **never** affecting `status` or the exit code. They are the tuning goals (3.8). An unparseable target is a parse
   error, like an assertion.
3. **`extends`**: an optional scenario name. The base's `actions` run first, then the scenario's own. `assertions` and `targets` come only
   from the file itself, and `default_days`, `seed` and `profile` are its own or the base's. Only one level is allowed (a base that extends is a
   parse error), and a cycle is a parse error. Used by `full_layout`, `full_crowd` and `full_soak` (3.6, 3.10), so the layout is written once.
4. **`when`**: an optional condition on any action with day ≥ 1: `"when": "tier>=village"` (grammar `tier>=(village|town)` only, v1). The
   action becomes due at its (day, tick) **and** once the condition holds, checked every 100 ticks. It runs **once**, and is never retried
   or repeated. `ActionSchedule` keeps conditional actions in a separate pending list. The report gains `conditional_done: [indices]` so a
   resumed run (`--reload-at`) restores them. A conditional action that fails at run time (for example `hire` finds no free adult) is
   **skipped**, not an ERROR: it is logged and counted in `sim.skipped_actions` for that day. An unconditional action that fails is still an ERROR (M2 rule).
5. **`profile`**: an optional boolean (default false), which turns on the JFR stream of 3.3. `simulate.sh --profile off|on` overrides it,
   and the report says which applied.
6. **Provenance** (report fields, written by `simulate.sh` into the request): `git_commit` and `git_dirty` (from `git status --porcelain`),
   `scenario_sha256` of the canonical file (M13's field, or added here if M13 did not), `extra_assertions`, `probe_burn_ms`, `profile`,
   `days`, `load_ok`. `sim-digest.py` refuses to print a B0 or F row unless the tree is clean, there are no extra assertions, the probe burn
   is 0, profile is on, days is 30, load is OK and the scenario hash matches `sim/tuning.lock`.
7. Assumption, checked in step 0 against `AssertionTest`: scopes cover the day records 1..N and never the baseline (day 0).

### 3.6 The `full` scenario (`sim/scenarios/full.json`, 30 days, Normal difficulty, `profile: true`)

**"No player input" (pinned, orchestrator to confirm: decision D-M26-1).** After the setup (day 0) and the day-1 hires, the harness never
changes the world or the village on its own initiative. That means no replacement hires (`replace` is forbidden in `full`, checked by a
`ScenarioFilesTest` row), no items, no commands, no tier writes and no top-ups. The single exception is a fixed list of **standing orders**,
written at setup and each executed at most once, when its `when` condition first holds. They model a player's plan made at the start
("hire a miner once the Mine unlocks"). Without them, Village-tier buildings could never be staffed, because a hire before the tier is
refused (`TIER_LOCKED`), and the run would test only Hamlet jobs. If the orchestrator rejects this, the fallback is `full` without standing
orders plus `full_village` (`extends: full`, a `tier village` setup action), and the roadmap criterion "reaches Village" is then read from `full`.

**Layout** (site-relative, final coordinates fixed by the layout checks of step 6). The `site` action needs a 64 × 40 patch whose corners
lie within the claim minus 8 (72 from the Heart). That fits only if the long side is roughly tangential and its near edge is at about 24.
This is a real risk (risk 3). Fallback order: lower `min_distance` to 12; then split into **two named sites** (a `site` action gains an
optional `name`, and other actions an optional `"site": "<name>"`), with the Mineshaft, Mine, Hunting Lodge and Hunting Ground on the
second one. The Mineshaft and Hunting Ground may be up to 128 from the Heart, but the Mine and Lodge must be within 80.

### 3.7 Back-of-envelope economy (what the first run will probably show)

Wage bill at Village is 10 workers × 1 = 10 emeralds a day. The merchant is capped at 8 a day at level 1 (16 XP a day at 2 XP per sale
reaches level 2 at about day 10 of employment, so 12 a day from then). Surplus supply per day is about 2.5 lots of logs (≈ 40 logs), about
2 of cobblestone (4 hauls × 16), about 4 of carrots and wheat (2 fields), and a little coal and leather. That is more than 8 lots, so income is
**cap-bound at 8 versus a bill of 10**. The treasury (32 − 4 hire charges − 6 more at Village − 4 to 10 a day) runs dry around day 7-9.
Strikes then follow in reverse hiring order. Because the merchant was hired first among the Village jobs, it keeps working, but the Hamlet
workers hired before it are paid first, so the last-hired (builder, guards, hunter, miner) strike. That is survivable. If the merchant
strikes instead, there is no income and a death spiral (hypothesis H1). The tuning levers, in order: `MERCHANT_DAILY_CAP[0]` 8 → 10-12,
then the price lots, then `WAGES`. Town stays out of reach while the dawn treasury never reaches 32. These are predictions for B0 to
confirm or refute, not decisions.

### 3.9 The tuning procedure (what the builder agent executes)

**3.9.1 Runs and replicates.** The world seed stays 1 (the layout depends on the village). Villager AI is not seeded, so "seeds" means
**replicate runs** of the same configuration. Three numbers set the shape of the run plan:
- The economy failure of 3.7 shows from about day 8 and spirals after day 10, so a probe must be **15 days** long (critique #5).
- Probes are compared only with runs of the **same length and the same window**.
- Gate timing comes only from runs made alone.

| Kind | Command | Replicates | Wall (est., 3.9.6) | Use |
|---|---|---|---|---|
| Layout smoke | `simulate.sh full_layout 1` | 1 | ~3 min | layout and harness checks (step 6) |
| Harness checks | `simulate.sh full_short 6` (± `--probe-burn 0.5`, ± `--assert`) | 1 each | ~6 min each | T-L3-3, T-L3-4 (step 6, before B0) |
| B0 (before) | `simulate.sh full 30` | 3, **sequential, alone** | ~30 min each | the "before", and the control for round 1 (its days 1-15) |
| Probe | `simulate.sh full 15 --profile off` | 2 in parallel (two `SIM_DIR`s, two `SIM_REPORT_DIR`s) | ~20 min for both | one tuning round's candidate |
| Shared-lever check | `simulate.sh starter 10` and `starter_cook 10`, in parallel | 1 each | ~10 min | rounds whose lever is read outside the merchant/market group (3.9.2 step 5) |
| F (after) | `simulate.sh full 30` | 3, sequential, alone, **once** | ~30 min each | the final gate |
| Regression | `bare 5`, `starter 10`, `starter_cook 10`, `defended 10` ×3, `raid` ×(M25's count) | per the owners' rules | ~1.5 h | after F |
| Gate extras | `full 30 --reload-at 15`, `full_crowd 5` | 1 each | ~35 min | T-L3-5, T-L3-6 |

Every run writes to `reports/sim/m26/<label>/<rep>/` (`SIM_REPORT_DIR`). A run longer than 10 minutes is started with the Bash tool's
`run_in_background` (timeout ≤ 2 h). The agent is re-invoked when it exits, so it never blocks a foreground call over the 10-minute limit.
It reads only `.summary.md` and the digest (3.9.3), never the whole log.

**3.9.2 One round.**
1. Write the hypothesis in PROGRESS (`H<n>`): what is wrong, which metric shows it, which value, and why that value.
2. Change **one lever**: at most 3 related values (for example the 3 merchant caps), each inside its bound in `sim/tunable-bounds.json`
   (3.9.4). Change DESIGN.md's text too. The bound does **not** move when DESIGN changes.
3. `scripts/check-tuning-diff.sh` (3.9.4) must pass, then `verify.sh --fast` must be green.
4. Run 2 probes. The digest evaluates every gate except the timing gates (`village_ms.*`, `jfr`) and every target **on days 1-15**, for
   the candidate and for the control. The control is B0's 3 runs truncated to days 1-15 in round 1, and afterwards the last kept
   configuration's probes (a kept candidate becomes the next control). For each target it prints the numeric left-hand side and the
   margin to its threshold. **Keep** the change only if all three hold:
   - no non-timing gate passes in more control runs than candidate runs;
   - the aimed target's margin improves in **both** candidate runs over the control's **median**;
   - no other target's median margin gets worse by more than the spread (max − min) of the control.

   Otherwise revert (`git revert`, recorded) and write down what was learned.
5. If the lever is read by a scenario other than `full` (anything outside the merchant/market group, for example `TOOL_SPEED`, food
   need, `FOOD_RESERVE_DAYS`, `WAGES`), run the shared-lever check. A failure there reverts the change.
6. Commit the kept change ("M26 tune H<n>: X a → b, metric m before → after") with its PROGRESS entry.

**3.9.3 Recording.** `scripts/sim-digest.py [--window A..B] [--compare REF...] <report.json>...` prints one markdown row per run: label, rep,
commit (+dirty), status, days, Village day (first day with `tier >= 1`), Town day, `zerorun(food.days_left_after_dinner)`, min/max of it
from day 6, min/last treasury, Σ strikers, Σ emeralds sold, max employed, deaths (by cause), births, `village_ms` mean/p95,
`village_ms.jfr`, `sim.log_errors`, wall minutes, `load_ok`, and then every gate and target with value and margin. `--compare` prints
whether each of a run's key series (Village day, treasury, `food.days_left_after_dinner`, employed, population) lies within the range of
the reference runs, day by day, with the share of days inside. The PROGRESS format per round is:
```
### M26 tuning H3: MERCHANT_DAILY_CAP {8,12,16} -> {10,14,18}
Hypothesis: income is cap-bound (8/day vs bill 10), strikes from day 8 (B0 days 1-15: Σ strikers 12, 14, 9).
| run | commit | status (d1-15) | village day | zerorun | food after dinner min..max d6+ | treasury min/last | Σ strikers | Σ sold | deaths | log errors |
|---|---|---|---|---|---|---|---|---|---|---|
| control B0/1..3 | ... |
| candidate P3/1..2 | ... |
Decision: kept (Σ strikers median 12 -> 2 / 3, both better; other target margins within control spread).
```
B0 and F each get a full 30-day table, and a final "before → after" table of every changed value goes into PROGRESS and DESIGN
("tuned in M26 (H<n>)").

**3.9.4 Guardrails: tuning never touches tests, gates or the harness.**
- **Freeze (step 8, before B0), approved by the orchestrator.**
  - The test audit lists every L1/L2 test that hard-codes a tunable as *follow* (switched to read `Balance`) or *pin* (keeps the DESIGN
    number: `WageRulesTest`, `MarketRulesTest` caps, M15 D1 speed ratios, roadmap L2 counts), with a reason for each.
  - `sim/tunable-bounds.json` gives, for every constant that may be tuned, its freeze value and explicit bounds. Ratios get about ±50 %,
    small integers get a list (for example `WAGES` each in {1, 2, 3}, `MERCHANT_DAILY_CAP` each in 6..24 and rising by level), and
    pinned constants get no entry (they are untunable).

  Both go to the orchestrator before B0, and the approval is recorded in section 8. Re-pointing tests is done in a separate commit with
  no value change. The freeze commit is tagged `m26-freeze` and pushed. The tag moves only by a recorded orchestrator decision.
- **`sim/tuning.lock`** holds SHA-256 hashes: of each scenario file in canonical form (core `Json`, sorted keys, compact), which covers
  setup, the kit, hires, standing orders, `default_days`, `seed`, `profile` and assertions; of every file in `src/gametest/java/dev/villageheart/sim/**`
  and `src/main/java/dev/villageheart/core/sim/**` (the harness, `zerorun`, the sampler); and of `sim/baselines/*.json`. L1
  `TuningLockTest` fails on any mismatch. Only the orchestrator updates the lock, in a commit that says why. Every report records its
  scenario hash (3.4 #6), and the digest refuses a B0/F row whose hash differs from the lock.
- **`scripts/check-tuning-diff.sh`** (default base: the `m26-freeze` tag; it refuses to run without the tag). It runs in `verify.sh`
  whenever the tag exists, not only as the agent's own step. It exits 1 if a commit after the tag:
  - touches anything other than `core/Balance.java`, `docs/DESIGN.md`, `docs/PROGRESS.md`, `docs/ROADMAP.md`, `docs/BACKLOG.md`,
    `docs/plans/M26.md`, unless the commit message starts with `M26 bugfix:`;
  - changes `Balance.java` other than by replacing numeric literals inside the initializers of constants listed in the bounds file
    (checked with a token diff of each changed line: same name, same type, only literals differ);
  - leaves a value outside its bound;
  - changes more than 3 values in one commit;
  - lets an `M26 bugfix:` commit touch `Balance.java`, `sim/**`, the lock or the bounds file.

  Its self-test `scripts/test-check-tuning-diff.sh` builds a throwaway git repo with one good tuning commit, one good bugfix commit, and
  bad ones: a new method in Balance, a value out of bounds, 4 values, a test edit, a scenario edit, and a bugfix that touches Balance.
- **Baselines are not tuning files.** Re-capturing `sim/baselines/starter.json` (M13) is a separate commit approved by the orchestrator.
  PROGRESS shows the old and new baseline side by side. A tuning commit can never do it, because the lock covers baselines.
- **Bugs are not tuned around.** If a run fails because a worker is stuck, a path never resolves, something crashes (`sim.log_errors` > 0)
  or a status is wrong, it is a **bug**:
  - It goes in BACKLOG, gets a failing test first at the lowest layer, then an `M26 bugfix:` commit under the normal definition of done.
    If it is in another milestone's code it goes to the orchestrator.
  - The verifier reviews every `M26 bugfix:` commit on its own, asking "is this a balance change in disguise?".
  - After any bug fix the control is stale. The next round first re-runs 2 control probes of the current kept configuration (labelled
    `B0'`/`C'`), and they count toward the machine-time cap.
- A failing L1/L2 test after a value change means the change broke a rule someone pinned. Revert the change. Never edit the test.

**3.9.5 Stop rules.**
- **Caps**: 6 tuning rounds, 3 bug-fix commits, and 10 h of L3 machine time (summed `wall_seconds` of all M26 runs, from the digest).
  The first cap reached means "stop and report".
- **Done**: F (run **once** per final configuration: 3 runs, alone, clean tree) passes every gate **3 of 3**. The targets hold on at
  least 2 of 3, except `tier >= 2` (stretch, report only). Then the regression set passes under its owners' rules.
- **Any F failure** (one gate in one run) means stop and report. F is not re-run until it passes. A regression failure after F also
  means stop and report: the orchestrator either sends M26 back to rounds (counting against the caps, with F re-run in full afterwards)
  or accepts it.
- **Also stop and report** when the same value has been reverted twice (oscillation), or when a gate fails for a reason no value in 3.8
  moves (for example `village_ms`, or deaths by vanilla night AI).
- The report gives B0, the best configuration, the remaining failures with their deaths, food and economy rows, and the options.

**3.9.6 Wall clock and how the loop affords it.** Evidence: about 40 s per in-game day after a 35 s boot (`bare` and `starter`, 8
villagers). For `full`, 12-14 villagers, 10 jobs (two "away" jobs), a bigger forced area and JFR at about 2 % suggest **50-70 s per day**,
so a 30-day run takes 25-35 min and a 15-day probe 13-18 min (about 20 min with two in parallel on 4 cores). The real figure comes from
the **first B0 run** (a 1-day smoke with idle Village jobs cannot tell). If it is over 90 s per day, the orchestrator is told and the
probe length stays at 15 days (correctness first). Worst-case machine time:

| Block | Time |
|---|---|
| Smokes and harness checks | 0.4 h |
| B0 (3 × 30 days) | 1.6 h |
| 6 rounds (probes 0.35 h + some shared-lever checks) | 2.5 h |
| F | 1.6 h |
| Regression | 1.5 h |
| Gate extras | 0.6 h |
| **Total** | **≈ 8.2 h** (under the 10 h cap; bug-fix re-runs come out of the slack) |

The loop affords it because M26 is the last milestone: no other build track competes for the CPUs, so AGENT_LOOP's "at most 3
Minecraft-heavy workers" is met with one or two sims. The agent waits on background runs at almost no usage cost (it reads one digest
per run), and the work splits cleanly at round boundaries if a usage window ends (all state is in git and `reports/sim/m26/`).

### 3.10 Release-gate support for `full` (prepared by M26, run at the gate)

- `full_soak.json` (`extends: full`, 60 days): the gate assertions that still hold over 60 days, plus
  `world.save_bytes < world.save_bytes@day1 + 1048576 on last day` and `sum(sim.log_errors) == 0 from day 1`.
- `scripts/check-sim-log.sh <scenario> [--count]`: the rule of `sim.log_errors` (ERROR from any logger, WARN or ERROR with a
  `dev.villageheart.` frame in its trace) over `reports/sim/<scenario>.log` and `.2.log`. It exits 1 on a hit, or prints the count.
  `simulate.sh` runs it after **every** run and writes `log_errors` into the report, so the digest shows it for B0, probes and F, not only

## 6. Risks, unknowns, out of scope

**Risks** (highest first):
1. **(top) `full` chains about ten milestones' features, unseeded, for 30 days with no rescue.** A bug in any job (a stuck worker, a
   deposit trip that never ends, a guard who walks off) shows up as a balance failure. The tuning loop is then tempted to "tune around" a
   bug, or to slip a balance change in as a "bug fix". Mitigations:
   - the bug rule and the `M26 bugfix:` review of 3.9.4;
   - `sim.log_errors` gated at 0;
   - `workers.status.*` in the digest (a job whose status is not `ok` on most days is a bug lead);
   - `full_layout` before any long run, and B0 read for bugs before any value changes;
   - the caps of 3.9.5.
2. **The economy may spiral** (3.7 H1): strikes stop work, so income drops and more workers strike. Gates do not catch it (the treasury
   stays ≥ 0), only targets do. The hire order (merchant first) and the merchant cap are the first levers. The 15-day probes are long enough to see it.
3. **The site may not fit.** 64 × 40 inside the claim minus 8, at least 24 from the Heart, is tight (3.6). Fallbacks are lower
   `min_distance`, then two named sites. Found by T-L3-1 in minutes.
4. **Machine time.** About 8.2 h worst case (3.9.6), under the 10 h cap. The estimate of 50-70 s per day is unproven until the first B0 run.
5. **JFR attribution.** Only Java frames running on the thread are sampled, Mixin naming must match, and native time is not counted. The
   gate is the sections; JFR is a coverage check (2× + 0.05 ms), with truncated share and sample count gated and a red-is-red check (T-L3-3).
6. **Night deaths without replacements.** Up to 2 deaths are expected over 30 days (the `starter` history). Gates allow one lost standing
   order (`max(employed) >= 9`) and the population target has slack. Deaths by vanilla night AI are not a tuning matter (stop rule).
7. **"No player input" with standing orders** is an interpretation (D-M26-1). The orchestrator may prefer the `full_village` fallback.
8. **Pinned tests or bounds block a needed change** (wages, merchant caps). That goes to the orchestrator (stop rule). Never edit the test.
9. **Vanilla professions at red workstations** before the tier-up (3.6 hazards): covered by T-L2-3's eviction case and `full_layout`.

**Out of scope**: running the 60-day soak and the 2-player desync session (release gate); new game rules (tuning changes numbers only);
a config file or UI for Balance (DESIGN §11); a second world seed; Town as a gate (stretch target only); per-item merchant metrics; L4
screenshots (no visual change: M26 changes numbers and harness code only).

**BACKLOG folded in**:
- "TESTING.md: SIM_REPORT_DIR must also differ for same-checkout concurrent runs" (step 7, since tuning probes run in parallel).
- M11-r1 "`sum(deaths.cause.minecraft:starve) == 0` can never fail": `full` does not use it; its food criterion uses
  `food.days_left_after_dinner`.
- M23 "L3 growth metrics left to M26" (`growth.births`).
- M14 "tier metrics left to a later scenario" (`tier`, `tier.*`).
