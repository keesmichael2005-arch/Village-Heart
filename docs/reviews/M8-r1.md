### Security of the server-side actions
- **Order of checks.** Every receiver goes through `HeartActions.handle`, which checks, in order:
  1. the rate limit;
  2. that the player's `containerMenu` is a `HeartMenu` with the same container id and the player is near the Heart;
  3. that the epoch is current;
  4. that a village exists;
  5. the rank, re-read from the current `VillageState` on every action.
- **Names a client sends.** Villagers are looked up in the Heart's level only (`villagerInOtherDimension`). Positions become
  `HeartLocation`s in the Heart's dimension, and the client cannot name a dimension.
- **Fire.** Fire only acts on a villager that is in the village registry or carries the worker attachment.
- **Visitors.** A Visitor's opening data and every refresh are built per viewer by `HeartSnapshotBuilder`, which leaves out
  villager rows, building rows, stock lines and job choices. Mutation 6 shows the tests catch a leak.
- **Codecs.** Every string has a length bound: job id 32 (client to server), key 64, id 64, name 32, text 120, and arg 16 ×
  2. Every list has a bound, and enum ordinals are range-checked. Hostile input of either kind throws a `DecoderException`:
  vanilla then disconnects that player and the server keeps running. Tests: `clientStringsAreBounded`, `listsAreBounded`,
  `badEnumOrdinalIsRejected`. On the encoding side, `TextLine` and `HeartSnapshotBuilder` cut every string to its cap before
  it is encoded, so the server cannot throw an encoder exception on a long name tag or a long modded item id.
- **Repeated rejections.** The rate-limited reply is sent at most once a second. The `NO_PERMISSION` warning is logged at
  most once a minute per player. Disconnect forgets the player's buckets.

### Snapshot size bound
`HeartCodecsTest.worstCaseSize` is a real worst case:
- every list is at its cap and every string at its cap in 3-byte characters (`€`);
- every int is `Integer.MIN_VALUE` and every long `Long.MIN_VALUE`, which are the longest varints;
- the test checks that it really reached the cap.

It printed `481053 bytes (469 KiB)`, asserts that this is under 512 KiB, and checks that the snapshot still round-trips.

## Non-blocking notes
1. **The epoch check in the action path has no integration test** (mutation 2 survives). `ActionGateTest` covers the
   gate's rule. Nothing at L2 reaches `Rejection.STALE`, though. T-L2-5(c) is commented "the epoch changed", but after the
   break the menu is already closed by `stillValid`, so the test asserts `NOT_OPEN`. That matches the plan.

   The check only matters if the Heart is broken and placed again at the same position within one server tick. Even then,
   the rank re-read refuses a former Steward, who is a Visitor in the new claim, so this is not a hole.

   Suggested test: in one `thenExecute`, open the screen, set the Heart to air, place a Heart at the same position, then
   send an action from the old menu and expect `STALE`.
2. **The `nearHeart` check in the action path has no test** (mutation 7 survives). `stillValid` closes the menu on the next
   player tick, which `menuClosesWhenFarOrHeartGone` tests. That leaves only a window of one tick. A same-tick test (move the
   player away, then send) would pin it.
3. **The Villagers tab need icons show M7's stub values.** The worker shows bread, bed and emerald even though the Overview
   says "beds 0". This should be accurate once M11 makes the needs real; worth a glance then.
4. **"Slots 1/0" on an invalid Farmhouse that holds a worker** reads oddly: workers here / slots of the invalid verdict. The
   builder already noted it in plan §8. A later UI pass could show "1 worker, 0 slots" or hide the slots while the building
   is invalid.
