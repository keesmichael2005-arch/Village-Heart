## Non-blocking notes

1. `Stockpiles.deposit` does not pass `c.unreadContainers()` to `noteDepositShort`. A short deposit while a Storage chest sits in
   an unloaded chunk still starts the 10 s hold. Consider treating `unreadContainers > 0` like an unknown site in the core rule.
   Removed or replaced chests also count as unread until the next rescan, but that only delays FULL by about one rescan.
2. The L2 regression covers only "no Storage at deposit time". The mixed case (one readable full Storage plus one unknown) is
   covered at L1 only. A glue mutation that passes `0` for `unknownSites` would survive all tests. It is one argument, so the risk
   is small.
3. `StockpilePerfTest` headroom is 4x to 10x, so it does not catch a 3x to 5x slowdown (measured above). If that sensitivity is
   wanted, tighten the limits towards the M6 budget (snapshot of 864 slots < 1 ms, deposit < 0.3 ms) scaled to the 13 824-slot grid.
   Or rely on `StockpileCostTest` and say so in TESTING.md.
4. `docs/TESTING.md` line 139 still says the real snapshot is "asserted at 3 ms in `snapshotCostReal`". It is now print-only.
   No wall-clock guard on the real glue (`StackKey` per slot) is left. A deterministic counter (for example `getItem` calls per
   snapshot) would replace it. Also, pre-M6 `villageTickerTimesSystems` still asserts `meanMs() < 0.5` in Layer 2, which is a
   wall-clock upper bound. It is out of M6 scope.
5. `depositMarksChestChanged`'s "shrink path" step withdraws 864 from 27 x 64. That empties 13 slots through `setItem(EMPTY)`
   (vanilla calls `setChanged`) and shrinks one slot by 32, so the shrink step alone would not catch a missing `changed()` on
   withdraw. The grow step makes the test red today, and `changed()` is called from one shared place (`Stockpile.finish`). To
   prove the shrink path too, make the withdraw leave every touched slot non-empty (for example, withdraw 32 when the first slot
   holds 64).
