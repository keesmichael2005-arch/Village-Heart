## Fix list

1. **False "Storage full" after a deposit made while no Storage was known (real bug; blocking).**
   `src/main/java/dev/villageheart/stock/Stockpiles.java`, `deposit`: `if (stored < asked) runtime(server).tracker.noteDepositShort(...)`
   runs even when the deposit saw no known Storage (`c.sites()` empty because there is no Storage yet, or because every Storage is
   unknown, e.g. right after a restart while the scans are missing). The tracker then holds FULL for 200 ticks as soon as a Storage
   becomes readable, even if it is empty. Repro (a temporary GameTest, since removed): with no Storage, `deposit(5 cobble)` returns 0;
   build an empty 2-chest Storage; once `snapshot.sites == 1` wait 22 ticks. Result: `alert=FULL free=54`
   (`Expected alert with 54 free slots to be OK: was FULL on tick 26`) on the unmutated code. In M7, workers that try to deposit right
   after a restart will raise a false "Storage full" every time.
   Expected: only a deposit that saw every Storage can mark the village full. For example, note the short deposit only when
   `!c.sites().isEmpty() && c.unknownSites() == 0`. Better, move that rule into the core (e.g. `noteDepositShort(time, sitesSeen,
   unknownSites)`) so an L1 test covers it. Add a regression GameTest like the repro (deposit with no Storage, or with only an unknown
   Storage, then a readable empty Storage, then the alert is OK after a refresh) and check that it fails without the fix.

2. **`depositMarksChestChanged` (T-L2-6) cannot fail (vacuous test; blocking).**
   `src/gametest/java/dev/villageheart/gametest/StockpileGameTests.java`. Mutation: `ContainerInventory.changed()` made a no-op. Result:
   the test **still passes** (mutation run C, see below). The test deposits 64 cobblestone into an empty chest, so
   `ContainerInventory.add` uses `container.setItem`, and vanilla's `BaseContainerBlockEntity.setItem` already calls `setChanged()`
   (1.21.11 sources, line 123). The paths that depend on `changed()` are `have.grow(n)` (topping up a partial stack) and
   `have.shrink(n)` (a partial withdraw), and the test never takes them. Without `setChanged` on those paths, comparators/hoppers
   miss the change and the chunk is not marked dirty, so a deposit can be lost on save.
   Expected: drive the comparator signal only through the grow path (and ideally the shrink path). For example, pre-fill all 27 slots
   with 1 cobblestone (signal 1), deposit 27 x 63 (all partials), and expect signal 15. Then a partial withdraw should lower the signal
   again. Prove that it fails with `changed()` as a no-op.

## Non-blocking notes

1. `snapshotCostReal` asserts wall-clock medians inside Layer 2, which goes against the M4 lesson. It held in every run above, but
   consider moving the timing into `perfTest` (a GameTest can print it, and only the perf task asserts), or using M4's best-batch
   retry window. Also `StockpilePerfTest` uses one 30-sample median and not the M4 best-batch retry (`RoomScannerPerfTest`). The spill
   case reached 1147 µs of 3000 µs.
2. By design ("no empty slot in any **readable** Storage"), one full known Storage plus one unknown or unloaded Storage gives FULL.
   M8's alert text should say "known Storage is full" or similar.
3. `componentsAreRespected` covers a name and damage. Add an enchanted item (e.g. an enchanted book vs a plain book) to the pairwise
   check, since enchantments are a separate component type.
4. `depositHere` never notes a short deposit, so it cannot raise FULL. That is intended (T-L2-3b checks it), but the facade Javadoc
   should say so.
