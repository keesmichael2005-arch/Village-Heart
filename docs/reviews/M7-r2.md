## Round-1 fix 1: the deposit trip flake

**What changed.** The builder made three changes:

- A per-villager `Workers.tripRunning` flag, which:
  - blocks a second `DepositTrip` from starting, whether the WORK activity or go_home starts it;
  - makes `GoToJobBlock` yield while a trip runs.
- The trip now puts its walk target back on any tick it is missing, unless the pathfinder reported the target
  unreachable in the last 20 ticks.

**Why the flag is safe.** The flag lives in a `WeakHashMap` keyed by the entity. It is cleared in `stop()`.

- Every brain swap goes through vanilla `refreshBrain`, which calls `brain.stopAll` first. That covers hire, fire
  and the self-heal in `WorkerSystem`.
- An entity that unloads or changes dimension comes back as a new object.

So the flag cannot get stuck and leave a worker that never walks again.

## Round-1 fix 2: POI tickets left behind by a Heart release

**What changed.**

- `releaseAll` now records each held block whose chunk is unloaded in `pending_ticket_releases`.
  - This list is saved in the world claim. It survives `releaseAt` and `clear`.
  - The schema stays optional, so older saves still decode.
- `processPending` runs every 20 ticks, whether or not a village is claimed. It releases a pending ticket once that
  block's chunk is loaded.
- It never loads a chunk itself.
- If the current village holds the block again, the entry is dropped and the ticket is not released.

**Mutation check of `heartReleaseWithUnloadedWorkstation`.** The builder's mutation was "the release is never
recorded". I tried another:

| Mutation | Result |
|---|---|
| `processPending` returns at once (pending entries are never processed) | **red**: "still pending" on tick 3002 |
| `VillageCodecs` drops `pending_ticket_releases` on decode (Layer 1) | **red**: `VillageCodecsTest.pendingTicketReleasesSurviveReleaseAndRoundTrip` |

**Deviation: the test runs a POI query instead of spawning a villager. Acceptable.**

- The final step calls `PoiManager.take` with `VillagerProfession.ALL_ACQUIRABLE_JOBS`. That needs a free ticket
  (`HAS_SPACE`), which is the same condition vanilla's `AcquirePoi` claims with.
- A real villager would have to walk to a forced chunk 100,000 blocks away. That would only add timing noise, not
  coverage.
- The test also checks the parts that matter:
  - before the release, the chunk is really unloaded and the entry is recorded;
  - after the chunk is forced to load, the entry is cleared and the ticket is free.

**Can a pending release take the ticket of a NEW village? No.**

- `processPending` skips any block in the current `reservedJobBlocks`.
- Without that skip, it still could not happen in practice:
  - A stale pending ticket fills the POI's only slot. So a new village's reservation pass cannot take it until
    `processPending` has freed it. The pass then takes it on its next run, within 20 ticks.
  - The only way the new village could hold that block while the entry is still pending is if the block was
    replaced, which creates a new POI record.
- I removed the `heldNow` check as a mutation and all 102 tests still passed. So that defensive branch has no test,
  but it is also nearly unreachable. Even if it misfired, the pass's `hasFreeTicket` branch takes the ticket back
  within 20 ticks. Non-blocking (note 2).

## Non-blocking notes

1. **The trip guards have no deterministic test.**
   - One could be written: during a running trip, erase `WALK_TARGET`, let one brain tick pass, and assert that
     `WALK_TARGET` points at Storage, not the composter. A second test could force both activities' trips to try to
     start and assert that only one starts.
   - Without such tests, a future regression would show up only as an occasional flake.
2. **The `heldNow` branch in `JobSiteReservations.processPending` is untested.** It is nearly unreachable (see above).
3. **A tiny remaining window.** When a pending block's chunk loads, `processPending` releases its ticket up to 20
   ticks later. In that window, someone could break and re-place the block, and a vanilla villager could claim the new
   POI. The release would then free that villager's ticket. This is about as unlikely as round-1 note 3 (crash between
   saves) and is not worth guarding.
4. **`DepositTrip.tick` erases `CANT_REACH_WALK_TARGET_SINCE`** when it re-targets. Vanilla only reads that memory to
   give up on a walk, and the trip has its own 600-tick timeout, so I saw no effect.
5. **Round-1 notes 3 and 4** (crash between the POI save and the saved-data save; the fully qualified names in
   `Workers.levelOf`) still stand and are still non-blocking. The new `Workers.TRIPS` field also uses fully qualified
   names inline.
