## The builder's doubts
- **(a) Variance in `bare`.** I agree it is robust enough. The assertion is relative to `population@day1`, and night 1 falls inside
  day 1 (the day starts at daytime 0). So night-1 losses, like my run's zombie death and the builder's 3 losses in `bare 2`, are
  already in the day-1 number. Only a loss of 2 or more over nights 2–5 would turn the run red. That has not happened in any of the
  5 real multi-day runs I know of. If it does happen, the plan's remedy (a scenario-level gamerule, with the reason given) is the right one.
- **(b) `clean_shutdown=true` after a real crash.** This is not a hole. A crashed run is caught three separate ways: the crash-report
  file, status `RUNNING`, and fewer than N days. Even with the crash-report check mutated away, `selftest_crash` would exit 2 on its
  status. The field name is misleading, though (note 2).
- **(c) The stub self-test adds about 30 s to `verify --fast`.** That is acceptable for what it protects (the exit-code contract).
  A shorter poll interval or fewer sleep cases could trim it later.

## Non-blocking notes
1. **`kill_group` kills every simulation on the machine.** `pkill -KILL -f "villageheart.sim.request="` is not scoped to this
   run. Running `verify.sh` (whose self-test calls `simulate.sh` many times) while a real simulation runs kills that simulation, and
   it ends in ERROR. I reproduced this. It fails safe, but it matters for overnight loops. Scope it, for example by matching the
   absolute request path or a run id.
2. **`clean_shutdown` is true after a crash.** `SERVER_STOPPED` also fires on the crash path. Consider setting it only after a
   `finish()` (or recording `crashed`), so the report can be trusted on its own, without the crash-report file.
3. **The stub self-test does not cover a wrong `reloads` value.** Add a fake case where phase 2 reports `reloads: []` (it should
   expect 2), so the `reloads` check in `decide()` cannot rot unnoticed.
4. **T-L2-2 does not test the spherical radius.** The far villager is outside the AABB too, so removing
   `distanceToSqr(centre) <= r2` survives. Add a villager near a box corner (inside the box, outside the sphere).
5. **`SIM_DIR` only works with the stub.** The Loom run config hard-codes `build/run/sim` (the request path and the run dir). With
   `SIM_DIR` overridden and the real Gradle command, the server would read a stale `build/run/sim/sim-request.json`, and the crash
   check would look in the wrong folder. Refuse `SIM_DIR` unless `SIM_GRADLE_CMD` is also overridden, or document this.
6. **`world.save_bytes` trails the autosave.** It was constant on days 1–4 and only changed on day 5. This is documented in plan
   §3.6. It is fine for the soak's "grows < 1 MB", but not for per-day trends.
