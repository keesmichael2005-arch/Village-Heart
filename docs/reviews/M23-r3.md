### 2. A licensed pair wasted its day on NOT_VISIBLE aborts: fixed

**The fix.** `VillagerMakeLoveMixin.villageheart$freshSight` wraps `BehaviorUtils.targetIsValid` inside `VillagerMakeLove.isBreedingPossible`. That one method serves both the start condition and `canStillUse`. When the cached `NEAREST_VISIBLE_LIVING_ENTITIES` snapshot says the partner is unseen, the wrapper returns true only if all of these hold:
- `self` holds today's active licence (`holdsLicence`, which ignores the probe switch).
- `BREED_TARGET` is a living villager.
- The partner is within √5.
- A fresh `hasLineOfSight` succeeds.

**Owner rule check (no births except the dawn licence).** I disassembled `isBreedingPossible` from the 1.21.11 jar:

```
BREED_TARGET present (villager) && targetIsValid(...) && self.canBreed() && partner.canBreed()
```

The wrapper replaces only the `targetIsValid` term. `Villager.canBreed` is still false for any unlicensed villager inside the claim (`VillagerBreedingGateMixin`), and `getBreedOffspring` is still vetoed. So the rescue cannot start or extend a run for an unlicensed villager in the claim.

### Notes (not blocking)

1. **The rescue's distance and line-of-sight guards are not pinned by a test** (mutant D stays green). Without them, a licensed pair separated by a wall or more than √5 apart would keep its run going until it times out, instead of stopping as NOT_VISIBLE. That could cost time but never a licence or the owner rule, because the birth tick still needs √5 and `canBreed`. No test covers the guard outside the claim, and today it can only matter for a villager who holds a licence, who is by definition a claim villager.
