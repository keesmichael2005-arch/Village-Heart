## Item conservation (brief point 2), read from the code
- **Normal batch:** every unit is one step on the server thread (inputs out, output in, bank −200); fuel is loaded one item at a time
  (item out, then bank +burn). Outputs stay in the cook's pockets until the batch ends (plan decision), then `DepositTrip` hands in
  everything not kept. Mutation A shows a dupe is caught by four tests. No loss or dupe found in the normal paths.
- **Server restart / chunk unload mid-batch:** the inventory is saved with the entity, the bank with the village, both in the same
  autosave; `CookKeep`'s no-batch branch keeps whole units and the fuel, and planner row 4 resumes. `restartMidBatchResumes` drops the
  runtime only (deviation T-L2-7) and shows bank 1600 − 8 × 200 = 0 with 8 cooked: no double charge. Acceptable: the entity
  inventory and `smoker_heat` round-trips are vanilla / L1 (`VillageStateSmokerHeatTest`). Edge: a chunk that unloads (entity saved)
  before a crash with no autosave can leave inventory and bank from different moments (≤ 1 fuel item or 1 unit off). BACKLOG 3.
- **Death mid-batch:** villagers do not drop their inventory, so up to a batch of inputs + outputs + carried fuel is lost
  (`AFTER_DEATH` → `fireById` → `CookJob.forget` releases the reservations, no leak). Same open question as the miner's haul. BACKLOG 1.
- **Fired mid-batch:** the items stay with the now-vanilla villager (plan §6 out of scope, shared rule for every job). BACKLOG 1.
- **Unloaded mid-fetch:** no unload hook releases the reservation, so the reserved inputs are hidden from dinner (which subtracts all
  reservations) and the other cook until the cook loads again and its fetch deadline expires. BACKLOG 2.
- **Heat bank:** heat only enters through `loadFuel` (one carried item removed), so it cannot be duplicated. It is lost (by design)
  when the smoker block is gone or the village has no Kitchen at all; it is not mapped to a Kitchen (deviation 3), so a bank can
  outlive its Kitchen while another Kitchen exists — stale data, no gain. A Kitchen that is only invalid keeps it in the code (`KitchenSystem.gone`),
  but the plan's T-L2-10 (d) that would prove it was not built (BACKLOG 7). BACKLOG 4.
- `completeUnit` puts the inputs back with `addItem` and ignores the remainder when the output does not fit; it fits in practice
  (the space was just freed). BACKLOG 5.

## Stockpile API (brief point 3)
`Stockpile.nearestHolding(from, key, holder)`, `withdrawFrom(site, key, n, holder)`, `available(key, holder)` and the glue
`Stockpiles.nearestHolding(level, from, key, holder)`, `withdrawAt(level, anchor, key, n, holder)`, `available(server, key, holder)`
exist with the names M19's plan uses. Reservations are global (not per site), and `withdrawFrom` caps by `available(key, holder)`,
so whatever site a holder takes from, the others' reserved count always stays in stock: two cooks, the builder (BuildSystem reserves
"stock minus other consumers' reservations") and a future self-crafter cannot over-take. `StockpileHolderTest` covers the core.
The cook glue's use of it is what item 2 asks to prove.
