1. **T-L4-1 `refusedPlacementKeepsClientItem` is vacuous: it passes without the resync it is meant to prove.**
   File: `src/gametest/java/dev/villageheart/gametest/VillageHeartClientTests.java`.
   `runCommand("tp @a ~ ~ ~ 0 60")` runs from the server command source, so the player lands on a block corner
   (client position `(0.0, -60, 0.0)` in this world). Looking down at 60° from there, the target cell above the clicked
   block overlaps the player's own hitbox. Vanilla `BlockItem.canPlace` fails **on the client**, so the client never
   predicts the placement and never decrements the stack. The test therefore never exercises the ghost-item case.
   Evidence: I removed `sp.containerMenu.sendAllDataToRemote()` from `VillageHeartBlock.getStateForPlacement` and
   the test still passed. A per-tick probe showed the client count stayed at 1 every tick.
   Then I changed only the teleport to `tp @a ~0.5 ~ ~0.5 0 60` (the player stands at `(0.5, -60, 0.5)`).
   - With the resync removed, the test goes red: `client main hand count after refusal is 0, expected 1`.
   - With the resync in place, it is green, and the screenshot still shows the refusal message with the Heart in the hotbar.

   Expected: put the player on a block centre, or otherwise make sure the target cell is free. Add a precondition
   showing that the client really predicted the placement, for example a client-side check that the target cell is
   unobstructed for the player. Re-run the mutation: without `sendAllDataToRemote` the test must fail. Look at the new
   screenshot. The production code is correct; only the test is wrong.

2. **The `VillageTestSupport.purgePoi` reset step logs 14 `ERROR` lines every GameTest run.**
   File: `src/gametest/java/dev/villageheart/gametest/VillageTestSupport.java`.
   The error is `[Server thread/ERROR] POI data mismatch: never registered at BlockPos{...}`, once per claim test.
   Cause: `setBlock(bell → AIR, 3)` queues vanilla's own POI removal for the bell, then `poi.remove(p)` removes it at
   once, so the queued removal finds nothing. Evidence: in the run with `purgePoi` removed, the log has no such lines.
   The routine ERRORs would hide a real POI bug in later milestones (villager workstations, beds).
   Expected: for bell blocks, only set the block to air and let vanilla remove the POI. Call `poi.remove` only for
   POIs whose block is no longer a POI block. The log must have zero `POI data mismatch` lines. The purge itself is
   needed: without it, `heartNeedsBellToClaim` fails (see the evidence below), so keep it.
