# M19 review, round 1 (verifier)

Reviewed: branch `m19` at `70e5e65`. Merging `origin/dev` changed nothing ("Already up to date").
- Diff: `git diff origin/dev...HEAD`, 133 files, +9273 lines.

Three things make this a FAIL:
- the smith duplicates every item it smelts or crafts;
- two item-loss paths;
- a GameTest that fails about one run in three.

The design rules are in good shape. The owner decisions are implemented, the tests for the rules are mostly strong, and the save codec and the enums are clean.

## Fix list

1. **Item duplication in `SmithJob.give()`: blocking.**
   - Where: `src/main/java/dev/villageheart/worker/smith/SmithJob.java:1501-1507`.
   - What's wrong: `SimpleContainer.addItem(stack)` adds a **copy** and returns the leftover. It never shrinks its argument. I checked this in the 1.21.11 bytecode: `stack.copy()`, then the two move calls, then `areturn` of the copy. So `stack` is still full afterwards, `!stack.isEmpty()` is always true, and the same items are also dropped on the ground.
   - Callers hit: every smelted ingot (`:510`), every finished tool or armour piece (`:871`), stick and plank leftovers (`:836`), and the commit rollback (`:735`).
   - Evidence: I added a temporary assertion to `minerWithoutPickaxeGetsStone` that counts `STONE_PICKAXE` item entities within 100 blocks. Result: `dropped stone pickaxes on the ground: 1, in mine chest: true`, so the test went red. The assertion is reverted.
   - Expected: `ItemStack rest = inv.addItem(stack); if (!rest.isEmpty()) drop(rest);`, as `withdraw()` and `SmithCrafts.refund` already do.
   - Add a GameTest that fails today. Count ground item entities after a craft and after a smelt, for example in `minerWithoutPickaxeGetsStone` and `smeltsRawOre`.
   - The existing tests only count containers, which is why this went unseen. Check other `addItem` callers for the same pattern (see item 4).

2. **A saved craft is overwritten, and its materials lost, when its slot reads UNKNOWN: blocking.**
   - Where: `core/smith/SmithPlanner.decide` (`:51-55`).
   - What's wrong:
     - With `savedCraft` present and `craftPresence == UNKNOWN`, the planner returns neither `CancelCraft` nor `Craft`. It falls through to `takeOrder`, then `StartCraft`.
     - `commitCraft`, then `SmithCrafts.commit`, then `VillageState.withSmithCraft` (`:635-640`) is a plain `put` on the furnace key.
   - Scenario: a pickaxe is committed for the Mine. Next morning the Mine is invalid or unloaded, so its slot reads UNKNOWN. A guard-sword order is committed on the same furnace, and the pickaxe record, with its `committed` ingots and sticks, is replaced. `adopt()` cannot help because a craft exists at that furnace.
   - Expected: while a saved craft exists on this smith's furnace, the planner must not start another craft there. UNKNOWN pauses; it does not free the furnace. `withSmithCraft` should refuse to overwrite a different key.
   - L1 test: saved craft plus UNKNOWN presence plus an urgent orderable demand gives no `StartCraft`.

3. **Two smiths in one Smithy can start two golem builds: blocking (item loss).**
   - Where: `worker/smith/GolemBuilds.start` (`:25-27`) is an unconditional `withGolemBuild(smithy, 0)`, keyed by the Smithy.
   - What's wrong: `SmithPlanner` returns `BuildGolem` only when `buildOwnedByMe`. For the second smith it falls through to `StartGolem` whenever `GolemRules.allowed(pop, golems, builds)` holds, e.g. population ≥ 10, 0 golems, 1 build.
   - Scenario: smith B spends another 36 ingots and a pumpkin. A's progress resets to 0. Whoever finishes second gets `finish == false`, so a whole golem's materials vanish.
   - The same race happens when both smiths decide `StartGolem` before either has saved a build. The cap does not count a smith that is still fetching golem materials.
   - The plan's `anOrphanedCraftIsAdoptedAndASecondSmithLeavesTheGolem` does not cover population ≥ 10.
   - Expected:
     - `start` is compare-and-insert and refuses when an entry exists, with the materials going back to the smith.
     - The planner never returns `StartGolem` while the same Smithy has a build.
     - A golem fetch counts toward the cap.
   - Tests: L1 for the planner. L2 if practical: two smiths, population 10, 72 ingots, so exactly one build and 36 ingots used.

4. **`golemWithoutIronWaits` is flaky and reproduces alone: blocking.**
   - Full verify, Layer 1 (`build` runs the GameTests too): `failed ... health 40.0 dist 9.54 ... iron 3 day 7997 target null on tick 6002`, i.e. 1 failed of 418. Layer 2 in the same run: 418/418 green.
   - Alone, three runs: pass, **fail** (`health 40.0 dist 5.16 ... iron 3 day 7997`), pass.
   - Pattern: after the glass pen is removed and the 3 ingots are stored, the golem walks part of the way (5 to 9.5 blocks from the wait spot), never reaches the 1.5 radius, and no ingot is used before the 6000-tick limit.
   - This is not one of the accepted flakes (`two_hunters_one_ground`, L4 world-load timeout). Find out why the golem stalls short of the spot (walk timeout and cooldown cycle? path to the spot blocked? the smith not offering the repair?). Fix the behaviour, not the time limit, then run it alone about 10 times.

5. **Ingot or tool lost when the smith's inventory is full: should fix.**
   - Where: `SmithJob.java`.
   - What's wrong: the return value of `addItem` is ignored.
     - `repairSlotTick` (`:1130-1135`): an ingot is withdrawn from Storage and then `addItem(got)` is ignored. If the 8 slots are full, the ingot is lost, and this repeats every `SMITH_REPAIR_TICKS`.
     - `fetchRepairTick` (about `:1178`): a Barracks slot is set to EMPTY and then `addItem` is ignored, so the tool vanishes if the inventory is full.
   - Expected: drop or put back the leftover.

6. **`refundPending` is never acted on for smith crafts: should fix.**
   - Where: `SmithCraft.refundPending` (set by `SmithCrafts.refund` and by the codec for a bad saved craft) is read only by `SelfCraftSystem` for self-crafts.
   - What's wrong: a partly refunded smith craft keeps its leftover `committed` items. A bad saved craft (unknown recipe) has its need coerced to `AXE` and can then be resumed as a `Craft`.
   - Expected: the smith (or a system tick) retries the refund and never resumes a `refundPending` craft. L1/L2 test with a codec-loaded bad craft.

7. **In-place repair edits a chest slot without `setChanged()` and without re-checking the item: should fix.**
   - Where: `repairSlotTick` (`:1115-1138`) mutates `c.getItem(slot)` directly.
   - What's wrong: the damage change may not be saved. A player can also swap the scanned item for another damaged one, which then gets repaired with the scanned job's material.
   - Expected: `c.setChanged()`, and check that the item id matches `hit.job().itemId()`.

8. **`golemIgnoresCreeper` is vacuous for the mod's code, and `IgnoreCreeperGoal` cannot do its job: minor.**
   - The mutation: with the `IgnoreCreeperGoal` registration commented out in `IronGolemGoalsMixin`, the test still **passes**.
   - Why: vanilla's `NearestAttackableTargetGoal` for iron golems already excludes creepers.
   - The only other way a golem gets a creeper target is `HurtByTargetGoal` (priority 2). A priority-4 goal cannot preempt it (`canBeReplacedBy` needs a lower priority number), so the new goal never runs in the one case where it would matter.
   - The owner rule holds in practice, because vanilla already does it and a creeper only hurts by exploding.
   - Expected: either drop the goal and document that vanilla covers it, or make it effective (for example clear a creeper target in a `tick` inject). Test it by forcing `golem.setLastHurtByMob(creeper)` or `setTarget(creeper)`.

9. **Storage gear is never repaired: minor, not item loss.**
   - Where: `RepairScan` Storage hits have `slot = -1`, and `fetchRepairTick` skips every hit with `slot < 0`.
   - Expected: implement it, or drop Storage from the scan and say so in DESIGN §5.7.
