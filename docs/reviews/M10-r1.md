2. **The D10 fix (COLLECT timeout restarts after a trip) misses the trip-first order and has no regression test** (`FarmJob.plan`, the `case COLLECT` branch).
   - A deposit trip can start in two ways:
     - (a) The planner sees `DepositTrip.wanted` first and answers YIELD. The fix handles this: `before != COLLECT` restarts the clock.
     - (b) The `DepositTrip` behaviour's own start check (every 20 ticks, run before `FarmerWork.tick` in the brain) fires first. `FarmJob.tick` then returns early while the trip runs, so `ws.action` stays COLLECT. On return the planner answers **CONTINUE** (the item still exists) and returns before the switch, so `itemSince` is stale. `collect()` then blacklists the item at once, for 6000 ticks, which is also the item's despawn time.
   - **Reproduced deterministically** with a temporary GameTest (patch kept outside the repo; it is described here so the builder can rebuild it):
     - Setup: one wheat item at (4, 0, 27), no field. The farmer starts COLLECT at tick ~10.
     - At ≥ 120 ticks, the test fills the inventory with 8 cobblestone stacks at the end of a tick where `(gameTime + 1 + villagerId) % 20 == 0`, so the trip check comes first.
     - Result with the current code: the trace shows no YIELD; after the trip, at tick 492, the item is blacklisted and the test fails ("blacklisted true").
     - Same test, injecting where `% 20 == 2` (planner first, YIELD at tick 155): passes with the current code. With the D10 change reverted it **fails** (blacklisted at tick 494).
     - So the mechanism is real, but only order (a) is fixed. Reverting D10 leaves the whole suite green, so nothing guards it.
   - In a real village, wanted() becomes true mid-COLLECT when vanilla pickup fills the last slots on the way. That is likely (about 50%) to take path (b).
   - **Expected:**
     - Restart the collect clock whenever the farmer comes back from any trip. For example, mark the worker state while `Workers.tripRunning(v)` and reset `itemSince` (or drop `ws.item`) on the first tick after it.
     - Add an L2 test for both orders, along the lines above.
   - Also correct PROGRESS/D10. In a traced `storageFullStopsHarvest` run, phase 2 never COLLECTs before its trip: the YIELD comes from IDLE/HARVEST, because the inventory is full of kept cobblestone and nothing fits. So D10 is probably not the cause of that flake, and the cause is still unknown. Say so rather than calling it fixed.

- **`loose()` 60-block box:** batches run one after another, and `sweepStrayCrops` discards items within 72 blocks of the corner at the start, so it cannot count a neighbour's items from the same moment. But the box is far wider than the farmer's 24-block disc around the composter. An item that ends up outside the disc is counted, is never collected, and the wait times out with no reason given (`looseDescription` helps). Counting inside the work area would make the cause obvious.
