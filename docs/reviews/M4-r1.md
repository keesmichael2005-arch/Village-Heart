## Fix list

1. **Perf tests are flaky under realistic load (blocking).** `src/test/java/dev/villageheart/core/room/RoomScannerPerfTest.java`.
   The first full `scripts/verify.sh` on a clean checkout failed Layer 1: `capWorstCaseIsBounded` had a **median of 15 750 µs against the 10 ms limit**.
   Raw timings (µs): `[7664, 3220, 7300, 7258, 7415, 11177, 8430, 11706, 32175, 14467, 2995, 28887, 18520, 21047, 20475, 15750, 27767, 24011, 13951,
   38776, 15313, 12889, 18615, 26818, 26477, 3246, 24347, 20740, 19533, 3091]`. The load average was about 7 on 4 cores while other agents ran Minecraft.
   The same scan takes about 3 ms when it gets the CPU, so this is scheduler contention, not the code. `room16x16x8Under5ms` has the same structure (one
   median of 30 samples) and is exposed the same way: it passed at 2.2 ms in that run only because the contention hit the other test.
   Expected:
   - Time several batches (for example 5 × 30 after warm-up) and assert on the **best batch median**, or on a low percentile such as p25. Contention only
     adds time, so the fastest samples measure the code. Keep the roadmap's absolute 5 ms limit for T-L1-16.
   - For T-L1-17 (the cap is enforced during the fill, not after), add a deterministic guard: wrap the grid in a counting `BlockView` and assert
     `cell()` calls ≤ about 8 × 4097 and `openToSky()` calls ≤ about 4097 + a small constant. Then the "bounded" property no longer depends on wall-clock
     time, and the timing limit can stay loose.
   - Print every batch median in the failure message.

2. **Deviation 1 (generalised roof test) reports roof holes outside the room, at wrong positions (blocking).**
   `src/main/java/dev/villageheart/core/room/RoomScanner.java`, `locateLeak`, the `covered` list. The extra candidates `Q` (E's other covered horizontal
   neighbours) can be **outdoor** cells under any overhang, so a plain wall gap next to a porch, pergola or neighbouring roof is reported as
   `ROOF_MISSING` at a hole in that outdoor covering. The plan's P-only rule gets these right. Probes (FakeGrid `room5x5x3()`, a ground slab at y = 0
   over x/z −6..12, wall gap (0,2,3); I ran them as a temporary test, then removed it):
   | Probe | Outdoor build | m4 result | P-only rule (plan) | With the fix below |
   |---|---|---|---|---|
   | A | porch roof y=4 over x −3..−1, z 0..6, with a 1-wide slot at z=3 | `ROOF_MISSING (-1, 4, 3)` ✗ | `WALL_GAP (0, 2, 3)` | `WALL_GAP (0, 2, 3)` |
   | B | pergola slats at y=4 on even z, x −4..−1 | `ROOF_MISSING (-1, 4, 3)` ✗ | `WALL_GAP (0, 2, 3)` | `WALL_GAP (0, 2, 3)` |
   | E | two neighbouring roofs at **y=8** (z −2..2 and 4..8) | `ROOF_MISSING (-1, 8, 3)` ✗ (6 blocks above the gap, the room's roof is intact) | `WALL_GAP (0, 2, 3)` | `WALL_GAP (0, 2, 3)` |
   | F | none (control) | `WALL_GAP (0, 2, 3)` | same | same |

   E is not a wording slip on an odd shape: the room's roof is intact and the reported position is outdoor air 6 blocks up, so a player cannot act on it.
   **Fix (verified):** only consider a neighbour `Q` that is already part of the room, i.e. add `parent.containsKey(q.pack()) &&` to the `covered.add(q)`
   condition. With that one change all of `RoomScannerTest` (including `gableRoofSlopeCellReportsIt`, the reason for the deviation) and `SharedRoomsTest`
   pass, and probes A, B and E report `WALL_GAP (0, 2, 3)`. Add probes A and E as regression tests in `RoomScannerTest`, and update plan §9 to match.

## Non-blocking notes
1. `largerRoofHolesReportAHoleCell` accepts any cell of the 1×2 / 2×2 hole. The plan (T-L1-2) asked for the exact cell; the deterministic BFS would allow pinning it.
2. Probe C (wall gap under a pergola slat) and D (posts beside the lintel) report `ROOF_MISSING` at an adjacent outdoor cell with both rules. This is the misreport class plan §3.2 documents and accepts.
3. `wallLikeCellsBlock` can hardly fail in core (FakeGrid SOLID always blocks). The real proof is the L2 materials test, which is mutation-checked.
4. `MarkerView` forces the marker cell OPEN but `openToSky` delegates to the inner view, so a collidable marker would break the "agrees with cell()" contract. This is harmless while `MarkerBlock` is `noCollision()`; M5 should keep it that way or also override `openToSky`.
5. The first real-world scan took about 7 ms (cold classifier cache). Worth watching once M5 scans in the round-robin, but nothing is wrong now.
