### Is the changed roadmap setup still an honest proof? Yes.
The builder changed the setup to two farmers (A, B) and one lumberjack (C). C is the only villager who can chop, so every log that falls is
C's and no per-villager attribution is needed. With the strike gate mutated, C felled a log by tick 427 of the run. The 2 500-tick window is
therefore about six times the time C needs to fell a log, and the strike has no time-based exit: only a dawn or a settle changes the payroll,
and the test checks `ON_STRIKE` every 100 ticks. The test watches part of the day, not all of it, but no mechanism could let C start chopping
later that day. A and B are shown to be paid and not on strike, and the deposit at the end proves C can chop.

### The builder's weak spots
- **`frozenWhileHeartUnloaded` has no workers.** It proves the clock and the dawn event (no run while frozen, exactly one on load), and the
  `isLoaded` mutation turns it red. `WageSystem` charges only through `runDawn`, so a worker would add little. Optional: a record-only worker
  and treasury assertions.
- **`wagesByLevel` discards the entity instead of unloading its chunk.** `WageSystem` and `HeartFacts.wageBill` read only `WorkerRecord.level`
  and never the entity, so the record is what gets tested either way. Acceptable.
- **`WageStats` has one listener slot.** It is safe: every wage test has its own `wages_*` environment, so its own batch, and the tests move
  the shared clock anyway. `VillageTestSupport.reset` and `done` clear the slot.
- **`Workers.hire` order (record, then charge, then install).** If `install` throws after the charge, the record stays and `WorkerSystem`'s
  re-install branch (now at the recorded level, as `workerComesBackAtItsLevel` shows) restores the worker. Nothing is charged twice:
  `Payroll.hire` treats someone already in `paidToday` or `unpaid` as free.
- **`depositInventory` takes the emeralds first and puts them back if something throws.** See fix item 2. The normal paths conserve
  "inventory + treasury": checked in `treasuryScreenActions` (70 → 70; a full inventory on withdraw drops the overflow at the player's feet;
  a full treasury never calls the `max == 0` count-only path).
  - An inventory that is full at put-back time is handled: `placeItemBackInInventory` drops the overflow at the player.
  - A disconnect in the middle of an action cannot happen: every action runs inside one server-thread tick.
  - Two players depositing at once are serialized: Fabric play receivers run on the server thread, and each action re-reads the treasury.
- **Money safety, other paths.**
  - The treasury can never go negative: `withTreasury` and `withdrawTreasury` throw on a negative result, and `PayRun` and `settle` only
    spend what is left.
  - `Payee` rejects a negative wage, so a broken save cannot mint emeralds through `settle`.
  - Permissions: commands need op level 2. A right-click checks `DEPOSIT_TREASURY` against the rank read from saved data. Screen actions go
    through `ActionGate` (rate limit, open menu, epoch, then `BAD_AMOUNT` before the permission check).
  - Save and reload: `payrollSurvivesReload` reads back an equal payroll, workers with their levels, and the treasury.
- Observation, no fix needed: if a Heart chunk loads on a later day and a deposit lands in the same tick before `WageSystem` (which runs at
  END_SERVER_TICK), that deposit settles the previous day's strikers, and the dawn run then charges them again. The cost is at most one extra
  wage per striker, once, and only in that exact tick.

1. **`src/test/java/dev/villageheart/core/sim/ScenarioFilesTest.java`, `starterHasItsActionsAndAssertions`: Layer 1 is red.**
   - What's wrong: M12 added `{ "action": "command", "command": "villageheart treasury add 32" }` and three wage assertions to

   - Then run `scripts/verify.sh` (full) to exit 0 and say so in PROGRESS. As far as I can tell, PROGRESS never recorded a green full verify
     at this head.
2. **`src/main/java/dev/villageheart/economy/Treasury.java`: the put-back on a throw can duplicate emeralds (in `depositInventory`, and
   likewise in `depositFromHand`).**
   - What's wrong:
     - `depositInventory` removes the emeralds, then calls `deposit()`. `deposit` → `writeAndSettle` writes the treasury
       (`data.update(v -> v.withTreasury(...))`) and *then* runs `Wages.mirrorNeeds` (entity writes), `changed()` (`HeartFacts.invalidate`,
       `HeartMenu.markAllDirty`) and the log line.
     - If any of those throws, the `catch` puts all `removed` emeralds back into the inventory, but the treasury already holds them. The
       emeralds are duplicated.
     - `depositFromHand` has the matching flaw: if `deposit` throws after the write, `stack.shrink` is skipped, so the emeralds are credited
       and still in the hand.
   - It is unlikely (it needs an exception in the mirror or menu code), but this is the money path, and the class Javadoc promises "never
     lost or made".
   - Expected:
     - Put the emeralds back only if the treasury write did not happen. For example, read the treasury before the write and compare after the
       throw, or split `deposit` into a write step whose failure triggers the put-back and post-write side effects that run in their own
       try/catch, are logged, and never undo or redo the item move.
     - Do the same for the hand path: shrink as soon as the write has returned.
     - Add a test for it, such as a GameTest with a test-only hook that makes a post-write side effect throw once. Assert that inventory plus
       treasury is unchanged, and that the same holds for a throw before the write.
